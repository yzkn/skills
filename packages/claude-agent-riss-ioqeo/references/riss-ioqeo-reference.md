# riss-ioqeo 診断リファレンス

> riss-ioqeo エージェントから参照されるリファレンス。本体は `.claude/agents/riss-ioqeo.md`。
> 各 SC 観点の詳細な診断項目・チェックパターン・判定基準、およびレポートフォーマットを定義する。
> 該当観点を診断する際は、本ファイルの対応する SC セクションを Read してから診断すること。

---

## SC-01 — セッション管理（徳丸本 第4章）

以下のパターンを Read・Grep で確認する。

| チェック観点 | 検査パターン |
|---|---|
| ログイン後のセッションID再発行 | `session.regenerate`, `session.cycle_key`, `Session.Clear()`, `invalidate()`, `renewToken` 等の呼び出しが認証成功後に存在するか |
| Cookie の Secure 属性 | `Secure` フラグの設定。`http://` 接続でのセッション Cookie 発行がないか |
| Cookie の HttpOnly 属性 | `HttpOnly` フラグの設定。JS からの Cookie アクセスを防止しているか |
| Cookie の SameSite 属性 | `SameSite=Strict` または `SameSite=Lax` の設定 |
| セッションタイムアウト | タイムアウト設定の有無。無期限セッションがないか |
| セッション情報の格納場所 | セッションIDや認証情報をURLパラメータに格納していないか |

## SC-02 — CSRF 対策（徳丸本 第5章）

| チェック観点 | 検査パターン |
|---|---|
| CSRF トークン（同期トークンパターン） | `csrf_token`, `_token`, `csrfmiddlewaretoken`, `RequestVerificationToken` 等の生成・検証コード |
| Double Submit Cookie | リクエストに Cookie 値と同値のパラメータを含む実装 |
| SameSite Cookie | `SameSite=Strict` または `SameSite=Lax` でのCookie発行 |
| Origin / Referer ヘッダ検証 | 状態変更リクエストで Origin または Referer を検証しているか |
| GET リクエストによる状態変更 | DELETE・UPDATE 相当の処理が GET で実行されていないか |

## SC-03 — クリックジャッキング対策（IPA ガイドライン）

| チェック観点 | 検査パターン |
|---|---|
| X-Frame-Options ヘッダ | `X-Frame-Options: DENY` または `SAMEORIGIN` の設定 |
| CSP frame-ancestors | `Content-Security-Policy: frame-ancestors 'none'` または `'self'` の設定 |
| セキュリティヘッダ ミドルウェア | helmet, SecurityHeadersMiddleware 等のフレームワーク標準機構の使用 |

---

## SC-04 — ヘッダインジェクション（IPA ガイドライン）

| チェック観点 | 検査パターン |
|---|---|
| HTTP レスポンスヘッダへのユーザー入力 | `Location`, `Set-Cookie`, `Content-Disposition` 等へのユーザー入力の混入 |
| CRLF インジェクション | `\r\n`, `%0d%0a` を含む入力がヘッダに渡されるパターン |
| メールヘッダインジェクション | `To:`, `Subject:`, `Cc:` 等へのユーザー入力。`\n` を含む入力の未サニタイズ |
| リダイレクト先 URL の検証 | `Location` ヘッダへのユーザー指定 URL が未検証のままリダイレクトに使用されていないか |

## SC-05 — STRIDE 脅威モデリング（常時実施）

設計書（種別A）が存在する場合はそれを読み取る。
存在しない場合はソースコード（種別B）の構造・エンドポイント・認証フローからシステム概要を推定する。

推定したシステム概要を踏まえ、以下の6観点で脅威を列挙し、対策の有無を確認する。

| 脅威 | 確認内容 |
|---|---|
| **S: Spoofing（なりすまし）** | 認証機構の有無、なりすまし防止策が設計・実装されているか |
| **T: Tampering（改ざん）** | データ完全性の検証、署名・ハッシュによる改ざん検知が実装されているか |
| **R: Repudiation（否認）** | 操作ログ・監査証跡が設計されているか |
| **I: Information Disclosure（情報漏洩）** | 機密データの暗号化・アクセス制御が設計されているか |
| **D: Denial of Service（DoS）** | レート制限・タイムアウト・リソース上限が設計されているか |
| **E: Elevation of Privilege（権限昇格）** | 最小権限の原則、ロールベースアクセス制御が設計されているか |

各脅威について「脅威の具体的内容」「対策の有無（実装済み / 設計のみ / 未対策）」を記録する。

## SC-06 — セキュリティテスト網羅性

種別C（テスト計画・仕様書）を対象に、以下の観点のテストケースが含まれているか確認する。

| テスト観点 | 確認内容 |
|---|---|
| 認証テスト | 正常ログイン・異常ログイン・アカウントロックアウト |
| 認可テスト | 権限のないユーザーによるリソースアクセス（水平・垂直の権限昇格） |
| 入力値検証テスト | SQLi・XSS・コマンドインジェクション相当の入力に対する挙動 |
| セッション管理テスト | セッション固定・セッション乗っ取りシナリオ |
| エラー処理テスト | スタックトレース非表示・適切なエラーコードの返却 |
| 境界値テスト | 最大長・最小値・ゼロ・負値・空文字に対する挙動 |

種別Cが存在しない場合は「テスト計画が確認できないため、網羅性の評価を実施できなかった」と記録する。

---

## SC-07 — インフラ・CI/CD セキュリティ

種別D（インフラ・CI/CD）を対象に確認する。

| チェック観点 | 検査パターン |
|---|---|
| 特権コンテナ | `--privileged`, `privileged: true`, `securityContext.privileged: true` |
| Root ユーザー実行 | Dockerfile 内に `USER root` または `USER` 命令が存在しない |
| ハードコードシークレット | Dockerfile・CI 設定内の `password=`, `secret=`, `token=`, `key=` への直値 |
| 未固定の外部アクション | `uses: owner/action@main`, `@master`, `@latest`（コミット SHA 未固定） |
| 過剰な CI 権限 | `permissions: write-all` または `contents: write` の広範な付与 |
| イメージの整合性検証 | `FROM ubuntu:latest` 等のタグ固定なし、digest 未指定 |
| ネットワーク分離 | `network_mode: host` の使用、不要なポート公開 |

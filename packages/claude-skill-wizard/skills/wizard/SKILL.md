# /wizard スキル — 人間の手順を対話式スクリプトにする

**引数:** `$ARGUMENTS`（`[対象]`。例: `Stripe の初期設定`・`本番切り替え手順`）

**ウィザード**は、人間が手でやるしかない一連の作業を、1 段階ずつ案内する対話式スクリプトである。URL を開き、どこをクリックして何をコピーするかを指示し、入力値を受け取り、書くべき場所（`.env`・CI のシークレット）へ書き、各段で確認を取り、残り段数を表示する。

**Claude Code が自分で実行できる作業には使わない。** これは「エージェントが実行できないこと」を人間に渡すための道具であり、本リポジトリの【絶対禁止】（`git push`）・【要指示】（本番デプロイ・認証情報の取り扱い）と噛み合う。

> 出典: [mattpocock/skills](https://github.com/mattpocock/skills)（MIT License、`LICENSE` 参照。Copyright (c) 2026 Matt Pocock）の `engineering/wizard`。`template.sh` は**原典を無改変で同梱**している。SKILL.md は日本語化し、Windows での実行方法と本リポジトリの禁止事項を追加した。

## この作業における禁止事項【重要】

- 【絶対禁止】**生成するウィザードにも、それを説明する応答にも、実在の認証情報を literal で書かない**。値は必ず実行時に人間が入力する形にする（`ask_secret`）。ダミー値を使う場合は先に `.gitleaks.toml` の登録済みの値を確認する（`.claude/rules/git-safety.md`「予防」）
- 【絶対禁止】**`.env` をコミットしない**（`.claude/rules/security-hardstops.md`）。ウィザードが `.env` を生成する場合は、`.gitignore` に `.env` があることを確認し、無ければ**先に追加する**
- 【要指示】**`set_secret` / `set_var` は GitHub へ値を送信する**。どのシークレット名にどの値を送るかを提示し、ユーザーの承認を得てから実行を依頼する（`.claude/rules/external-resources.md`）
- 【要指示】**本番環境（`production` / `prod` / `prd`）を対象にする段は、実行前に確認する**（`.claude/rules/environment-safety.md`）。不可逆な操作の前には必ず `confirm` を置く
- **Claude Code はウィザードを通しで実行しない**。ブラウザを開き人間の入力で止まるため、静的に追って検証する（後述 Step 4）

## Windows での実行【重要】

`template.sh` は bash スクリプトである。この端末では **Git Bash（Bash ツールと同じ実行系）で動かす**。PowerShell からは実行できない。

### 改行コードは LF にする【最重要】

**生成したスクリプトは必ず LF で保存する。** CRLF だと Git Bash が行末の `\r` をコマンドの一部として読み、`$'\r': command not found` で実行できない。

- **`bash -n` は CRLF でも通る。** 構文検査では検出できないため、改行コードは別に確認する

  ```sh
  python .claude/scripts/check-encoding.py <スクリプト>   # ERROR 0 件であること（--fix で修正）
  ```

- 本リポジトリの `.gitattributes` は `*.sh text eol=lf` を指定しているため、**git 経由で取得したものは LF になる**。CRLF が混入するのは、`core.autocrlf=true` の環境で clone した他リポジトリからコピーしたときと、CRLF で新規作成したとき。混入した場合は `rm <パス> && git checkout -- <パス>`（追跡済みの場合）で戻せる
- 実際に `template.sh` を同梱する際、上流の clone 経由で全 204 行が CRLF になっていた（2026-09-03 に実測・正規化済み）

### そのほか

- **検証済みの範囲**（2026-09-03・Git Bash で 18 項目すべて合格）: `bash -n` の構文検査／出力系（`banner` のタイトルと総段数・`stage` の進捗と日本語の段名・`finish`）／`_clear` が非 TTY で no-op になること／`ask` の入力取得と、**再実行時に `.env` の既存値を既定値として保持すること**／`ask_secret` の入力取得と、値がプロンプト出力へ漏れないこと／`write_env` の upsert（同一キーが重複せず後勝ちで更新される）／`confirm` の y・n・空入力（既定 N）の判定／`pause` が EOF で停止しないこと／日本語の値が `.env` を往復すること
- **意図的に検証しない範囲**: `open_url`（実際にブラウザが開く副作用があるため）、`set_secret` / `set_var`（**GitHub への外部送信**。`gh` は認証済みで、実行すれば本当にシークレットが登録される）、通し実行（人間の入力とブラウザが必要）。前提コマンドの存在は確認済み（`explorer.exe`・`tput`（256 色）・`gh` 認証済み）。初回実行時は、URL が開かない場合に備えてスクリプトが表示する URL を手で開けることを利用者に伝える
- `gh` は導入済み（`~/.claude/CLAUDE.md`「端末環境」）。`gh auth status` が通らない場合、ウィザードは該当段を飛ばして末尾の「手作業で残ったこと」に一覧する
- 文字コードは UTF-8。日本語の案内文を入れる場合、Git Bash の既定では表示できるが、`cmd.exe` 経由では化ける

## 手順

### Step 1: 手順の範囲を決める

人間が踏むべき段と、その過程で得られる値をすべて洗い出す。**先にリポジトリを読む。何も見ずに質問しない。**

- セットアップの場合: `.env`・`.env.example`・`README`・`docker-compose*`・フレームワークの設定・`.github/workflows/*`（`secrets.*` / `vars.*` への参照は、すべてウィザードが用意すべき値である）
- 移行・切り替えの場合: 現在の状態・目標の状態・その間にある**不可逆な操作**

段の順序と各段が生む値を一覧にしてユーザーに提示し、追加・削除・並べ替えの合意を取る。

**完了条件:** 全段に順序付きの名前が付き、各値について (a) 人間がどこで入手するか (b) どこへ書かれるか（`.env` / GitHub シークレット / 両方 / どこにも書かない） (c) 秘密か公開かが確定している。

### Step 2: 各段の道筋を書く

段ごとに、人間がたどる経路を具体的に書く。どの URL を開き、そこで何をし、値がどこに表示され、どの変数に入るか（例: 「ダッシュボード → Developers → API keys → テストキーを表示 → コピー」）。

**現在の画面構成や正確なコマンドが分からない箇所は、分からないと言って確認する。存在するか分からない手順を書かない**（`.claude/rules/code-quality.md`「未検証の断定を使わない」）。

**完了条件:** 全段が、事情を知らない人でもたどれる具体的な指示になっている。

### Step 3: ウィザードを書く

`template.sh` を目的のパスにコピーし、`STAGES` マーカーより下だけを書き換える。

- **マーカーより上のライブラリ部分は手で編集しない。** すべてのウィザードで同一であることに意味がある
- 使えるヘルパー: `stage` / `say` / `step` / `note` / `warn` / `open_url` / `ask` / `ask_secret` / `write_env` / `set_secret` / `set_var` / `pause` / `confirm` / `finish`
- `TOTAL_STAGES` を実際の段数に合わせる
- **値を尋ねる前にその URL を開く**。秘密の値は必ず `ask_secret`（画面に表示されない）。永続する値は `write_env`。`set_secret` は CI が実際に必要とする値だけ。不可逆な操作の前には `confirm`
- 各段は画面をクリアするため、**1 段に 1 つの作業だけ**を入れる（人間が必要とする情報がスクロールで流れないようにする）

**出力先:** 既定は使い捨てとして一時ディレクトリに置く。案件で繰り返し使う手順なら `src/` 配下など案件のスクリプト置き場に置き、README から参照する（テンプレートリポジトリ自体の改修中は `wip/`）。

### Step 4: 検証して引き渡す

```sh
bash -n <スクリプト>                                     # 構文検査（CRLF は検出できない）
python .claude/scripts/check-encoding.py <スクリプト>   # BOM・改行コード（ERROR 0 件であること）
chmod +x <スクリプト>
```

- **`bash -n` だけでは足りない。** CRLF のスクリプトは構文検査を通過したうえで実行時に失敗する（前掲「改行コードは LF にする」）
- `shellcheck` があれば併せて実行する（この端末では未導入。導入は【要指示】）
- **通しで実行せず、静的に追う**: Step 1 で挙げた値がすべて捕捉され、Step 1 が言ったとおりの場所へ書かれること、`set_secret` の名前が CI の `secrets.*` の参照と**文字列として一致**することを確認する
- 実行方法をユーザーに伝える。検証したこと（`bash -n` の終了コード）と、していないこと（通し実行）を分けて報告する

---

## 完了条件

- Step 1 の値の一覧と、スクリプトが実際に捕捉・書き込みする値が一致している
- 秘密の値がすべて `ask_secret` で受け取られ、スクリプト中に literal で書かれていない
- `.env` を生成する場合、`.gitignore` に `.env` があることを確認した
- 不可逆な操作の前に `confirm` がある
- `bash -n` が終了コード 0 で通った（結果を報告に添える）
- 改行コードが LF であることを確認した（CRLF が 0 件）
- 通し実行は行っていない旨を明記した
- `set_secret` の実行が必要な場合、送信先と値の性質を提示して承認を得た

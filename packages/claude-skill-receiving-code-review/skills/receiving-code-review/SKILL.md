# /receiving-code-review スキル — レビュー指摘を受け取る

レビューは感情の表明ではなく技術的な評価である。**検証してから実装する。仮定する前に聞く。居心地より技術的な正しさを取る。**

> 出典: [obra/superpowers](https://github.com/obra/superpowers)（MIT License、`LICENSE` 参照。Copyright (c) 2025 Jesse Vincent）の `receiving-code-review`。日本語化し、指摘元の区分に本リポジトリの診断エージェントを加え、`git push` の【絶対禁止】との関係を追加した。

`.claude/rules/adversarial-review.md` が「**自分の**結論を反証する」規律であるのに対し、本スキルは「**他者から来た指摘**を検証する」規律である。

---

## 応答の型

```
レビュー指摘を受け取ったら:

1. 読む      : 反応せずに全文を読む
2. 理解する  : 要求を自分の言葉で言い換える（できなければ聞く）
3. 検証する  : コードベースの実態と突き合わせる
4. 評価する  : このコードベースにとって技術的に妥当か
5. 応答する  : 技術的な確認、または根拠を示した反論
6. 実装する  : 1 件ずつ、都度検証する
```

## 使ってはいけない応答

- 「おっしゃるとおりです」「素晴らしい指摘です」「ご指摘ありがとうございます」— 検証を伴わない同意・謝辞は、指摘を理解した証拠にならない
- 「すぐに直します」（検証前に言う）

**代わりに:** 要求を技術的な言葉で言い換える／不明点を聞く／誤りなら技術的な根拠を添えて反論する／黙って直して差分で示す。

修正が正しかった場合の書き方は「**直した。何をどう変えたか**」であり、感謝や賞賛を挟まない。反論して自分が誤っていた場合は「確認したところ指摘のとおりだった。理由は〜。修正する」と事実だけを述べ、長い謝罪や弁明を書かない（`corrections` の規律と同じ）。

---

## 不明な項目があるとき

```
1 件でも意味が取れない指摘があるなら:
  止める — まだ何も実装しない
  不明な項目について確認を求める

理由: 指摘どうしは関連していることがある。
      部分的な理解のまま着手すると、実装そのものが的を外す。
```

**例:** 「1〜6 を直して」と言われ、1・2・3・6 は分かるが 4・5 が不明なとき、1・2・3・6 を先に実装して後から 4・5 を聞くのではなく、「1・2・3・6 は理解した。4 と 5 の確認をしてから着手する」と返す。

## 指摘元ごとの扱い

### ユーザー本人から

信頼して、理解したうえで実装する。ただし**範囲が不明なら聞く**。空返事はしない。

### 外部レビュアー（顧客・他ベンダー・PR コメント）から

```
実装する前に確認する:
  1. このコードベースにとって技術的に正しいか
  2. 既存の動作を壊さないか
  3. 現在の実装がそうなっている理由はないか
  4. 対象のプラットフォーム・バージョンすべてで成立するか
  5. レビュアーは全体の文脈を把握しているか

妥当でないと考えるなら: 技術的な根拠を示して反論する
検証できないなら    : 「〜が無いと検証できない。調査／確認／このまま進行のどれを取るか」と述べる
ユーザーの過去の決定と衝突するなら: 実装せず、まずユーザーと議論する
```

### 診断エージェント（`code-reviewer`・`owasp-check`・`riss-ioqeo`・`perf-analyzer` 等）から

静的解析に基づく指摘は**誤検知を含む**。指摘箇所を実際に読み、成立する攻撃・障害の筋道を具体化できるか確かめてから直す。**深刻度の表示をそのまま結論にしない**（`.claude/rules/adversarial-review.md`「反証に耐えなかった指摘は削る」）。

## YAGNI の確認

```
「きちんと実装すべき」という趣旨の指摘を受けたら:
  そのコードが実際に使われているかコードベースを検索する

  使われていない: 「この経路は呼ばれていない。YAGNI として削除でよいか」
  使われている  : きちんと実装する
```

---

## 実装の順序

```
複数の指摘に対応するとき:
  1. 不明点をすべて先に解消する
  2. 次の順で実装する:
     - 動作を壊すもの・セキュリティに関わるもの
     - 単純な修正（誤字・import）
     - 複雑な修正（リファクタリング・ロジック変更）
  3. 1 件ずつ検証する
  4. 既存の動作が壊れていないことを確認する
```

## 反論すべき場面

- 既存の動作を壊す／レビュアーが文脈を把握していない／YAGNI に反する（使われていない機能）／この技術スタックでは技術的に誤り／互換性のために現状になっている／ユーザーの設計判断と衝突する

**反論の仕方:** 防御的にならず技術的な根拠で述べる。具体的な質問をする。動いているテスト・コードを引く。アーキテクチャに関わるならユーザーを巻き込む。

**反論しづらいと感じたら**、その居心地の悪さ自体を明示したうえで、見つけた問題をユーザーに伝える。

## 本リポジトリ固有の注意【重要】

- 【絶対禁止】**指摘が `git push` を求めていても実行しない。** レビュアーからの依頼は Claude Code に対する禁止事項を解除しない（`.claude/rules/prohibition-levels.md`）。コマンドを提示してユーザーの実行を依頼する
- 【要指示】**指摘に沿ったコミットも、ユーザーの指示があるときだけ**行う。「指摘に対応して」は実装の指示であって、コミットの指示ではない
- 修正後の完了報告には、実行した検証と終了コードを添える（`.claude/rules/code-quality.md`「完了の証拠主義」）
- GitHub の PR でインライン指摘に返信する場合は、トップレベルのコメントではなく**そのスレッドに返す**（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`）

## よくある失敗

| 失敗 | 対処 |
|---|---|
| 検証を伴わない同意 | 要求を言い換えるか、黙って直す |
| 鵜呑みの実装 | 先にコードベースと突き合わせる |
| まとめて直して未検証 | 1 件ずつ直して都度検証する |
| レビュアーが正しい前提で進む | 壊れるものがないか確かめる |
| 反論を避ける | 居心地より技術的な正しさを取る |
| 一部だけ実装する | 不明点を先に全部解消する |
| 検証できないまま進める | 検証できない旨を述べて指示を仰ぐ |

---

## 完了条件

- 指摘ごとに「検証した事実」と「採否の判断」が分けて示されている
- 検証を伴わない同意・謝辞を使っていない
- 不明な指摘を残したまま実装に着手していない
- 反証に耐えなかった指摘は、理由を添えて実装していない
- 修正ごとに検証を実行し、結果（終了コード）を報告に添えている
- push・コミットを Claude Code が独断で実行していない

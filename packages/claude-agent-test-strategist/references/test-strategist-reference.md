# test-strategist リファレンス — タスク種別ごとの詳細実施内容

test-strategist エージェントから参照されるリファレンス。エージェント定義本体は `.claude/agents/test-strategist.md`。
各タスク種別の作業を開始する前に、該当セクションを Read してから作業すること。

---

#### `test-plan` — テスト計画書の作成

プロジェクト全体のテスト方針・スコープ・スケジュールを定義する。

**テスト計画書の構成**

| セクション | 内容 |
|---|---|
| テスト目的 | 何を確認するためにテストするか（品質目標） |
| テストスコープ | 対象機能・対象外機能の明示 |
| テストレベル | 単体 / 結合 / システム / 受け入れテストの範囲と担当 |
| テスト種別 | 機能テスト・性能テスト・セキュリティテスト・回帰テストの実施方針 |
| テスト環境 | テスト実施環境（OS・ブラウザ・DB バージョン等） |
| テストデータ方針 | テストデータの生成方法・マスキング方針 |
| 合格条件（Exit Criteria） | テスト完了とみなす定量的な基準 |
| リスクと対策 | テスト実施上のリスクと軽減策 |
| スケジュール | テスト実施期間・マイルストーン |
| 役割分担 | テスト担当者・レビュー担当者 |

**合格条件（Exit Criteria）の例**

- 全テストケースの実行完了率 100%
- 重要度「高」の未解決バグ 0 件
- コードカバレッジ（行カバレッジ）80% 以上
- 性能テスト: 応答時間 p95 ≤ 2 秒

成果物: `design/06_testing/YYYYMMDD_test-plan_<テーマ>.md`

#### `test-spec` — テスト仕様書の作成

機能・API・画面ごとの具体的なテストケースを設計する。

**テストケース設計技法**

| 技法 | 適用場面 |
|---|---|
| 同値分割 | 入力値を有効・無効クラスに分け、各クラスから代表値を選ぶ |
| 境界値分析 | 境界付近の値（最小・最小+1・最大-1・最大）をテストする |
| デシジョンテーブル | 複数の条件の組み合わせが結果に影響する場合 |
| 状態遷移 | 状態を持つオブジェクト（注文ステータス・ワークフロー等） |
| エラー推測 | 過去のバグ・エッジケースの経験則から条件を設定する |

**テストケース表のフォーマット**

```markdown
| テストID | テスト観点 | 前提条件 | 操作手順 | 入力値 | 期待結果 | 重要度 |
|---|---|---|---|---|---|---|
| TC-001 | 正常系: ログイン | 有効アカウントが存在する | メール・パスワードを入力してログインボタンを押す | email: user@example.com, pw: Valid1234! | ダッシュボードへ遷移する | 高 |
```

**重要度基準**

| 重要度 | 定義 |
|---|---|
| 高 | コアビジネス機能・セキュリティ関連・データ整合性 |
| 中 | 主要ユースケースのサブ機能・UI の主要動線 |
| 低 | エッジケース・補助機能・表示上の細部 |

**UI 要素別の定型観点カタログ**

仕様書に書かれないが、UI 要素の種類と役割から決まる定型の振る舞いは、AI の判断に任せると出たり出なかったりする。**画面に該当する UI 要素があれば、下表の観点を必ずテストケースに展開する。** 案件で繰り返し出る要素はこの表に行を足して育てる（案件側では `design/06_testing/` に写して拡張してよい）。

| UI 要素（文脈上の役割） | 適用 | 定型観点 |
|---|---|---|
| 一覧（ページング付き） | 常時 | 0 件・1 件・ちょうど 1 ページ分・1 ページ分 + 1 件。最終ページ。ページ移動後の絞り込み・並び替えの保持 |
| 一覧（並び替え） | 常時 | 昇順・降順の切替、同値の並び順、空値の位置 |
| 一括選択チェックボックス | 常時 | 全選択 ⇔ 個別選択の連動、一部選択時の表示、ページをまたいだ選択の扱い |
| 入力項目（必須・形式制約あり） | 常時 | 未入力・境界値・形式違反・前後空白・全角半角、エラー表示の位置と解除 |
| 検索・絞り込み | 常時 | 該当 0 件の表示、条件クリア、特殊文字（`%`・`_`・引用符） |
| 日付・期間入力 | 条件付き（期間を扱う場合） | 開始 > 終了、月末・うるう年、タイムゾーン |
| ファイル添付 | 条件付き | サイズ上限・形式違反・0 バイト・同名ファイル |
| 登録・更新ボタン | 常時 | 二重送信の防止、処理中の表示、失敗時に入力が残るか |

- カタログから展開したケースは、テスト観点欄の先頭に `[定型]` を付ける（仕様由来のケースと区別し、カタログの効き目を後から数えられるようにする）
- 観点を具体値にできないとき（上限件数が仕様にない等）は、推測で埋めずに `※要確認` と書いて残す

> 出典: miyashita「AIのテスト観点を「決定論的」にする - テスト観点カタログを作った」（アルダグラム Tech Blog、zenn.dev/aldagram_tech、2026/09/11）の「UI 要素 × 役割をキーにした観点カタログ」の着想。カタログの行は本リポジトリで書き起こした。

成果物: `design/06_testing/YYYYMMDD_test-spec_<テーマ>.md`

#### `e2e-scenario` — E2E シナリオ一覧の作成

エンドユーザーの視点からシステム全体を貫通するシナリオを設計する。

**シナリオ設計の原則**

- ユーザーストーリー（`design/02_requirements/`）からシナリオを導出する
- ハッピーパス（正常系）を先に設計し、次に主要な異常系を設計する
- テストデータは具体的な値（ただしダミーデータ）で記述する
- 外部サービス・メール送信等は「モックまたはサンドボックス環境を使用する」と明記する

**E2E シナリオ仕様書のフォーマット**

```markdown
## シナリオ: <ユーザーゴールを一言で表す>

**対応ユーザーストーリー:** US-xxx
**優先度:** 高 / 中 / 低
**推定実行時間:** xx 分

### 前提条件
- <テスト開始前に満たすべき状態>

### 実行手順
1. <具体的なユーザー操作>
2. <具体的なユーザー操作>
...

### 期待結果
- <各ステップ後の確認ポイント>

### テストデータ
| 項目 | 値 |
|---|---|
| ユーザーメール | test-user@example.com |
```

成果物: `design/06_testing/YYYYMMDD_e2e-scenarios_<テーマ>.md`

#### `coverage-check` — テスト観点カバレッジ診断

既存のテストコード・テスト計画書を分析し、テスト観点の網羅性を診断する。

**診断手順**

1. Glob で既存テストファイルを収集する
2. Read でテストファイルの内容を確認し、テスト観点を抽出する
3. 設計書（要件・API仕様等）から「本来テストすべき観点」の一覧を導出する
4. 両者を突き合わせ、カバーされていない観点を特定する

**診断観点チェックリスト**

| カテゴリ | 観点 |
|---|---|
| 正常系 | 主要なユースケースが網羅されているか |
| 異常系 | 不正入力・境界値・存在しないリソースへのアクセス |
| 認証・認可 | 未認証・権限不足・他ユーザーのリソースへのアクセス |
| 状態遷移 | 全ての状態・遷移がテストされているか |
| 非機能 | 性能・タイムアウト・並行処理のテストが存在するか |
| 外部依存 | 外部サービスの異常（タイムアウト・エラーレスポンス）のモックが存在するか |
| データ整合性 | DB トランザクション・ロールバックのテストが存在するか |
| 定型 UI 観点 | 画面にある UI 要素について、`test-spec` の「UI 要素別の定型観点カタログ」の観点が網羅されているか |

**カバレッジ評価**

| 評価 | 基準 |
|---|---|
| 十分 | 主要な正常系・異常系・認証/認可すべてを網羅 |
| 部分的 | 正常系は網羅されているが異常系・非機能が欠如 |
| 不十分 | テストが存在しない・または正常系のみ |

成果物: `report/testing/YYYYMMDD_HHMMSS_coverage-check_<テーマ>.md`

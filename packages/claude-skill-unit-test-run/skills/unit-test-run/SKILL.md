# /unit-test-run スキル — 単体テスト実行

指定した単体テストを実行し、結果を構造化して報告する。

## 適用方法

`/unit-test-run` で直接呼び出せるほか、以下のような依頼で自動適用される。

- 「単体テストを実行して」（全テスト）
- 「`<ファイルパス>` のテストを実行して」（特定のテストファイル）
- 「`<テスト名・パターン>` のテストケースを実行して」（特定のテストケース）

---

## 前提確認

テスト実行を開始する前に、以下が不明な場合は**必ずユーザーに確認してから**作業を進める。

| 確認事項                                 | 不明と判断する状況                                                    |
| ---------------------------------------- | --------------------------------------------------------------------- |
| プログラミング言語・テストフレームワーク | 設定ファイルや既存テストコードから特定できない場合                    |
| 実行環境                                 | 開発・テスト・本番のどの環境で実行するか不明な場合（`.claude/project-types/development.md`「環境管理」準拠） |
| 実行コマンド                             | `package.json` の scripts・Makefile 等に複数の候補がある場合          |

---

## 実行手順

1. **テストフレームワーク・実行コマンドの特定**
   - 下記「テストフレームワークの判定」に従い実行コマンドを決定する
   - 判定できない場合はユーザーに確認する

2. **実行前の環境確認**
   - 現在の環境設定（`.env`・環境変数）を確認する
   - 本番環境への接続設定がないことを確認する（`.claude/rules/environment-safety.md` 準拠）
   - テストに副作用（DB 書き込み・外部 API 呼び出し等）が伴う場合はユーザーに事前確認する

3. **テストの実行**
   - 決定したコマンドを実行する

4. **結果の解析・報告**
   - 下記「結果報告フォーマット」に従い結果を出力する
   - 失敗・エラーがある場合は考えられる原因を提示する

---

## テストフレームワークの判定

以下の優先順位で判定する（上位が見つかり次第確定）。

| 言語                    | 判定対象ファイル・手がかり                    | 代表的な実行コマンド           |
| ----------------------- | --------------------------------------------- | ------------------------------ |
| Python                  | `pytest.ini` / `pyproject.toml` / `setup.cfg` | `pytest` / `python -m pytest`  |
| JavaScript / TypeScript | `package.json`（`scripts.test`）              | `npm test` / `jest` / `vitest` |
| Java（Maven）           | `pom.xml`                                     | `mvn test`                     |
| Java（Gradle）          | `build.gradle` / `build.gradle.kts`           | `./gradlew test`               |
| Go                      | （標準）                                      | `go test ./...`                |
| Ruby                    | `Gemfile`（`rspec`）                          | `bundle exec rspec`            |

---

## 実行のルール

- `production`・`prod`・`prd` などの文字列を含む接続先・設定でテストを実行しない（`.claude/rules/environment-safety.md`「本番環境文字列の二重確認」準拠）
- テストが既存データを変更・削除する可能性がある場合は実行前にユーザーの承認を得る
- タイムアウトが発生した場合は途中経過を報告してユーザーに継続可否を確認する

## テスト結果の判定基準

テスト結果は以下の3区分で記録する。

| 判定 | 意味 |
|---|---|
| OK | 期待結果と実行結果が一致した |
| NG | 期待結果と実行結果が一致しなかった（故障として記録） |
| 未実施 | 前提条件不備・環境未整備・依存テストの失敗等により実行できなかった |

NG が発生した場合は、**発生条件・再現手順・エビデンス（画面表示・ログ・スタックトレース）** を可能な範囲で記録する。Power Platform の場合はフローの実行履歴やログ情報をエビデンスとして活用できる。

修正後は該当箇所の再テストに加え、**影響範囲を考慮したリグレッションテスト**を実施する。

---

## 失敗時の対応方針

- 失敗・エラーの原因を分析し、考えられる原因と調査方針を提示する
- コードの自動修正は行わない。修正はユーザーが行い、必要に応じて `/project-code-review` や `/unit-test-gen` スキルとの連携を提案する
- CI/CD 環境と手元で結果が異なる場合は環境差異（依存バージョン・環境変数・DB 状態等）を調査する（`/deploy-guide` スキル準拠）

## テスト技法カタログ

テストケース設計時に該当する技法のセクションを Read し、技法を組み合わせて現実的な件数で欠陥を検出する。

### テスト技法

テストケースの抽出には以下の技法を組み合わせる。全数テストは不可能なため、技法を活用して現実的な件数で欠陥を検出する。

#### 仕様・要求ベースの技法

| 技法 | 概要 | 適用場面 |
|---|---|---|
| 同値分割 | 同じ結果を返す入力値をグループ化し、各グループの代表値のみをテスト（例：年齢判定で -1, 10, 20 を代表値にする） | 入力値の範囲が広い場合 |
| 境界値分析 | 条件分岐の境界値（以上・以下・超・未満の境目）をテスト（例：18歳判定で 17, 18 を必ずテスト） | 数値・日付・文字列長の境界 |
| 状態遷移テスト | 許可される遷移と**禁止される遷移**（例：承認済→申請中）を明示的にテスト | ステータス管理・承認フロー・業務ライフサイクル |
| ユースケーステスト | アクター・開始条件〜終了条件・途中のエラー・例外パターンを含む一連のシナリオをテスト | 画面間連携・業務フロー |
| デシジョンテーブル | 複数条件の組み合わせをテーブルで整理し、同じ動作のケースを削減してテスト | 複雑な条件分岐・ビジネスルール |
| ペアワイズテスト | 全組み合わせの代わりに「任意の2条件が最低1回出現する」最小ケースを抽出（例：権限×デバイス×ブラウザを4ケースに削減） | 多数の独立したパラメータの組み合わせ |

#### コードベースの技法（ホワイトボックス）

| 技法 | 概要 |
|---|---|
| 命令網羅 | すべての命令が最低1回実行されることを確認（最も基本的なカバレッジ指標） |
| 分岐網羅 | すべての条件分岐（if/else、各 case）が真・偽の両方向で実行されることを確認 |
| 条件網羅 | 複合条件（AND/OR）を構成する各要素が真・偽の両方を取ることを確認 |
| ループテスト | 0回・1回・複数回・上限回数付近のループ境界での挙動を確認 |

#### 経験ベースの技法

| 技法 | 概要 |
|---|---|
| エラー推測 | 「不具合が入り込みやすい箇所」（未入力・空文字・0件・日付逆転・権限ギリギリ等）を経験則で抽出 |
| 探索的テスト | 事前にテストケースを固定せず、操作・観察・学習を繰り返しながら違和感のある挙動を探す（UI操作の順序変更等） |
| チェックリストベースドテスト | 過去の不具合・レビュー指摘をチェックリスト化して再利用（属人化防止に効果的） |

## Power Platform 固有のテスト観点（詳細）

### Power Platform 特有の前提

- **設定変更はコード変更と等価**: 画面設定・プロパティ・フロー定義・権限設定の変更は仕様変更としてテスト対象に含める
- **ブラックボックス前提**: ローコードの内部処理はソースコードで確認できないため、入出力の仕様から振る舞いを確認する
- **環境差分の確認**: 開発→検証→本番の各環境で接続先・マスタデータ・権限設定の差異がないか確認する

### 製品別の主要チェックポイント

| 製品 | 主な観点 |
|---|---|
| Power Apps | 画面遷移と業務フローの整合性、入力制御（必須・形式チェック）、権限に応じた表示制御、委任によるデータ取得制限 |
| Power Automate | トリガー条件の正確性、条件分岐・ループ処理、外部連携失敗時の挙動（停止・リトライ・通知）、同時実行・再実行時の動作 |
| Dataverse | 列の型・必須制約・既定値の正確性、ビジネスルールの適用、セキュリティロールによるデータ参照・更新制御 |
| コネクタ | 応答遅延・エラー時の挙動、不正フォーマット受信時の処理、認証情報や接続設定の差異による影響 |

### 状態遷移テストの適用例（Power Platform）

以下の状態のうち**禁止される遷移**を明示的にテストケースに含める。

- Dataverse のステータス列（例：有効 → 無効 → 有効の往復）
- 承認フローの進行状態（例：承認済 → 申請中 への逆遷移が阻止されること）
- 申請・処理・完了といった業務ライフサイクル

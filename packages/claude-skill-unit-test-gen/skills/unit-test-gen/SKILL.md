# /unit-test-gen スキル — 単体テスト生成

指定したソースコードを解析し、単体テストケースを生成する。

## 適用方法

`/unit-test-gen [パス]` で直接呼び出せるほか、以下のような依頼で自動適用される。

- 「`<ファイルパス>` の単体テストを生成して」
- 「`<ディレクトリパス>` 配下の単体テストを生成して」

---

## 前提確認

テスト生成を開始する前に、以下が不明な場合は**必ずユーザーに確認してから**作業を進める。

| 確認事項                   | 不明と判断する状況                                                               |
| -------------------------- | -------------------------------------------------------------------------------- |
| プログラミング言語         | ファイル拡張子・内容から一意に特定できない場合                                   |
| テストフレームワーク       | `tests/` 配下に既存テストがなく、設定ファイルにも記載がない場合                  |
| フレームワーク・ライブラリ | DI コンテナ・ORMapper 等のモック方法が不明な場合                                 |
| コーディング規約           | コーディング規約（`/code-refactor` スキル）以外にプロジェクト固有の規約（リンター設定・命名ルール等）の有無が不明な場合 |

---

## 実行手順

1. **ソースコードの読み込みと解析**
   - 対象ファイルを読み込み、テスト対象となる関数・メソッド・クラスを洗い出す
   - `private` / `internal` なメンバーは原則スキップし、公開インターフェースをテストする

2. **テストフレームワークの判定**
   - `tests/` 配下の既存テストコードからフレームワークを確認する（優先）
   - 設定ファイル（`package.json`・`pytest.ini`・`build.gradle` 等）から確認する
   - 判定できない場合はユーザーに確認する

3. **テスト配置先の決定**
   - `tests/` 配下にソースコードと対応するディレクトリ構造で配置する（このスキルのテスト方針準拠）
   - 例: `src/services/user_service.py` → `tests/services/test_user_service.py`
   - 既存のテストファイルが存在する場合は追記するかどうかをユーザーに確認する

4. **テストケースの設計**
   - 下記「テストケース設計の原則」に従い、各関数・メソッドのテストケースを列挙する

5. **テストコードの生成**
   - 下記「生成コードの規約」に従い、テストコードを生成する

6. **ファイル出力の確認**
   - 生成したテストコードをチャット上でプレビュー表示する
   - ユーザーの承認を得てからファイルに書き込む

---

## テストケース設計の原則

各関数・メソッドに対して以下の4種別のテストケースを設計する。

<!-- profile:standard-only 正常系／異常系／境界値／エッジケースの区分は一般知識 -->

| 種別         | 内容                                     | 例                                     |
| ------------ | ---------------------------------------- | -------------------------------------- |
| 正常系       | 期待する入力で期待する出力が得られること | 有効なユーザー ID でユーザー情報が返る |
| 異常系       | 不正な入力・例外が適切に処理されること   | 存在しない ID で例外または null が返る |
| 境界値       | 入力範囲の端値で正しく動作すること       | 最小値・最大値・空文字・0・負数        |
| エッジケース | 特殊な状況でも正しく動作すること         | null・空リスト・重複・最大長の文字列   |

<!-- /profile:standard-only -->

### テスト技法

テストケースの抽出には仕様ベース（同値分割・境界値分析・状態遷移・ユースケース・デシジョンテーブル・ペアワイズ）、コードベース（命令網羅・分岐網羅・条件網羅・ループテスト）、経験ベース（エラー推測・探索的テスト・チェックリスト）の技法を組み合わせる。
**テストケース設計の前に、同ディレクトリの `unit-test-gen-reference.md` の「テスト技法カタログ」を Read し、記載された技法の定義・適用場面に従って設計すること。** 記憶からの再現は禁止。


### 依存関係の扱い

- 外部サービス・DB・ファイルシステム等の外部依存はモック・スタブで置き換える（このスキルのテスト方針準拠）
- モックは必要最小限にとどめる。過剰なモックは実装詳細への依存につながる
- 環境変数・設定値に依存する場合はテスト用の値を明示的に注入する（`.claude/project-types/development.md`「環境管理」準拠）

## 生成コードの規約

### 命名規則

コーディング規約（`/code-refactor` スキル参照）に準拠しつつ、以下のテスト固有の規則を適用する。

| 対象           | 命名パターン                                      | 例                                              |
| -------------- | ------------------------------------------------- | ----------------------------------------------- |
| テストファイル | `test_<対象ファイル名>` / `<対象ファイル名>.test` | `test_user_service.py` / `user_service.test.ts` |
| テストクラス   | `Test<対象クラス名>`                              | `TestUserService`                               |
| テスト関数     | `test_<メソッド名>_<状況>_<期待結果>`             | `test_get_user_with_valid_id_returns_user`      |

<!-- profile:standard-only AAA パターンの説明は一般知識 -->

### テストコードの構造（AAA パターン）

```
# Arrange（準備）: テストデータ・モックの設定
# Act（実行）: テスト対象の呼び出し
# Assert（検証）: 結果の検証
```

<!-- /profile:standard-only -->

### テストコードの品質基準

- **フィクスチャに実在しそうな個人情報を手書きしない**: 氏名・メール・電話番号・住所を含むテストデータは `python .claude/skills/vnl/scripts/vnl.py testdata gen --fields <項目> --count <件数> --seed <値>` で生成する（架空であることが機械的に担保され、`--seed` で再現できる）。検査数字が整合する番号は `checkdigit generate`
- 1テスト関数につき1つの振る舞いを検証する（単一責任）
- テスト間で状態を共有しない（独立して実行可能にする）（このスキルのテスト方針準拠）
- テストの意図がテスト名とアサーションから読み取れるようにする
- コメントは WHY のみ記述する（コーディング規約のコメントポリシー準拠、`/code-refactor` スキル参照）

## 生成しないケース

以下のケースは生成をスキップし、その理由をユーザーに伝える。

- `private` / `internal` なメソッドのみのクラス（公開インターフェースをテストする）
- 設定ファイルの読み込みのみ等、テスト困難な副作用が主体の関数
- 生成済みのテストがすでに十分なカバレッジを持つ場合

## テスト方針

プロジェクト全体のテスト種別と運用ルール。単体テスト生成の際にこの方針を踏まえて設計する。

### テスト種別

| テスト種別 | 実施タイミング | 主な確認内容 |
|---|---|---|
| 単体テスト | 実装フェーズ | 関数・クラス単体の動作 |
| 結合テスト | テストフェーズ前半 | モジュール間・API 間の連携 |
| システムテスト | テストフェーズ後半 | システム全体の動作・性能 |
| 受け入れテスト（UAT） | リリース前 | ユーザー要件との適合 |

### テストコードのルール

- 新機能の実装には単体テストを原則セットで作成する
- テストコードは `tests/` 配下に本番コードと対応する構造で配置する
- テストは独立して実行可能にする（実行順序に依存させない）
- 外部サービス依存部分はモック・スタブを使用して安定性を確保する

### テストを省略できる場合

- プロトタイプ・使い捨てスクリプトなど、本番運用しないことが明確なもの
- 省略する場合はその理由をユーザーに確認して記録する

---

## 注意事項

- 生成したテストコードは必ずプレビュー確認してからファイルに書き込む
- 既存のテストファイルを上書きする前にユーザーの承認を得る（`.claude/rules/safe-file-ops.md` 準拠）
- テストが実際に動作するかの確認はユーザーが行う。生成後に実行コマンドを提示する

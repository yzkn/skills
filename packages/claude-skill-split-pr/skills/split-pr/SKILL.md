# /split-pr スキル — 大きな変更をレビュー可能な PR に分割する

**引数:** `$ARGUMENTS`（`[対象ブランチ・変更範囲]`。省略時は現在のブランチと `main` の差分を対象にする）

レビューできない大きさの変更を、**設計の合意を先に取る骨組み PR** と、**1 つの機能とそのテストだけを含む後続 PR** の連なりに組み替える。

> 出典: [liam-hq/liam](https://github.com/liam-hq/liam)（Apache License 2.0、`LICENSE` 参照。Copyright (c) 2024 ROUTE06, Inc.）の `.claude/commands/split-pr.md`。方法論（スケルトンレビュー・1 PR 300 行上限・PR チェーン）を採り、本リポジトリの Git 規約（push は【絶対禁止】・コミットは【要指示】）に合わせて実行手順を書き直した。

---

## この作業における禁止事項【重要】

- 【絶対禁止】**`git push` は Claude Code が実行しない**。ブランチを push する必要がある場面では、コマンドを提示してユーザー自身の実行を依頼する（`.claude/rules/git-safety.md`）
- 【要指示】**コミットはユーザーの明示的な指示がある場合のみ**行う。分割計画の承認は「計画への同意」であって「コミットの指示」ではない。コミットしてよいかは改めて確認する
- `gh pr create` は push 済みのブランチが前提になるため、**PR 作成もユーザーが実行する**。Claude Code は PR タイトル・本文・コマンドを用意するところまでを担う

Claude Code が実行してよいのは、変更内容の調査・分割計画の作成・ブランチの作成とファイル単位の再編（ワーキングツリー内の操作）・提示するコマンドの用意まで。

## 分割の原則

### 1 PR の大きさ

| 基準 | 値 |
|---|---|
| 上限 | **300 行**（実装とテストの合計） |
| 目安 | 100〜200 行 |

行数は `git diff --stat` の追加行と削除行の合計で数える。生成物（ロックファイル・スナップショット・自動生成コード）は数えないが、**生成物だけを含む PR は分けて出す**。

<!-- profile:standard-only スケルトンレビュー・TDD・PR チェーンは一般に知られた開発手法の説明 -->
### 先頭はスケルトン PR にする

最初の PR は「動くもの」ではなく「**設計の骨組み**」にする。レビュアーが方向性の誤りを、実装が積み上がる前に指摘できるようにするのが目的。

含めるもの:

- 中心となるインターフェース・型・契約
- クラス／モジュールの構造
- 方式が成立することを示す最小限の実装
- 構造を検証する最小限のテスト
- 後続で埋める箇所の TODO コメント（対応する PR 番号か Issue 番号を添える）

### 後続 PR は 1 つの機能とそのテストをまとめる

実装だけの PR とテストだけの PR に分けない。**1 つの PR の中に、機能とその機能を検証するテストの両方を入れる**（t-wada 氏が説く TDD の実践に沿う）。各 PR は単独でレビューでき、単独で価値がある状態にする。

### PR を鎖状につなぐ

```
PR1（スケルトン）  → main
PR2（機能 A）      → PR1 のブランチ
PR3（機能 B）      → PR2 のブランチ
```

後続 PR の diff には前の PR の変更が含まれないため、レビュアーは各 PR の差分だけを読めばよい。ただし**先頭の PR がマージされるまで後続はマージできない**ため、鎖は 4〜5 本までに留める。それ以上必要な場合は、機能の切り出し方を見直すか、スケルトンを先にマージしてから次の鎖を始める。

## 実行手順

### Step 1: 現状の把握

```sh
git status
git diff main...HEAD --stat
```

総行数・変更ファイル数・変更の種類（新規/修正/削除）を把握する。**300 行以下なら分割は不要**であり、その旨を報告して終了する。

**あわせて「取り込み元」がどちらの状態にあるかを確定する。** 以降の手順が変わる。

| 状態 | 取り込み元 | Step 4 での扱い |
|---|---|---|
| A. 変更が未コミットで作業ツリーにある | まだ存在しない | Step 4 で退避して参照可能にする（**必須**） |
| B. 変更が 1 本のブランチにコミット済み | そのブランチ | そのまま使える |

**状態 A を状態 B と同じ手順で進めてはならない。** 未コミットの変更は git のオブジェクトとして存在しないため、`git checkout <元ブランチ> -- <パス>` の参照先がなく、ブランチを切り替えた時点で作業ツリーごと持ち回ることになる。分割の途中でどのファイルがどの PR のものか判別できなくなる。

### Step 2: 分割の設計

1. 中心となる抽象（インターフェース・型・エントリポイント）を特定する
2. 機能を独立した単位に切り分ける。「この単位だけをマージしても壊れないか」を基準にする
3. 単位ごとの行数を見積もる
4. 単位間の依存関係を整理し、順序を決める

**依存の向きが循環する場合、その切り分けは間違っている。** 切り分け直す。

### Step 3: 計画の提示と承認

分割計画を次の形でユーザーに提示し、**承認を得てから Step 4 に進む**。

| # | ブランチ名 | ベース | 内容 | 主な変更ファイル | 見積行数 |
|---|---|---|---|---|---|
| 1 | `feature/xxx-skeleton` | `main` | 骨組み: 〜のインターフェースと最小実装 | ... | 約 150 |
| 2 | `feature/xxx-<機能A>` | `feature/xxx-skeleton` | 機能 A の実装とテスト | ... | 約 180 |

ブランチ名は `.claude/CLAUDE.md`「ブランチ戦略」に従う（`feature/<説明>` / `fix/<説明>` / `hotfix/<説明>`）。

提示の直前に敵対的レビューを 1 パス行う（`.claude/rules/adversarial-review.md` の実施タイミング 5）。特に次を疑う。

- この切り分けで、単独マージすると壊れる PR はないか
- スケルトン PR に「後から変えにくい決定」が漏れていないか（漏れていると後続で大きな手戻りになる）
- 300 行を超える単位が残っていないか

### Step 4: 取り込み元を固定する

Step 1 で状態 A（未コミット）と判定した場合、**先に変更を git のオブジェクトとして退避する**。退避しない限り分割は始められない。

```sh
git stash push -u -m "split-pr: 分割前の全変更"
git stash list                      # stash@{0} が取り込み元になる
```

`-u` は未追跡ファイルも含めるためのもので、新規追加ファイルを落とさないために必須。以降は `git checkout stash@{0} -- <パス>` でファイル単位に取り出す。

**ただし新規追加ファイル（退避時に未追跡だったもの）は `stash@{0}` からは取り出せない。** stash は未追跡ファイルを別のコミット（第 3 親）に格納するため、次のように参照先を変える。

```sh
git show --stat stash@{0}^3            # 未追跡として退避されたファイルの一覧
git checkout stash@{0}^3 -- <新規ファイルのパス>
```

どのファイルがどちらにあるかは Step 1 の `git status` で判別できる（`??` が未追跡）。Step 1 の時点で追跡済みと未追跡を分けて記録しておく。

参照先を間違えた場合は `error: pathspec '<パス>' did not match any file(s) known to git` で停止する（2026-08-19 に実測）。**このエラーは「そのファイルが存在しない」ではなく「参照先が違う」を意味する**ので、パスを疑う前に `^3` を試す。なお `git checkout` は複数パスのうち 1 つでも一致しないとコマンド全体が失敗し、何も取り出さない。取り出せたつもりで先へ進む事故は起きない。

> 一時ブランチにコミットして退避する方法もあるが、【要指示】コミットにあたるためユーザーの指示が要る。stash は履歴を作らないため、指示がない段階ではこちらを使う。

状態 B（コミット済み）の場合は退避不要で、そのブランチ名がそのまま取り込み元になる。

**取り込み元を固定したら、その名前（`stash@{0}` またはブランチ名）を報告に明記する。** 以降のすべての取り出しがこの 1 点を参照する。

### Step 5: PR を 1 本ずつ作る（作成 → 再編 → コミットの繰り返し）

**作業ツリーは 1 つしかないため、PR をまとめて作ることはできない。** 鎖の 2 本目は 1 本目のブランチをベースにするので、1 本目をコミットするまで 2 本目の内容を作れない。したがって次のサイクルを、計画した PR の本数だけ繰り返す。

```sh
# (1) ベースからブランチを切る。1 本目のベースは main、2 本目のベースは 1 本目のブランチ
git switch -c <このPRのブランチ> <ベースのブランチ>

# (2) 取り込み元からこの PR の分だけ取り出す
git checkout <取り込み元> -- <この PR に含めるパス...>

# (3) 行数が見積もりの範囲に収まっているか確認する
git diff --cached --stat
```

(3) の時点で 300 行を超えていたら、**コミットせずに Step 2 の切り分けに戻る**。ユーザーに再分割を提案する。

```sh
# (4) 【要指示】コミット。ユーザーの指示を得てから実行する
git commit -m "<type>[scope]: <説明>"
```

- コミットしてよいかは **PR ごとに確認する**。1 本目への承認を 2 本目に流用しない（`.claude/rules/prohibition-levels.md`「指示は操作単位で必要とする」）
- コミットメッセージは Conventional Commits に従う（`.claude/CLAUDE.md`「コミットメッセージ規約」）
- コミット前に機密情報チェックを行う（`.claude/rules/git-safety.md`）

(4) が終わったら (1) に戻り、いま作ったブランチをベースにして次の PR を作る。

全 PR を作り終えたら、取り込み元が stash の場合はまだ残っているので、**破棄するかどうかをユーザーに確認する**（`git stash drop` は不可逆。`.claude/rules/safe-file-ops.md`）。分割結果に取りこぼしがないことを確認するまでは残す。

```sh
git diff <最後のPRのブランチ> stash@{0}    # 差が空なら取りこぼしなし
```

### Step 6: push と PR 作成のコマンドを提示する

【絶対禁止】ここから先は Claude Code が実行しない。次の形でコマンドと PR 本文を提示し、ユーザーの実行を依頼する。

```sh
# 1 本目（スケルトン）
git push -u origin feature/xxx-skeleton
gh pr create --draft --base main --head feature/xxx-skeleton \
  --title "<タイトル>" --body-file <本文ファイル>

# 2 本目（1 本目をベースにする）
git push -u origin feature/xxx-<機能A>
gh pr create --draft --base feature/xxx-skeleton --head feature/xxx-<機能A> \
  --title "<タイトル>" --body-file <本文ファイル>
```

- **すべて Draft で作る**。鎖の全部が揃ってから Ready for review に変える（先頭だけ先にレビューが始まると、後続の設計が見えないまま議論が進む）
- PR 本文には、鎖の中での位置（「PR 2/4。ベースは #123」）と、その PR で**やらないこと**を明記する
- リポジトリに `.github/pull_request_template.md` がある場合はその項目を埋める

---

## 完了条件

- 取り込み元（`stash@{0}` またはブランチ名）を報告に明記した
- 各 PR の変更行数が 300 行以下に収まっている
- 先頭がスケルトン PR で、後から変えにくい決定がそこに含まれている
- 各 PR に、その PR の機能を検証するテストが同梱されている
- 各 PR が単独でレビューでき、依存の向きが循環していない
- コミットの指示を PR ごとに個別に得た（1 本目の承認を流用していない）
- `git diff <最後のPRのブランチ> <取り込み元>` が空で、取りこぼしがない
- 取り込み元が stash の場合、破棄の可否をユーザーに確認した
- push・PR 作成のコマンドを提示し、Claude Code 自身は実行していない
- 敵対的レビューの実施結果（潰した項目の件数）を報告に 1 行添えている

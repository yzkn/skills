# /long-run スキル — セッションリミット耐性のある自走ジョブ

長時間・時間計測を要する処理を、Claude Code のセッション（5時間枠）から切り離して OS 側で実行する。Claude が直接コマンドを実行して待つのではなく、**detach したジョブ**として起動して状態をファイルに記録する。セッションが切れても処理は継続し、解除後に確認スクリプトを実行するだけで再合流できる。

## いつ使うか

- ビルド・大量データ処理・データ移行・ベンチマーク・E2E テスト等、5 時間を超えうる処理
- 途中中断の影響が大きい処理、正確な経過時間を計測したい処理

Claude Code 組み込みの非同期手段（Bash の `run_in_background`・`ScheduleWakeup`・`/loop` 等）はいずれもセッションに紐づくため、リミットで停止する。本スキルは OS 所有のプロセスとして走らせるため、セッション終了の影響を受けない。これは**ジョブ本体の実行**にこれらを使うなという意味であり、手順 2 では cron を**再開のトリガー**としてのみ使う（トリガーが失われても、ジョブ本体と成果物は残る）。

## 仕組み

`.claude/scripts/long-run.ps1`（Windows）/ `.claude/scripts/long-run.sh`（Linux/macOS）が、ジョブごとに自己完結ディレクトリ `.jobs/<timestamp>_<名前>/` を生成する。

| ファイル | 役割 |
|---|---|
| command.txt | 実行するコマンド（唯一の正） |
| run.ps1 / run.sh | ジョブを detach 起動（親から切り離し・ログ/マーカー初期化） |
| _worker.ps1 / _worker.sh | detach されたワーカー本体。完了時に exit.code を書く |
| check.ps1 / check.sh | 状態確認（副作用なし・冪等・別セッションでも可） |
| README.md | このジョブの手順書 |
| resume-intent.md | 完了後にやること。**会話履歴を持たない新しいセッション**が再開時に読む |
| status.json / *.log / exit.code | 実行時に生成される状態・ログ・完了マーカー |
| collected | 回収済みマーカー。結果をユーザーへ報告し終えたら `claim` で作る |

完了判定は「プロセス生存」＋「exit.code マーカー」の二段で、セッションをまたいでも状態が一意に確定する（プロセス消滅かつ exit.code なし = 中断/異常終了、と区別できる）。

## 実行手順（Claude Code 向け）

### 1. ジョブを生成・起動する

Windows:
```
powershell -NoProfile -ExecutionPolicy Bypass -File .claude/scripts/long-run.ps1 create -Name <名前> -Command "<コマンド>" -Intent "<完了後にやること>" -Start
```
Linux/macOS:
```
bash .claude/scripts/long-run.sh create --name <名前> --command "<コマンド>" --intent "<完了後にやること>" --start
```
`-Start` / `--start` を省くと生成のみ（起動コマンドを表示）。起動は detach されるため Bash ツールは即座に返る。

**【必須】起動・完了待ち・結果の取り出しを 1 回の Bash 呼び出しに束ね、`run_in_background: true` で回す。** 承認ダイアログは Claude Code がコマンドを実行するたびに出るため、状態確認を別呼び出しで繰り返すと**そのたびにユーザーの操作で処理が止まる**。長時間ジョブは「投げたら人手を介さず終わる」状態にする。

```
powershell -NoProfile -ExecutionPolicy Bypass -File .claude/scripts/long-run.ps1 create -Name <名前> -Command "<コマンド>" -Start \
  && J=$(ls -dt .jobs/*<名前> | head -n 1) \
  && for i in $(seq 1 <上限>); do [ -f "$J/exit.code" ] && break; sleep 20; done \
  && cat "<成果物のパス>"
```

- 完了時に通知が届く。**この待機はセッションと共に消えるがジョブ本体は残る**（下記「4. セッションが切れたときの再合流」）
- **ジョブが `claude -p` 等の子セッションを起動する場合、子は headless で承認プロンプトを出せない。** 必要な allow パターンを**起動前に** `.claude/settings.json` へ入れておく（【要指示】）。無いとツール実行が拒否され、結果が歪む
- 【重要】**これは Claude Code から叩く回数を減らす工夫であり、ジョブ内コマンドの安全性判断を省くものではない**（下記「遵守事項」は変わらない）

### 2. 自動再開を仕掛ける

セッションリミット（429）で待機が切れても、ユーザーが「続けてください」と打たずに再開できるようにする。**独立した 2 系統を併用する**（片方が動かなくても他方が拾う）。

本節が担うのは「**ジョブの完了に気づいて結果を回収する**」ことである。「**リミットの解除に気づいて中断した作業を再開する**」のは別機構の `/auto-resume`（SessionStart フックが常駐ウォッチャーを起動し、429 検出時に解除時刻を掴んで待つ）であり、こちらは長時間ジョブの有無に関わらず常に働く。両者は独立しているので、以下の手順はそのまま実施する。

**(a) Claude Code を起動したまま待機する場合 — cron**

ジョブを起動したのと同じターンで `CronCreate` を登録する。

- `cron`: **1 時間周期**（例: `"37 * * * *"`。分マークは `:00` を避ける）、`recurring: true`
- `prompt`: 「`long-run.ps1 list` で <ジョブ名> を確認し、`★未回収` なら成果物を集計してユーザーへ報告する。未完了なら何もせず終了する」

リミット中の発火は 429 で失敗するだけで、**解除後の最初の発火で実際に再開する**。

- **`recurring: false`（ワンショット）にしない。** リミット中に発火すると失われる
- **周期を短くしない。** 理由は 2 つある。①429 で失敗したプロンプトは `last-prompt`（1 件だけ保存される領域）に入るため、発火のたびにユーザーが元々出していた指示が上書きされる ②**cron はリミット中かどうかを判別せず周期どおり発火する**ため、正常に待機しているだけの時間にも会話ターンを起動してトークンを消費する（実測: 25 分のジョブで 15 分周期は 9 回発火、1 時間周期は 1 回。ADR-042）
- 報告後の `claim` を忘れなければ、周期が長くても取りこぼさない。急ぐときはユーザーが声をかければ即座に再開できる
- 登録は**セッション内メモリのみ**（`durable` は無効）。Claude Code を終了すると消え、7 日で失効する
- 報告が済んだら `CronDelete` で削除する

**(b) 閉じて開き直す場合 — SessionStart フック**

`.claude/hooks/job-resume-check.ps1` が `settings.json` に登録済みで、**こちらは何も仕掛けなくてよい**。完了済み（`exit.code` あり）かつ未報告（`collected` なし）のジョブがある場合だけ、セッション開始時に再開を促す。`startup` / `resume`（`--continue` を含む）のいずれでも発火する。

そのため **`-Intent` / `--intent` は必ず渡す**。会話履歴を持たない新しいセッションで開き直したとき、`resume-intent.md` だけが「何のためのジョブか」を伝える。

### 3. ユーザーへ伝える

生成されたジョブディレクトリのパスと確認コマンド（check.ps1 / check.sh）を伝える。リミットに当たっても、解除後に check スクリプトを実行すれば状態を確認できる旨を案内する。

### 4. 状態を確認する

```
powershell -NoProfile -ExecutionPolicy Bypass -File .jobs/<id>/check.ps1
bash .jobs/<id>/check.sh
```
一覧: `long-run.ps1 list` / `bash long-run.sh list`

### 5. セッションが切れたときの再合流

**セッションが切れてもジョブは走り続ける。失われるのは「待つ側」だけである。**

- 【重要】**Bash ツールの `run_in_background` による待機はセッションと共に消える。** 完了通知も届かなくなるが、ジョブ本体・`status.json`・ログ・`exit.code` は残る。**待機が消えたことをジョブの失敗と混同しない**
- 通常は手順 2 の自動再開（cron または SessionStart フック）が拾う。手動で再合流する場合は **`long-run.ps1 list`（完了済みかつ未報告のジョブに `★未回収` が付く）→ 対象の `check.ps1`** の順。**ユーザーが長時間処理に言及したら、まず `list` を実行して未回収のジョブがないか確かめる**
- `run.ps1` には二重起動ガードがあり、実行中のジョブに対して再実行しても何もしない。再合流時に誤って重複起動する心配はない
- **成果物はジョブディレクトリの外（スクリプトが書く出力先）に残る**ため、セッションをまたいでも読み直せる

### 6. 報告したら回収済みにする

**ユーザーへ結果を報告した後に**実行する。これをしないと、セッション開始のたびに同じ再開通知が繰り返される。

```
powershell -NoProfile -ExecutionPolicy Bypass -File .claude/scripts/long-run.ps1 claim -Id <ジョブID>
bash .claude/scripts/long-run.sh claim --id <ジョブID>
```

- **報告より先に実行しない**（報告し忘れたまま通知だけが消える）
- 未完了のジョブ（`exit.code` がないもの）は保護され、スキップされる
- `-All` / `--all` で完了済みの全ジョブを一括回収できる（導入時の移行措置用）

## 遵守事項

- **command.txt に入れるコマンドは実行前にユーザーへ提示する**。破壊的操作・本番接続・外部送信を含む場合は、CLAUDE.md および `.claude/rules/`（環境安全・外部送信抑制・security-hardstops 等）の該当規約に従って確認・承認を得る
- 【必須】**ジョブ用にスクリプトを新規作成したら、起動前に `python .claude/scripts/check-encoding.py <スクリプト>` を通す**（ERROR 0 件であること）。日本語を含む `.ps1` を BOM 無しで書くと PowerShell 5.1 が cp932 として読んで構文エラーになり、**ジョブは起動した直後に失敗する**（detach しているため、失敗に気づくのは待機が終わってからになる。実測は ADR-050）。**短時間で終わる形（`--dry-run` 等）で一度通してから本番のジョブを起動する**
- **長時間ジョブ化は禁止事項の回避手段にならない**。ジョブの detach 起動自体は許可された操作だが、中で実行するコマンドの安全性はコマンド単位で判断する（【絶対禁止】操作をジョブ経由で実行してはならない）
- `.jobs/` 配下は端末ローカルの実行時状態（`.gitignore` 済み・証跡ではない）。確認が済んだら削除してよい

## 制約

- Windows 版は `powershell.exe`、bash 版は `nohup` を使用する（`file-lock` と同様、常駐は OS 依存）
- PC のシャットダウン・スリープ・強制ログオフではジョブも停止する（OS 起動中のみ自走）
- **ワーカーは Windows の Job Object に属する**（2026-09-01 実測）。個々の Bash 呼び出しの終了では死なないこと（22 分継続）と、起動元プロセスが消えても継続することは確認済み。**Claude Code のプロセス自体が終了した場合の生存は未検証**。ただし停止した場合も「中断/異常終了（プロセスが存在せず完了マーカーもありません）」と判別されるため、完了と誤認することはない（実測で確認）
- 途中経過は stdout.log / stderr.log に追記される
- Windows のジョブディレクトリを bash から、または bash のジョブを Windows から確認することは想定しない（生成した OS 側の check スクリプトを使う）
- **自動再開の 2 系統にはそれぞれ限界がある**（だから併用する）: cron は Claude Code を終了すると消える（セッション内メモリ・7 日失効）。SessionStart フックは**ユーザーが Claude Code を開くまで動かない**（なくせるのは「続けてください」という指示であり、開く操作そのものは残る）
- **429 中に発火した cron 回がジョブ登録を壊すかは未検証**（429 を人為的に再現できないため実測不能）。`recurring: true` なら次回発火で回復するため実害は小さいと判断している。cron の発火・複数回の継続・one-shot の自動削除・ジッター、および SessionStart フックの `startup` / `resume` 双方での発火とコンテキスト注入は実測済み

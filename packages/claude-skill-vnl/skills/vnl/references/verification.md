## 未検証・限界（SKILL.md にも要点を残している）

- **`checkdigit --kind jpcorp` / `mynumber`**: 公表されている算出式に基づく実装だが、**公的機関が示す既知サンプルとの突き合わせは未実施**。生成→検証の往復整合（200 件 × 3 方式）のみ確認済み
- **`color cvd` の ΔE 閾値**（critical 10 / warning 25）: 経験的な目安で**規格値ではない**。色覚多様性の再現行列は Viénot・Brettel らの手法に基づく近似で、医学的診断には使えない
- **`cron`**: DST のある地域を `--tz` に指定した場合の切り替え時刻の扱いは検証していない（UTC / Asia/Tokyo は DST がないため影響しない）
- **`clock`**: 祝日データを同梱しないため、`--holidays` を渡さなければ祝日は営業日として数えられる
- **トリガー精度**: 実測済み（2026-08-31・40 ケース × 3 回）。**合格 27/40・発動すべき 7/20・発動すべきでない 20/20**（`report/skill-eval/20260831_192155_vnl.*`）。**誤発動はゼロだが、発動しない場面が多い**。下記「トリガー精度の実測」を参照

## フェーズ 3（`qr`）で判明した OpenCV の癖（実測）

`cv2.QRCodeEncoder_Params.version` は **QR 規格のバージョンと 1 ずれる**。`params.version = N` で規格 version N+1 の symbol が出る。実測（OpenCV 4.13.0）:

| `params.version` | 結果 |
|---|---|
| 0（既定） | 自動。ただし最小は 25x25（**規格 version 1 = 21x21 は生成できない**） |
| 1〜39 | 固定。内容が入らなければ `cv2.error` |
| 40 | 181x181（規格 version 41 相当）で **QR 規格の上限 177x177 を超える** |
| 41 以上 | **戻ってこない**（20 秒でタイムアウトを確認） |

このため `qr encode --version` は**規格のバージョン 2〜40 で受け取り、範囲を検査してから -1 して渡す**実装にした。生成後にモジュール数が 177 を超えていないかも防御的に検査する。

**往復整合の検査（`roundtrip_ok`）では捕まらない不具合がある。** 開発中、`--in-file` で読んだ内容の末尾に Windows の CRLF の `\r` が残っていたが、QR は `\r` を忠実に符号化するため往復は一致し、検査は通っていた。生成物を**別経路（画像ファイル経由の `qr decode`）**で読んで入力と突き合わせるテストで検出した。

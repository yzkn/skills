# /systematic-debugging スキル — 根本原因を確定させてから直す

**引数:** `$ARGUMENTS`（`<症状・エラーメッセージ・失敗しているテスト名>`）

**中核原則: 修正に着手する前に必ず根本原因を突き止める。症状だけを消す修正は失敗である。**

> 出典: [obra/superpowers](https://github.com/obra/superpowers) の `systematic-debugging` スキル（MIT License、`LICENSE` 参照）。SKILL.md を日本語化し、本リポジトリの規約・関連エージェントへの接続を追加した。`references/` の 3 文書と `scripts/find-polluter.sh` は**原典無改変**（英語のまま）。
>
> 同リポジトリの `verification-before-completion` は既に `.claude/rules/code-quality.md`「完了の証拠主義」として取り込み済み（`doc/adr/20260724_009_superpowers由来の完了の証拠主義の採用.md`）。本スキルはその前段にあたる。

## 鉄則

```
根本原因の調査を終えるまで、修正を提案してはならない
```

フェーズ 1 が完了していない状態で修正案を出さない。

## 適用範囲

あらゆる技術的問題に使う（テスト失敗・本番のバグ・想定外の挙動・性能問題・ビルド失敗・連携の不具合）。

**特に使うべき状況:**

- 時間的プレッシャーがある（緊急時ほど当て推量が魅力的に見える）
- 「1 か所直せば済む」と思えている
- すでに複数回修正を試している
- 前回の修正が効かなかった
- 症状を完全に理解できていない

**省略してよい理由にならないもの:** 単純に見える（単純なバグにも根本原因がある）／急いでいる（当て推量の方が遅い）／今すぐ直せと言われている。

## 4 つのフェーズ

各フェーズを終えてから次に進む。

### フェーズ 1: 根本原因の調査

1. **エラーメッセージを最後まで読む** — 警告を飛ばさない。スタックトレースを全部読む。行番号・パス・エラーコードを記録する。答えがそこに書いてあることが多い
2. **再現させる** — 確実に起こせるか。手順は何か。毎回起きるか。**再現できない場合は当て推量に進まず、データを増やす**
3. **直近の変更を確認する** — `git diff`・直近のコミット・依存の追加・設定変更・環境差分
4. **多コンポーネント系では境界ごとに証跡を取る** — CI → ビルド → 署名、API → サービス → DB のように層がある場合、**修正案を出す前に**各境界で「入ってきた値」「出ていった値」「環境変数・設定の伝播」「各層の状態」をログに出し、1 回動かして**どこで壊れているか**を確定させる。層を特定してから、その層だけを調べる
5. **データの流れを遡る** — 悪い値はどこで生まれたか、それを渡したのは誰か。発生源まで遡り、**発生源で直す**（症状の場所で直さない）。詳細な手順は `references/root-cause-tracing.md`

### フェーズ 2: パターン分析

1. **動いている例を探す** — 同じリポジトリ内の類似する正常動作コードを見つける
2. **参照実装を最後まで読む** — 流し読みしない。パターンを部分的に理解したまま適用しない
3. **差分を列挙する** — 動く側と壊れている側の違いを、些細に見えるものも含めて全部書き出す。「これは関係ないはず」と決めない
4. **依存関係を把握する** — 必要な他コンポーネント・設定・環境・前提

### フェーズ 3: 仮説と検証

1. **仮説を 1 つだけ立てる** — 「Y という理由で X が根本原因だと考える」と具体的に書く
2. **最小限で試す** — 仮説を確かめる**最小の変更**を 1 つだけ。同時に複数を直さない
3. **確認してから進む** — 効いたらフェーズ 4。効かなければ**新しい仮説を立て直す**（修正を積み増さない）
4. **分からないときは分からないと言う** — 分かったふりをしない。調査を続けるか、ユーザーに確認する

### フェーズ 4: 実装

1. **失敗するテストを先に作る** — 最小の再現。フレームワークがなければ単発スクリプトでもよい。**修正前に必ず用意する**（`/tdd`）
2. **修正は 1 つだけ入れる** — 特定した根本原因に対する変更のみ。「ついでに」の改善・リファクタリングを混ぜない（`.claude/rules/code-quality.md`「単一目的の変更」）
3. **検証する** — テストが通るか、他が壊れていないか、症状が実際に消えたか。**完了を宣言する前に「完了の証拠主義」に従って証拠を添える**
4. **効かなかったら止まる** — 試した修正の回数を数える。3 回未満ならフェーズ 1 に戻って新情報で再分析する。**3 回以上ならアーキテクチャを疑う（次項）**

### 3 回失敗したらアーキテクチャを疑う

**アーキテクチャの問題を示す兆候:**

- 修正のたびに、別の場所で新しい共有状態・結合・問題が見つかる
- 修正に「大規模なリファクタリング」が必要になる
- 修正が別の場所に新しい症状を生む

このとき問うのは仮説ではなく前提である。「このパターンは本当に妥当か」「惰性で維持しているだけではないか」「症状を直し続けるのではなく構造を変えるべきか」。

**4 回目の修正に進む前に、ユーザーと構造の話をする。** これは仮説の失敗ではなく、設計の誤りである。

## 止まるべきサイン

次のような考えが浮かんだら、フェーズ 1 に戻る。

- 「とりあえず直して、調査は後で」
- 「X を変えて動くか試してみる」
- 「複数まとめて変えてテストする」
- 「テストは省いて手で確認する」
- 「おそらく X なので、それを直す」
- 「完全には理解していないが、これで動くかもしれない」
- 「参照実装は長いので、適当に読み替えて適用する」
- データの流れを追う前に解決策を並べている
- **すでに 2 回以上試した上での「もう 1 回だけ」**
- **修正のたびに別の場所で新しい問題が出ている**

**ユーザー側の合図**: 「それは実際に起きているの？」（検証せずに仮定した）／「それで分かるの？」（証跡を取るべきだった）／「当て推量をやめて」／「もっと根本から考えて」／「詰まってる？」。いずれもフェーズ 1 に戻る合図である。

## よくある言い訳と実際

| 言い訳 | 実際 |
|---|---|
| 「単純な問題だから手順は不要」 | 単純な問題にも根本原因がある。手順は単純な問題なら速く終わる |
| 「緊急だから手順を踏む時間がない」 | 当て推量の反復より系統的調査の方が速い |
| 「まず試して、それから調べる」 | 最初の修正がその後の方針を決める。最初から正しくやる |
| 「修正が効いたらテストを書く」 | テストのない修正は定着しない。先に書けば効いたことを証明できる |
| 「まとめて直せば時間の節約」 | 何が効いたか分離できない。新しいバグを生む |
| 「参照実装は長いので要点だけ」 | 部分的な理解はバグを保証する。最後まで読む |
| 「問題が見えた、直そう」 | 症状が見えたことは根本原因の理解ではない |
| 「もう 1 回だけ試す」（2 回失敗後） | 3 回失敗は構造の問題。修正ではなくパターンを疑う |

## クイックリファレンス

| フェーズ | 主な活動 | 完了条件 |
|---|---|---|
| 1. 根本原因 | エラー精読・再現・変更確認・境界の証跡取得 | **何が**起きて**なぜ**そうなるかを説明できる |
| 2. パターン | 動く例との比較 | 差分を列挙できる |
| 3. 仮説 | 仮説 1 つを最小変更で検証 | 確定した、または次の仮説へ |
| 4. 実装 | 失敗するテスト → 修正 → 検証 | 症状が消え、既存テストが通る |

## 「根本原因が存在しない」と判断する場合

系統的な調査の結果、環境依存・タイミング依存・外部要因だと分かった場合:

1. 手順を完了したと見なしてよい
2. 何を調査したかを記録する
3. 適切な処理を実装する（リトライ・タイムアウト・エラーメッセージ）
4. 将来の調査に備えて監視・ログを追加する

**ただし「根本原因なし」の 95% は調査が不完全なだけである。**

## 関連（本キットでの使い分け）

| 状況 | 使うもの |
|---|---|
| 手順・規律として適用する（人が読む判断基準） | **本スキル** |
| 実際にテストを走らせ、ログを解析して原因箇所を特定させる | `debugger` サブエージェント（結果は `report/debug/` に保存。修正の自動適用はしない） |
| 本番障害が進行中で、影響範囲の切り分けから対応する | `/trouble-shoot`（8 ステップの対話進行） |
| 収束後の事後分析・ポストモーテム・再発防止 | `incident-responder` サブエージェント |
| 性能問題の静的な洗い出し | `perf-analyzer` サブエージェント |

- 「原因が分かった」と考えた時点で**敵対的レビューを 1 パス実施する**（`.claude/rules/adversarial-review.md` の実施タイミング 6）。反例を 1 つ具体化し、耐えなかった仮説は捨てる
- 完了報告には検証の事実（終了コード・テスト結果）を添える（`.claude/rules/code-quality.md`「完了の証拠主義」）
- 根本原因が設計上の判断に起因していた場合は `/record adr` に残す

# 承認の境界（全案件に共通）

案件ごとの例外は `projects/<案件>/project.md` の「承認の境界（この案件の例外）」に書く。食い違うときは、**厳しいほう**に従う。

## 段階（`stage`）で決まる範囲

| 操作 | `propose` 提案だけ | `implement` 実装まで | `merge` マージまで |
|---|---|---|---|
| 調査・読み取り・手元での試行（変更を残さない） | ○ | ○ | ○ |
| 作業ブランチ・作業ツリーでの編集とコミット | × | ○ | ○ |
| 作業ブランチの push、PR / MR の作成（**親のセッションだけ**） | × | ○ | ○ |
| PR / MR のマージ、マージ後の作業ブランチの削除 | × | × | ○ |

- 段階の指定が無い依頼は `propose` として扱う
- 途中で範囲を広げたいときは、利用者に確かめ、タスクファイルの「決定事項」に記録してから `stage` を書き換える
- 指令リポジトリ自身への状態の記録（コミットと push）は、どの段階でも行ってよい

## 常に個別の承認が要る操作（段階に関わらず）

- 本流のブランチへの直接の push、`push --force`、履歴の書き換え
- 削除: リモートのブランチ（マージ済みの自分の作業ブランチを除く）・タグ・リリース・リポジトリ・Issue など
- リリース・デプロイ・パッケージの公開・公開範囲の変更
- システムの設定の変更: タスクの登録、フック、グローバルの設定、ツールの導入
- 依存の追加・更新、ライセンスに関わる変更
- 費用が生じる操作、認証情報の作成・変更
- 他人の PR / Issue へのコメントなど、第三者の目に触れる書き込み
- ほかのエージェントの担当の引き継ぎ（takeover）

## 承認の取り方

1. 計画の時点で、承認が要る操作をタスクファイルの「承認が要る操作」に**すべて書き出す**（作業の最後で初めて止まらないように）
2. 承認待ちの操作は、できるだけ**最後にまとめる**。待つ間は、承認に依存しない部分を進める
3. 承認を得たら、日付と「誰が・何を」を「決定事項」に記録する。承認はその操作だけに有効（次の同種の操作には持ち越さない）
4. サブエージェントには、外部への公開操作・システムの変更をさせない。親が、利用者の承認のあとに行う

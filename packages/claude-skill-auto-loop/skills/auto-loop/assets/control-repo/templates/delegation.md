# 委任の指示書（ひな形）

サブエージェント・別のエージェントに作業を任せるときに、この形で渡す。受け手は会話の文脈を知らないので、これだけで作業できるように書く。

```markdown
# 委任: <名前（タスクファイルの「委任」の表と同じ）>

## 前提
- タスク: <案件>/<タスク ID>（状態ファイル: <指令リポジトリでの場所>）
- 目的: <この委任で達成すること。全体の中での位置づけを 1〜2 文>
- 作業の場所: <作業ツリーの絶対パス>　ブランチ: <ブランチ名>（起点: <本流リモート>/<基準ブランチ>）
- 先に読むもの: <ファイルの絶対パス。渡す側が、存在することを確かめてから書く>

## やること
1. <対象のファイル・範囲を具体的に>
2. ...

## やらないこと（禁止）
- この作業ツリーの外を編集しない。対象の外のファイルを変えない
- push・PR / MR の作成・マージ・タスクの登録・ツールの導入をしない（親が行う）
- 指令リポジトリを書き換えない（親が記録する）
- 判断に迷う点・前提と違う点を見つけたら、進めずに報告に書く

## 検証（終える前に必ず）
- <コマンド・手順。案件の project.md「検証の方法」から>
- 一括の置換は、先に dry run で件数と残りを確かめてから書き込む

## 終え方
- 区切りごとにコミットする（途中で止まっても、次の担当が続けられるように）
- 最後に、次の形で報告する
  - 結論（できた / 一部できた / できなかった）
  - 変えたファイルとコミット
  - 確かめたこと / 確かめられなかったこと
  - 親・利用者の判断が要ること、推測のままの点
```

## 止まった委任の「仕上げ」を任せるとき

上限・再起動・セッションの分岐で止まった委任は、元のエージェントを呼び戻せないことがある。作業ツリーに残った変更を、新しいエージェントに仕上げさせる。前提に次を足す。

```markdown
## 引き継ぎ
- この作業ツリーには、止まった前任の変更が残っている（コミット済み: <git log の範囲> / 未コミット: <git status の要約>）
- 最初に `git status` と `git diff` を読み、元の指示（下に再掲）と照らして、何が済み・何が残っているかを報告の冒頭に書く
- 済んでいる部分をやり直さない。残りだけを仕上げる
```

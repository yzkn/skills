# start — 着手（担当の主張 → 着手前の確認 → 計画）

## 手順

1. **タスクを選ぶ。** ID の指定が無ければ `status.ps1` を実行し、`ready` のうち自分に合うもの（`assignee` が `any`・自分の ID・自分の道具）から、優先度の高い順・古い順に 1 件を選んで利用者に示す
2. **担当を主張する。** push が通るまで、作業を始めない

   ```
   pwsh -NoProfile -File <scripts>/claim.ps1 claim <タスク ID>
   ```

   - 終了コード 2（他のエージェントが担当中・`draft`・`assignee` が合わない）→ そのタスクには手を付けず、別のタスクを選ぶか利用者に伝える
   - 終了コード 1（通信・認証）→ `preflight.ps1` で原因を確かめる
3. **読む。** タスクファイル全体、`projects/<案件>/project.md`（リポジトリ・進め方・検証の方法・落とし穴）、`policy.md`
4. **着手前の確認をする。** [preflight.md](preflight.md) の手順。NG が残るうちは、その NG に関わる作業に入らない
5. **目的と完了条件を固める。** 「目的と完了条件」が空・あいまいなら、原文と照らして書き、利用者に確かめる。確かめられないときは、解釈を「未確認・推測」に書いて進める
6. **計画を書く。** タスクファイルの「計画」に、ステップをチェックボックスで書く
   - PR / MR は、関心ごとごとに小さく分ける。積む順を決める
   - 検証の方法を、ステップごとに決めておく（`project.md` の「検証の方法」）。確かめられないもの（実機・実時間など）は、先に「未確認・推測」に書く
   - 委任するステップ（定型の繰り返しなど）に印を付ける。並列の数は `maxParallel`（既定 3）まで
7. **承認が要る操作を洗い出す。** `stage` の範囲を超える操作と、`policy.md` の「常に個別の承認が要る操作」を、「承認が要る操作」に**すべて**書き出す。承認待ちが最後にまとまるように、計画の順を整える
8. **再開のための情報を書く。** 「現在地」に、作業ブランチ（起点は `<本流リモート>/<基準ブランチ>`。ローカルの基準ブランチは遅れていることがある）、再開時に確かめ直す前提（ローカルのサーバー・認証など）を書く。補助のスクリプトや一時ファイルは `~/.claude/auto-loop/work/<タスク ID>/` に置く
9. **記録して送る。**

   ```
   pwsh -NoProfile -File <scripts>/claim.ps1 heartbeat <タスク ID> -Note '計画を作成'
   ```
10. **利用者に示す。** 計画の要点、承認が要る操作、最初に確かめたいこと。`stage` が `propose` なら調査に、`implement` 以上なら実装に進む

## 段階ごとの進め方

| `stage` | 進め方 |
|---|---|
| `propose` | 調べて、提案を報告の形でまとめる（変更は残さない）。根拠は代表例を実際に読んで確かめ、推測には「推測」と書く。提案を出したら `status: waiting` にして判断を待つ |
| `implement` | 作業ブランチで実装し、検証し、親のセッションが push して PR / MR を作る。マージはしない。URL を「成果物」に書く |
| `merge` | 上に加えて、検査が通った PR / MR を順にマージする。マージのたびに `checkpoint` する |

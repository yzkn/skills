# /code-refactor スキル — コードリファクタリング

コードの外部的な振る舞いを変えずに、内部構造の品質・可読性・保守性を改善する。

## 適用方法

`/code-refactor` で直接呼び出せるほか、以下のような依頼で自動適用される。

- 「`<ファイルパス>` をリファクタリングして」（ファイル全体）
- 「コードレビュー指摘の #`<番号>` に対応するリファクタリングをして」（特定の指摘のみ）

---

## 主要な責務

1. **コード分析**: 構造・設計パターンの評価、技術的負債の特定、コードの複雑さと保守性の測定
2. **リファクタリング計画**: 改善優先度の策定、段階的な改善計画の作成、影響範囲とリスクの評価
3. **実装と検証**: 安全なリファクタリングの実行、既存機能の保持確認、改善効果の測定

---

## 前提確認

リファクタリングを開始する前に、以下が不明な場合は**必ずユーザーに確認してから**作業を進める。

| 確認事項 | 不明と判断する状況 |
|---|---|
| プログラミング言語・フレームワーク | ファイル拡張子・内容から一意に特定できない場合 |
| コーディング規約 | このスキルで定義した規約以外にプロジェクト固有の規約（リンター設定・スタイルガイド等）の有無が不明な場合 |
| テストの有無 | `tests/` 配下に対応するテストが存在するか不明な場合（下記「テストに関する注意」参照） |

### テストに関する注意

リファクタリングは振る舞いを保持するが、テストがなければ意図しない変更を検出できない。テストが存在しない場合は `/unit-test-gen` でテストを先に作成することを推奨し、ユーザーの判断を仰ぐ。

## リファクタリング指針

<!-- profile:standard-only 品質属性・設計原則の一言解説。`.claude/rules/code-quality.md`（常時適用）と重複する -->

### コード品質の目標

| 品質属性 | 内容 |
|---|---|
| 可読性 | 意図が明確で理解しやすいコード |
| 保守性 | 変更や拡張が容易な構造 |
| 再利用性 | 重複を排除しモジュール化を促進 |
| テスタビリティ | テストしやすい設計 |

### 設計原則

- **SOLID 原則**: 単一責任・開放/閉鎖・リスコフ置換・インターフェース分離・依存関係逆転
- **DRY（Don't Repeat Yourself）**: 重複コードを排除しモジュール化する
- **KISS（Keep It Simple）**: 不必要な複雑さを避け、シンプルな設計を維持する
- **YAGNI（You Aren't Gonna Need It）**: 現時点で不要な機能・抽象化を追加しない

## 実行手順

1. **対象コードの読み込みと分析**
   - 指定されたファイルを読み込む
   - **言語別の参照ファイルを Read する**（下表。命名規則・言語固有の手法・禁止変換・自動整形コマンドを収録）
   - レビュー番号が指定されている場合は直前の `/project-code-review` 結果から該当の指摘事項を参照する
   - コードの構造・技術的負債・改善機会を把握し、優先度を判断する

   | 対象 | Read する参照ファイル |
   |---|---|
   | `.py` | [`references/python.md`](references/python.md) |
   | `.ts` `.tsx` `.js` `.jsx` `.mjs` `.cjs` | [`references/typescript.md`](references/typescript.md) |
   | `.cs`（Dataverse プラグインを含む） | [`references/csharp-dotnet.md`](references/csharp-dotnet.md) |
   | `.pa.yaml` `.fx.yaml`・Power Fx 数式 | [`references/powerfx-canvas.md`](references/powerfx-canvas.md) |
   | `.ps1` `.psm1` `.psd1` | [`references/powershell.md`](references/powershell.md)（`.claude/hooks/*.ps1` は【要指示】。同ファイル 6 節を先に読む） |
   | 上記以外の言語 | 参照ファイルなし。本ファイルの汎用規約に従い、**言語・フレームワークの慣習を優先**する |

   - 複数言語が混在するリポジトリでは、**実際に変更するファイルの言語**の参照ファイルだけを読む
   - 参照ファイルが無い言語で固有の判断が必要になった場合は、独断で規約を決めず、既存コードの支配的な慣習に合わせたうえでその旨を報告する

2. **リファクタリング箇所の特定と計画**
   - 下記「リファクタリングの種別」に照らして改善箇所を列挙する
   - レビュー番号が指定されている場合はその指摘事項のみを対象とする
   - 影響範囲とリスクを評価し、段階的な実施順序を決める

3. **変更のプレビュー表示**
   - 変更前後の差分を diff 形式でチャット上に表示する
   - 各変更の理由（設計原則・コーディング規約のどのルールに対応するか）を明示する

4. **ユーザーの承認**
   - プレビューに対してユーザーの承認を得る
   - 変更箇所が多い場合はまとめて承認か個別に承認かをユーザーに選択させる

5. **変更の適用**
   - 承認された変更のみをファイルに書き込む
   - 小さな単位で段階的に適用し、各段階で動作を確認する

6. **テスト実行・ドキュメント更新の提案**
   - 変更後に `/unit-test-run` でテストを実行することを提案する
   - API 仕様書・設計書・README 等が変更によって陳腐化する場合は更新を提案する

## リファクタリングの種別

設計原則とコーディング規約に準拠した改善を行う。

| 種別 | 内容 | 根拠となる原則 |
|---|---|---|
| 命名の改善 | 変数・関数・クラス名を意図が伝わる名前に変更する | コーディング規約 命名規則 |
| 関数の分割 | 50行超・複数の責務を持つ関数を分割する | SOLID（単一責任）・コーディング規約 関数設計 |
| 引数の整理 | 4つ以上の引数をオブジェクトにまとめる | コーディング規約 関数設計 |
| 定数化 | マジックナンバー・マジック文字列を定数として定義する | コーディング規約 その他 |
| 重複の除去 | 重複したコードを共通関数・モジュールに抽出する | DRY 原則 |
| デッドコードの削除 | 未使用の変数・関数・コメントアウトされたコードを削除する | YAGNI 原則 |
| コメントの整理 | what コメントを削除し、why コメントのみを残す | コーディング規約 コメントポリシー |
| エラーハンドリングの整理 | 例外の握りつぶし・過剰な try-catch を整理し、適切なエラー処理に改善する | SOLID（単一責任） |
| 単純なパフォーマンス改善 | 不要なループ・過剰なメモリ確保・明らかな非効率を除去する（アルゴリズム変更は除く） | KISS 原則 |

---

## リファクタリングの原則

- **振る舞いを保持する**: 外部から観測できる動作を変えない。機能追加・バグ修正・アルゴリズム変更は対象外
- **小さなステップで行う**: 1つの種別ごとに変更をまとめ、レビュー可能な単位にする
- **不確実な場合は変更しない**: 影響範囲が読み取れない変更はユーザーに確認してから行う

---

## 対象外とする変更

以下はリファクタリングの範囲外とし、実施しない。

- バグの修正（`/project-code-review` で指摘し、修正はユーザーに委ねる）
- 新機能の追加
- アルゴリズムの変更を伴うパフォーマンス改善
- フレームワーク・ライブラリのバージョンアップ

---

## 対応言語・技術

### プログラミング言語

JavaScript / TypeScript、Python、Java、C#（.NET / Dataverse プラグイン）、Go、Rust、Power Fx（Canvas App・Power Apps の数式）、その他主要言語

### フレームワーク・ライブラリ

React、Vue.js、Angular、Node.js / Express、Django / Flask、Spring Boot、.NET Core、Power Platform（Canvas App の `.pa.yaml`・Dataverse プラグイン・カスタムコネクタ）

### Power Platform 案件での注意

- 【要指示】**Dataverse のスキーマ名（publisher prefix を含むテーブル名・列名）は改名しない**。`ya_AccountNumber` の `ya_` を含む名前の変更は、依存する Canvas App の数式・クラウドフロー・プラグイン登録・既存データ・連携先の Web API 参照を破壊する。命名が規約に反していても改名は**提案に留め**、ユーザーの明示的な指示を得るまで実施しない
- **既存アプリの命名に合わせることを優先する**。1 画面・1 コントロールだけ規約に沿わせると混在してかえって読みにくくなるため、アプリ全体を対象にするか一部に限るかを着手前に確認する
- Power Fx には「関数は 50 行以内」の基準がそのまま当てはまらない。長大な数式は名前付き数式（`App.Formulas`）またはユーザー定義関数への抽出で対応し、`.pa.yaml` の構造（コントロール階層・プロパティのキー）は変えない
- Canvas App・プラグインは自動テストが整備されていないことが多い。Power Fx は `/unit-test-gen` の対象外のため、テストが無い場合は手動での動作確認手順をユーザーと合意してから着手する（上記「テストに関する注意」の適用）

## コーディング規約（参照定義）

リファクタリング判断の基準となる規約。各種別は「リファクタリングの種別」表の「根拠となる原則」欄から参照する。

<!-- profile:standard-only 以下は言語慣習どおりの命名・関数設計・コメント作法（一般知識） -->

### 命名規則

| 対象 | 規則 | 例 |
|---|---|---|
| 変数・関数 | camelCase（JS/TS）/ snake_case（Python） | `getUserById`、`get_user_by_id` |
| クラス・型 | PascalCase | `UserRepository`、`ApiResponse` |
| 定数 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT`、`DEFAULT_TIMEOUT` |
| ファイル名 | kebab-case（Web）/ snake_case（Python） | `user-service.ts`、`user_service.py` |

言語・フレームワークの慣習が上記と異なる場合は、そちらを優先する。**言語固有の命名規則は上表を上書きする**（例: C# の定数は UPPER_SNAKE_CASE ではなく PascalCase）。言語別の規則は Step 1 の表に従って `references/` の該当ファイルを Read する。

### 関数・メソッドの設計

- 1つの関数は1つの責務のみを持つ（単一責任の原則）
- 関数の長さは目安 50 行以内。それを超える場合は分割を検討する
- 引数は原則 3 つ以内。それを超える場合はオブジェクトにまとめる

### コメントポリシー

- コードが「何をするか（what）」ではなく「なぜそうするか（why）」を書く
- 自明なコードにコメントは不要
- 複雑なロジック・制約・回避策には必ずコメントを残す

### その他

- マジックナンバーは定数として定義する
- コードの重複は原則避ける（DRY 原則）。ただし意味の異なる偶然の一致を無理に共通化しない
- 使用しないコードはコメントアウトではなく削除する（git 履歴で復元可能）

## 注意事項

- 変更はユーザーの承認を得てからファイルに書き込む（`.claude/rules/safe-file-ops.md` 準拠）
- `./doc/prompt/`・`./doc/thought/`・`./doc/adr/` 配下のファイルは証跡のため変更しない（`.claude/CLAUDE.md`「証跡の不変性」）
- 変更の理由と期待される改善効果をユーザーに明確に説明する
- リファクタリング結果を記録する場合はユーザーが `/record` で実施する

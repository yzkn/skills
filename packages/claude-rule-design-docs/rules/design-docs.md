# 設計書の正本管理・表記規則（パス条件付き適用）

## 正本と派生物の定義（Single Source of Truth）

- **`design/` 配下の Markdown が唯一の正本**である。Word / Excel / PowerPoint / HTML の納品物は office スキル・slides-maker 等で正本から生成する**派生物**とする
- 派生物は `dist/` 配下に出力する。`dist/` は git にコミットしない（`.gitignore` で除外）
- 【絶対禁止】**派生物を直接編集しない**。修正が必要な場合は正本の Markdown を修正してから再生成する（直接編集すると次回生成で修正が消失し、正本とのドリフトが発生する）
- 顧客から受領した Office ファイルは派生物ではなく**入力資料**であり、`intake/` 配下に保管して参照する（編集しない）。テキスト化は source-extract スキルで行う
- 正本と派生物の内容が食い違っている場合は正本を信頼し、派生物を再生成する。正本側が古いと判明した場合はユーザーに報告して更新方針を確認する

## 未確定情報の表記規約

- **未確定・想定中・顧客確認待ちの値は `==テキスト==` で囲む**（Word 蛍光ペン相当のマーク。派生物生成時にハイライトとして表現する）
  - 例: `処理対象は ==最大 1,000 件/日（顧客確認待ち）== とする`
- 確定したらマークを外し、その設計書末尾の「改訂履歴」表に確定内容と確定日（`YYYY-MM-DD`）を記録する。改訂履歴表がない場合は新設する
- `TBD`・`TODO`・空欄をそのまま放置しない。未確定であること自体が確定している場合は `==〜==` で理由・確認先を添えて明示する
- レビュー（document-review）・フェーズ完了判定の際は、`==〜==` の残存を検索（Grep: `==[^=]+==`）して未確定事項の一覧をユーザーに提示する

## 日付・データ表記

- 日付は ISO 8601（`YYYY-MM-DD`）で統一する
- CSV を扱う場合は BOM 付き UTF-8 で保存し（Excel での文字化け防止）、セル内のリスト値はセミコロン `;` 区切りとする

## Mermaid 図の記述規約

設計書に Mermaid 図（ER 図・業務フロー図・シーケンス図等）を書くときに適用する。図を単体の HTML として作る場合はインライン SVG を使う `/visual-doc` に委ねる。

- **ノード内に `<br/>` を書かない**。多くのレンダラーが HTML タグをそのまま文字として表示する。改行が必要なら ` / ` で区切るか、1 行に収まる長さへ短くする
- **ノードが 4 つ以上、またはラベルが長い場合は `graph TD`（縦方向）を使う**。`graph LR` は長いラベルを横一列に潰して読めなくする
- **図の中で新しい用語を導入しない**。ノードラベルに使う語は、本文または用語表で定義済みのものに限る
- 単純な一方向の手順を、必要もなくフローチャートにしない。番号付きリストで足りる場合はそちらを使う
- 図には図番号とキャプション（何を表す図か）を添え、本文から参照する
- **Markdown 正本の Mermaid コードブロックを画像に置き換えてはならない。** `dist/` の Word・PowerPoint・PDF に図を画像として載せる必要がある場合は、正本の Mermaid を残したまま `/pretty-mermaid` で SVG を書き出し、その SVG を派生物として扱う

> 出典: [mathbullet/skills](https://github.com/mathbullet/skills)（MIT License）の `explain` スキルから Mermaid 記述規約を抜粋して適応。

## フェーズ別フォルダの対応（システム開発案件）

設計書・成果物ドキュメントは `./design/` 配下のフェーズ別フォルダに格納する。

| フォルダ | 対象フェーズ | 格納する代表的な成果物 |
|---|---|---|
| `./design/01_planning/` | 企画 | 企画書、実現可能性検討書 |
| `./design/02_requirements/` | 要件定義 | 要件定義書、ユースケース仕様書 |
| `./design/03_basic_design/` | 基本設計 | 基本設計書、アーキテクチャ図、ER図 |
| `./design/04_detailed_design/` | 詳細設計 | 詳細設計書、API仕様書、画面設計書 |
| `./design/05_implementation/` | 実装 | コーディング規約、開発ガイド |
| `./design/06_testing/` | テスト | テスト計画書、テスト仕様書、テスト結果報告書 |
| `./design/07_migration/` | 移行 | 移行計画書、移行手順書、移行結果報告書 |
| `./design/08_operations/` | 運用 | 運用手順書、監視設計書、障害対応手順書 |

- 成果物ファイルは対応フェーズのフォルダにのみ格納する
- ファイル名は `<連番>_<成果物名>.<拡張子>` の形式を推奨する（例: `01_requirements.md`）
- フォルダ直下の `.gitkeep` は削除しない

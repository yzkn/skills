# /domain-modeling スキル — ユビキタス言語・用語集の構築

プロジェクト固有の用語（ドメイン用語）の定義を確定させ、用語集として維持するスキル。
用語が統一されると、会話・設計書・コード（変数・関数・ファイル名）が同じ言葉で書かれ、Claude Code の冗長な説明が減り、コードベースのナビゲーションも容易になる。

> 出典: [mattpocock/skills](https://github.com/mattpocock/skills)（MIT License）の domain-modeling スキルを本リポジトリ向けに適応。概念は Eric Evans『エリック・エヴァンスのドメイン駆動設計』のユビキタス言語に基づく。

**このスキルの対象はモデルを「変更する」とき**である。語彙合わせのために `design/GLOSSARY.md` を単に読むのはどのスキルでもやってよい 1 行の習慣であり、このスキルの発動条件ではない。

## 用語集ファイル

- 正本: `design/GLOSSARY.md`（Markdown 正本。`.claude/rules/design-docs.md` に従う）
- **遅延作成**: 書くべき用語が最初に確定したときに作成する。空のひな形を先に作らない
- サブシステム・境界付けられたコンテキストが複数あり 1 ファイルで矛盾が出る場合のみ、`design/GLOSSARY.md` を目次（コンテキストマップ）にして `design/GLOSSARY_<コンテキスト名>.md` に分割する

### フォーマット

```markdown
# 用語集（ユビキタス言語）

このプロジェクトで使う用語の正準定義。会話・設計書・コードの命名はこの用語に従う。

## 用語

**注文（Order）**:
顧客が確定した購入の単位。
_避ける同義語_: 購入、取引、オーダー明細（それは注文明細）

**請求書（Invoice）**:
納品後に顧客へ送付する支払い要求。
_避ける同義語_: 請求データ、ビル
```

### 記載ルール

- **断固として 1 つに決める**: 同じ概念に複数の言葉があるときは最良の 1 語を選び、他は `_避ける同義語_` に列挙する
- **定義は 1〜2 文で「それが何であるか」**を書く。何をするか（振る舞い）や実装詳細は書かない
- **プロジェクト固有の概念のみ**: タイムアウト・エラー型などの一般的なプログラミング概念は、多用されていても載せない
- **英語名を併記する**: コードの命名（テーブル・クラス・変数）に使う英語名を用語と対で確定させる（`.claude/rules/code-quality.md` のローマ字禁止と整合）
- 自然なまとまりができたら小見出しでグルーピングする

## セッション中の規律

### 用語集と矛盾したら即指摘する

ユーザーが既存定義と食い違う使い方をしたら、その場で確認する。「用語集では『キャンセル』を X と定義していますが、いまの文脈では Y に見えます。どちらですか？」

### 曖昧語は正準語を提案する

多義的・広すぎる言葉が出たら精密な言葉を提案する。「『アカウント』は顧客（Customer）とユーザー（User）のどちらを指していますか？　両者は別物です」

### 具体的なシナリオで検証する

概念間の関係が議論されたら、境界を突くエッジケースのシナリオを自作してぶつけ、定義の精度を上げる。

### コードと突き合わせる

ユーザーの説明とコードの実態が矛盾していないか確認し、矛盾があれば表に出す。「コードは注文全体をキャンセルしていますが、いま部分キャンセルが可能と仰いました。どちらが正しいですか？」

### その場で用語集を更新する

用語が確定した瞬間に `design/GLOSSARY.md` へ反映する。まとめて後で書かない。

## ADR への接続（控えめに）

**覆すコストが大きい・文脈なしでは不可解・真のトレードオフの結果**——この **3 条件をすべて満たす**ときのみ、`/record adr <タイトル>` での記録を提案する。**1 つでも欠けたら ADR にしない。**

各条件の定義と書式は [`.claude/skills/record/SKILL.md`](../record/SKILL.md)「ADR にするかの判断（粒度）」が正本である。判断に迷うときはそちらを Read する。

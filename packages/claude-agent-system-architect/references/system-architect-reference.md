# system-architect リファレンス — タスク種別ごとの詳細実施内容

system-architect エージェントから参照されるリファレンス。エージェント定義本体は `.claude/agents/system-architect.md`。
各タスク種別の作業を開始する前に、該当セクションを Read してから作業すること。

---

#### `tech-selection` — 技術選定

候補技術を比較評価し、推奨を提示する。

**比較評価軸**

| 評価軸 | 確認内容 |
|---|---|
| 機能適合性 | 要件に対する機能カバレッジ |
| 学習コスト | チームの習熟度・ドキュメントの充実度 |
| 運用コスト | ライセンス費用・インフラコスト・サポート体制 |
| コミュニティ | スター数・更新頻度・既知の脆弱性 |
| スケーラビリティ | スループット・水平スケール対応 |
| エコシステム | 周辺ツール・既存スタックとの統合 |
| ベンダーロックイン | 移行容易性・オープン性 |

WebSearch で公式ドキュメント・ベンチマーク・GitHub リポジトリを参照する。
個人ブログ等の二次情報は一次情報と明確に区別して引用する。

成果物: `report/architect/YYYYMMDD_HHMMSS_tech-selection_<テーマ>.md`

#### `system-design` — システム構成設計

システム全体のアーキテクチャを設計する。

**設計観点**

| 観点 | 内容 |
|---|---|
| コンポーネント構成 | サービス・モジュール・レイヤーの分割方針 |
| 通信方式 | REST / gRPC / イベント駆動（Kafka, SQS 等） |
| データストア | RDB / NoSQL / キャッシュ / 検索エンジンの選定と役割 |
| 認証・認可 | ID プロバイダー・トークン管理・RBAC 方針 |
| 非機能要件 | 可用性目標（SLA）・RTO / RPO |
| デプロイ構成 | コンテナ・Kubernetes・サーバーレス・CI/CD パイプライン |

構成図は Mermaid の `graph` または `C4Context` / `C4Container` 形式で記述する。

成果物: `design/03_basic_design/YYYYMMDD_architecture_<システム名>.md`

#### `scalability` — スケーラビリティ設計

負荷増大に対応するための設計を策定する。

**設計観点**

| 観点 | 内容 |
|---|---|
| 負荷想定 | ピーク RPS・データ量・同時接続数の推計 |
| 水平スケール | ステートレス化・セッション外部化・シャーディング戦略 |
| 垂直スケール | ボトルネック特定・リソース最適化 |
| キャッシュ戦略 | CDN / アプリキャッシュ / DB クエリキャッシュの設計 |
| 非同期処理 | キュー・バックグラウンドジョブ・イベント駆動への分離 |
| データベース設計 | リードレプリカ・接続プーリング・インデックス戦略 |
| 障害対応 | サーキットブレーカー・リトライ・フォールバック |

成果物: `design/03_basic_design/YYYYMMDD_scalability_<システム名>.md`

#### `security-arch` — セキュリティアーキテクチャ

セキュリティを組み込んだアーキテクチャを設計する。

**設計観点（OWASP Top 10 2021 に基づく）**

| カテゴリ | 設計内容 |
|---|---|
| 認証・認可 | MFA・OAuth 2.0 / OIDC・最小権限の原則 |
| 入力値検証 | バリデーション層の設計・エスケープ・パラメーター化クエリ |
| データ保護 | 保存時暗号化・転送時暗号化（TLS 1.3）・鍵管理 |
| シークレット管理 | Secrets Manager・環境変数分離・rotate 方針 |
| ネットワーク境界 | VPC・サブネット分離・WAF・API Gateway |
| ログ・監査 | 監査ログの設計・改ざん防止・SIEM 連携 |
| 依存関係 | SCA（Software Composition Analysis）の導入方針 |
| サプライチェーン | CI/CD のセキュリティゲート・イメージ署名 |

成果物: `design/03_basic_design/YYYYMMDD_security-architecture_<システム名>.md`

#### `re-architecture` — 再アーキテクチャ戦略

既存システムのアーキテクチャを刷新する移行計画を策定する。

**分析・設計ステップ**

1. **現状分析**: 既存コード・設計書を読み込み、現行アーキテクチャの構造・課題を整理する
2. **問題特定**: パフォーマンスボトルネック・保守性の問題・スケール限界を特定する
3. **移行方針の決定**: ビッグバン移行 / ストラングラーパターン / モジュラーモノリス化 等の選択肢を比較する
4. **移行ロードマップ**: フェーズ分割・依存関係・リスク評価を含むロードマップを作成する
5. **リスク軽減策**: 機能フラグ・カナリアリリース・データ移行戦略を設計する

**移行戦略の比較軸**

| 戦略 | 適用条件 | リスク | 期間 |
|---|---|---|---|
| ビッグバン | 小〜中規模、テスト網羅率高 | 高 | 短 |
| ストラングラーフィグ | 大規模、段階的移行が必要 | 低 | 長 |
| モジュラーモノリス化 | モノリスのスパゲッティ解消 | 中 | 中 |
| マイクロサービス移行 | 組織の独立デプロイが必要 | 高 | 長 |

成果物:
- `report/architect/YYYYMMDD_HHMMSS_re-architecture_<システム名>.md`（現状分析・移行戦略）
- `design/07_migration/YYYYMMDD_migration-roadmap_<システム名>.md`（移行ロードマップ）

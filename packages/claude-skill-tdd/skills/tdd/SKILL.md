# /tdd スキル — テスト駆動開発（red-green-refactor）

TDD はレッド（失敗するテスト）→ グリーン（最小実装）のループである。このスキルは、そのループが「残す価値のあるテスト」を生むための基準集でもある。各セクションはループの**毎サイクルで**適用する（終わってから見直すのではない）。

> 出典: [mattpocock/skills](https://github.com/mattpocock/skills)（MIT License）の tdd スキルを本リポジトリ向けに適応。

## 前提（本リポジトリのフェーズ規約）

- 実装フェーズへの移行承認を得ていること（`.claude/project-types/development.md`「実装への移行は必ず明示的に承認を得る」）。TDD はテストから書くが、テストコードも実装フェーズの作業である
- `design/GLOSSARY.md`（用語集）があれば読み、テスト名・インターフェースの語彙をプロジェクトのドメイン用語に合わせる。触る領域の `doc/adr/` の決定に従う

## シーム — テストをどこに書くか

**シーム（seam）**とは、テストの対象となる公開境界のこと。内部に手を突っ込まずに振る舞いを観測できるインターフェースを指す。テストはシームに置き、内部実装に対しては書かない。

**シームは事前合意制**とする。テストを書き始める前に「テスト対象のシーム（公開インターフェース）」を列挙してユーザーに確認する。合意していないシームにはテストを書かない。すべてはテストできない — シームを先に合意することで、テスト工数がクリティカルパスと複雑なロジックに集中する。

確認の聞き方: 「公開インターフェースはどれですか。どのシームをテストしますか？」

## 良いテストとは

テストは**公開インターフェースを通じて振る舞いを検証する**。実装詳細は検証しない。コードが全面的に変わってもテストは変わらないべきである。良いテストは仕様書のように読める — 「ユーザーは有効なカートで購入を確定できる」はどんな能力が存在するかをそのまま伝え、内部構造に依存しないためリファクタリングに耐える。

具体例・アンチパターン（悪いテスト）の詳細は必要時に以下を Read する。

- [references/tests.md](references/tests.md) — 良いテスト・悪いテストの例（実装詳細結合・インターフェース迂回・トートロジー）
- [references/mocking.md](references/mocking.md) — モックの使いどころ（システム境界のみ）とモック可能な設計

## アンチパターン（毎サイクル自己チェック）

- **実装結合** — 内部コラボレーターのモック・プライベートメソッドのテスト・裏口（DB 直接クエリ等）での検証。兆候: 振る舞いが変わっていないのにリファクタリングでテストが壊れる
- **トートロジー** — 期待値をコードと同じ方法で再計算していて、作りからして必ず通るテスト。期待値は独立した情報源（既知のリテラル・手計算の例・仕様書）から取る
- **水平スライス** — テストを全部書いてから実装を全部書く進め方。想像上の振る舞いを一括検証することになり、テストが形骸化する。**垂直スライス**で進める — 1 テスト → 1 実装 → 繰り返し。各テストは前サイクルの学びを反映するトレーサーバレット（tracer bullet）である

## ループの規則

- **レッドが先**: 失敗するテストを先に書き、それを通す最小限のコードだけを書く。将来のテストを先取りした実装・投機的な機能追加はしない（YAGNI）
- **1 サイクル 1 スライス**: 1 シーム・1 テスト・1 最小実装
- **リファクタリングはループの外**: red → green のサイクル内では行わない。グリーンの区切りで `/code-refactor`・`/project-code-review` に接続する

## 実行と報告

- テストの実行と結果報告は `/unit-test-run` の要領に従う（フレームワークの自動検出・サマリー形式）
- サイクルごとに「レッド確認 → 実装 → グリーン確認」の実行結果を省略せず示す。レッドを確認せずに実装へ進まない（テストが最初から通ってしまう場合、そのテストは何も検証していない疑いがある）

## 関連スキルとの棲み分け

| スキル | 担当 |
|---|---|
| **tdd（本スキル）** | テストファーストの実装ループ（新機能・バグ修正） |
| `/unit-test-gen` | 既存コードへのテストの後付け生成 |
| `/unit-test-run` | テストの実行・結果のサマリー報告 |
| `test-strategist` サブエージェント | テスト計画・E2E シナリオなどテスト戦略全体の設計 |

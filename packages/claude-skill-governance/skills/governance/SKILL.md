# Power Platform ガバナンス管理案件スキル

## 本スキルの目的

このスキルは、Power Platform ガバナンス管理案件において実施すべき工程・作業項目・成果物の判断基準を提供する。記載内容を厳守するものではなく、プロジェクト遂行時の迷いを解消するための参照資料である。

---

## 用語定義

| 用語 | 定義 |
|---|---|
| **ガバナンス** | 組織が Power Platform を効果的かつ安全に使用し、ビジネス価値を最大化するためのフレームワーク。ITとビジネスのバランス、セキュリティ・コンプライアンスと効率性のバランスを保ちながら、組織全体の生産性とイノベーションを促進するために用いられる。 |
| **市民開発** | IT部門に依存することなく、ローコード・ノーコードのソリューションを活用して業務部門が自ら業務のデジタル化を実現すること。ITに関する深い知識を持たない現場の担当者でもアプリを開発できる。 |
| **社内コミュニティ** | 組織内の市民開発者だけで構成されたコミュニティ。市民開発者同士で技術的な知識や過去のナレッジを相互に教えあう場。Viva Engage・SharePoint・Teams を段階的に活用する。 |
| **チャンピオン** | 同僚やほかの市民開発者から Power Apps・Power Automate のエキスパートと認識されている市民開発者。CoEスターターキットのダッシュボードや管理センターで見つける。 |
| **CoE（Center of Excellence）** | Power Platform の標準化・ガバナンス・推進を担う組織または仕組み。CoEスターターキットとアプリカタログが主なツール。 |

## ガバナンス管理の事前準備（ゴール設定）

ガバナンス管理を開始する前に、以下の3軸で「ゴール」を明確化する。ゴールが曖昧なまま進むと、自由（野良アプリ増殖）か厳格（IT部門ボトルネック）のどちらかに偏る。

| 軸 | 整理内容 |
|---|---|
| **目的** | Power Platformを利用する目的（アジリティ向上・コスト削減など） |
| **前提条件・制約事項** | 登場人物、ライセンス、内製化の範囲、外注システムとの棲み分け |
| **運用** | 市民開発の運用方針、システム内製化推進方法、ガバナンス設計 |

内製化の範囲の判断軸：開発者スキルとシステム規模のマトリクスで、小規模・低スキルから中規模・中スキルが Power Platform の適用範囲。大規模・高スキルが必要なシステムはスクラッチ開発を検討する。

## 標準作業項目一覧

| 作業項目 | 目的 | 主な成果物 |
|---|---|---|
| 事前調査 | 顧客テナントの導入状況ヒアリング・提案準備 | ヒアリングシート、プロジェクト計画書（内部向け） |
| 提案 | 事前調査結果をもとに案件提案 | 提案書、プロジェクト計画書（顧客向け） |
| 契約締結 | 契約締結・実作業開始 | 契約書 |
| プロジェクト計画 | ゴール・スコープ・コスト・リスクの明確化 | プロジェクト計画書（顧客向け）、WBS |
| Microsoft 365テナント | テナントの利用方針決定・導入支援 | 基本設計書、詳細設計書（パラメーターシート） |
| Power Platform環境 | 環境展開方針・DLPポリシー設計・運用支援 | 基本設計書、詳細設計書、運用手順書 |
| ガイドライン資料整備 | 市民開発者向けガイドライン類の整備 | コーディング標準、デザインシステム、命名規則 |
| 社内コミュニティ | 社内コミュニティの構築・運用支援 | 要件定義書 |
| 教育 | セミナー・ハンズオン・ハッカソンの運営支援 | 教材、受講者用手順書、スケジュール |

> 各作業項目の詳細な内容・成果物定義は `design/21_governance/02_標準作業項目.md` を参照。

## 各作業項目の詳細ガイド

### 事前調査

顧客テナントにおける製品導入・展開状況をヒアリングし、提案準備を行う。ライセンスコストや工数の見積もり精度を高めるため、前提条件・制約事項を詳細に把握する。

**成果物**:
- ヒアリングシート（業種・規模・信用情報、テナント構成、保有ライセンス）
- プロジェクト計画書（内部向け）

**注意**: Web 問合せの場合は顧客組織に関する情報を能動的に収集する。

---

### 提案

**入札参加時の確認ポイント**:
- 入札参加資格（全省庁統一資格、認証取得、免許保有、実務経験・類似案件の実績）を満たしているか
- （電子入札の場合）ICカード・カードリーダーを利用できるか

**成果物**:
- 提案書（見積・WBS）
- プロジェクト計画書（顧客向け）：キックオフミーティングまでに作成
- 職務経歴書・履歴書（提出を求められた場合のみ）

---

### 契約締結

**契約書に明記すべき事項**:

| 項目 | 内容 |
|---|---|
| 作業内容 | 作業の範囲や仕様 |
| 契約類型 | 請負か準委任か |
| 費用 | 委託料 |
| 期間 | 作業期間または納期・スケジュール |
| 役割 | 関係者の役割と責任分界点 |
| 作業端末・環境 | 端末貸出の有無、リモートワークの可否 |
| 納入物 | プログラム・ソースコード・ドキュメント一覧、納入場所、検収条件（期間内に検収されない場合の扱いも明記） |
| 再委託の条件 | 再委託の可否、事前承諾の要否 |
| 瑕疵担保 | 契約不適合責任の期間制限、瑕疵の範囲 |

### プロジェクト計画

最初に行うのは**ガバナンス管理の「ゴール」設定**。ゴールがぶれると後続の判断（ライセンス選択、DLPポリシー設定など）が担当者やタイミングによって変わってしまう。

**注意点**:
- ライセンス・アドオンコストを事前に悲観的に見積もりバッファを持つ
- アーリーアダプター・アンバサダー・チャンピオンの割合を事前に見積もる
- 市民開発とプロ開発の責任分界点を明確にする

**成果物**: プロジェクト計画書（顧客向け）、WBS

---

### Microsoft 365テナント 設計・導入

| 設計項目 | 内容 |
|---|---|
| テナントの数 | シングルテナント or マルチテナント（グループ会社・海外子会社の有無で判断） |
| ライセンスと数量 | Microsoft 365・Power Apps・Power Automateの各プランを何本購入するか |
| 開放順序 | 全員一斉 / サポート部門から順次 / 選抜ユーザーから順次 |
| 社内ポータル | SharePoint で作成 |
| 社内コミュニティ | Viva Engage で作成 |

---

### Power Platform環境 設計・運用

| 設計項目 | 内容 |
|---|---|
| 管理者の任命 | テナント単位・環境単位・システム単位ごとに管理者と責任範囲を定める |
| 登場人物の整理 | 市民開発者とプロ開発者の役割分担（規制とアジリティのバランス） |
| 環境分割の単位 | 開発用・検証用・本番用の3環境を推奨（1システムあたり） |
| 環境構成 | 既定環境の許可操作、野良アプリ防止策（CoEスターターキット活用） |
| データ損失ポリシー | コネクタ利用可否をDLPポリシーで制御 |
| 監査ログ | 監査ログの確認項目・頻度・保持期間・アラート条件を定める |
| CoEスターターキット | 導入可否、カスタマイズ内容を設計 |
| アプリカタログ | 申請手順・承認体制・掲載見直し基準を設計 |

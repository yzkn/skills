# /grill スキル — 徹底質問による計画の精緻化

作業を始める前に、ユーザーと Claude Code の間にある**認識のずれ**を質問によって潰すスキル。
ソフトウェア開発の最大の失敗要因は「作ってから『欲しかったものと違う』と判明すること」であり、その予防に特化する。

> 出典: [mattpocock/skills](https://github.com/mattpocock/skills)（MIT License）の grilling / grill-me / grill-with-docs スキルを本リポジトリ向けに統合・適応。

## 進め方（最重要ルール）

計画・設計のあらゆる側面について、**共通理解に達するまで容赦なく質問する**。設計の決定木を分岐ごとに下り、決定間の依存関係を 1 つずつ解消していく。

- **質問は 1 問ずつ**: 回答を待ってから次の質問に進む。複数の質問を一度に投げると回答者が混乱する（選択肢が明確な質問は AskUserQuestion ツールを使ってよいが、1 回 1 テーマを守る）
- **各質問に推奨回答を添える**: 単に聞くのではなく「私のおすすめは○○です。理由は〜」を必ず付ける
- **コードベースで答えが出る質問はユーザーに聞かない**: Read / Grep / Glob で調べて自分で解消する
- **合意に達するまで計画を実行しない**: ユーザーが「共通理解に達した」と確認するまで、実装・ファイル変更を開始しない（`.claude/project-types/development.md` の「実装への移行は必ず明示的に承認を得る」とも整合）

## 質問で掘るべき観点

| 観点 | 質問の例 |
|---|---|
| 目的・完了条件 | 何ができたら成功か。検証方法は何か |
| スコープ境界 | 何を含み、何を含まないか。今回やらないことは何か |
| 前提・制約 | 環境・期限・既存資産・技術制約は何か |
| エッジケース | ○○が空/重複/同時実行/失敗のときどうなるべきか |
| トレードオフ | A 案と B 案のどちらを優先するか（性能 vs 単純さ等） |
| 用語の定義 | 「○○」はこの文脈で正確には何を指すか |

## ドキュメント反映（用語・決定が固まったとき）

質問の過程で以下が発生したら、その場で対応するスキルに接続する（会話の最後にまとめてやらない）。

- **用語のゆらぎ・新しいドメイン用語が確定した** → `domain-modeling` スキルの規律に従い `design/GLOSSARY.md` を更新する
- **覆しにくい設計判断が確定した** → `/record adr <タイトル>` での記録を提案する（ADR にすべきかの判断基準は domain-modeling スキルを参照）

## 終了と次のアクション

すべての分岐が解消したら、**合意事項のサマリー**（決定・根拠・保留事項）を提示し、ユーザーの確認を得る。その後の展開先:

| 次にやりたいこと | 接続先 |
|---|---|
| 設計書として残す | `design/` 配下へ文書化（`.claude/rules/design-docs.md` に従う） |
| 要件定義書・ユースケースに構造化 | `requirements-analyst` サブエージェント |
| タスク分解・見積もり | `sprint-planner` サブエージェント |
| テストファーストで実装 | `/tdd`（実装フェーズへの移行承認を得てから） |

## 注意

- 質問のための質問はしない。決定木の未解決分岐がなくなったら素直に終了する
- ユーザーが「もう十分」と言ったら、残っている未解決点を列挙した上で終了する（黙って打ち切らない）
- セッションをまたぐ場合は `/record` で合意事項を記録してから中断する

# /design-sync スキル — 議事録・資料からの設計書/WBS 更新

**引数(入力ソースの指定。省略可):** $ARGUMENTS

プロジェクト進行中に発生した新情報を、既存の設計書（`design/`）・WBS（`task/`）に反映する。

## 鉄則

**ユーザー合意前に既存ファイルを変更しない。**
差分を洗い出してユーザーに提示し、明示的な合意を得てから初めて反映する。「黙って小さな修正を入れる」は typo 修正であっても禁止。

## 実行手順

### Step 1: 新規・更新ソースの特定

以下から「前回 sync 以降に追加・更新された情報」を探す。

- `intake/customer/`・`intake/minutes/` の新規ファイル
- ユーザーがチャットで共有した議事メモ・メール・決定事項
- 既存の `intake/extract/extract_*.md` の `抽出日:` と比較して新しいもの

チャットで直接共有されたテキストは `intake/minutes/source_議事メモ_<YYYYMMDD>.md` に保存してから扱う。

### Step 2: 新規情報の抽出

source-extract スキルの手順に従い、`intake/extract/` に転記する（要約せず転記）。

### Step 3: 既存ドキュメントとの差分分析

新情報を既存ドキュメントと突き合わせ、変更が必要な箇所を洗い出す。

| 変更カテゴリ | 主な影響先 |
|---|---|
| 業務ルール・要件の追加/変更 | `design/02_requirements/`（要件定義書・ユースケース） |
| アーキテクチャ・システム構成の確定 | `design/03_basic_design/` |
| 画面・API・テーブルの変更 | `design/04_detailed_design/` |
| スケジュール変更・マイルストーン確定 | `task/`（WBS）— `.claude/rules/wbs-tasks.md` に従う |
| 課題・リスクの新規/解決 | `task/issues.md`（課題管理表） |
| 未確定値の確定 | 該当設計書の `==〜==` マーク解除 + 改訂履歴表へ記録（`.claude/rules/design-docs.md`） |
| 重要な意思決定 | `/record adr` での記録を提案 |

### Step 4: 差分一覧の提示

```markdown
## sync 計画 — <日付>

入力ソース:
- <ファイル/議事メモ>

### 変更案

| # | 種別 | 影響先ファイル | 変更内容 | 根拠 |
|---|---|---|---|---|
| 1 | 追加 | design/02_requirements/01_requirements.md | 機能要件 FR-015 を追加 | 議事録 p.3「YY と決定」 |
| 2 | 修正 | task/wbs.md | タスク 2.3 の終了予定を 7/10 → 7/17 | 議事録 p.5「1 週間後倒し」 |
| 3 | 確定 | design/03_basic_design/01_basic_design.md | `==想定==` マーク解除（ライセンス境界確定） | メール 6/20 |

### 検討事項

- <一次情報だけでは判断できない論点。ユーザーの判断が必要>
```

**各変更には必ず根拠（一次情報への参照: 「議事録 p.3」「extract_定例.md の該当箇所」等）を付ける。** 議事メモが断片的でも推測で具体化せず、「この記述だけでは判断不能」と明示してユーザーに確認する。

#### アクションアイテムの抽出（入力が議事録の場合は必須）

議事録・議事メモを入力とする sync では、設計書への反映と別に**アクションアイテム（AI）を漏れなく抽出**し、差分一覧に含める。

- 「〜する」「〜を確認」「宿題」「持ち帰り」「次回まで」等の表現から、担当・期限を伴うべき作業を拾い出す
- 抽出形式:

```markdown
### アクションアイテム

| # | 内容 | 担当 | 期限 | 反映先の案 |
|---|---|---|---|---|
| A1 | ライセンス数の確定値を営業に確認 | 顧客: 田中様 | 7/20 | task/issues.md（課題として追跡） |
| A2 | ER 図にログテーブルを追加 | 自社 | 次回定例 | task/wbs.md（タスク 3.2 の子タスク） |
```

- **担当・期限が議事録から読み取れない場合は空欄のまま提示**し、推測で埋めない（ユーザー合意時に確定する）
- 反映先は原則 `task/issues.md`（追跡が必要な確認事項）または `task/wbs.md`（スケジュールに載せる作業）。反映は他の変更と同じく Step 5 の合意後に行う

### Step 5: ユーザー合意

変更ごとに 承認 / 修正あり / 却下 / 保留 を確認する。合意できた変更のみ Step 6 で反映し、保留項目は `task/issues.md` に追記して持ち越す。

### Step 6: 反映

- WBS の変更は `.claude/rules/wbs-tasks.md`（ID・依存整合・ステータスと日付の連動）に従う
- `==〜==` マークを外したら、該当設計書の改訂履歴表に確定内容と確定日を記録する
- 設計書を変更したら関連する派生物（`dist/`）の再生成が必要になる旨をユーザーに伝える
- 重要なアーキテクチャ判断・方針変更が含まれる場合は `/record adr` での記録を提案する

### Step 7: 検証と完了報告

- WBS を変更した場合は `.claude/rules/wbs-tasks.md` の「編集後の整合性セルフチェック」を実施する
- 設計書の大きな変更にはレビュー（`/document-review`）を提案する
- 報告内容: 反映したファイル一覧（差分の要点）/ 却下・保留の項目と理由 / 新規に発生した課題・要相談事項

## 完了条件

- [ ] 新規ソースが `intake/extract/` に転記されている
- [ ] 差分一覧がユーザーに提示され、変更ごとに合意が取れている
- [ ] 入力が議事録の場合、アクションアイテムが抽出され反映先（`task/issues.md` / `task/wbs.md`）が合意されている
- [ ] 合意された変更のみが反映されている
- [ ] `==〜==` の確定分が改訂履歴に記録されている
- [ ] WBS 変更時は整合性セルフチェックを通過している

# /deprecation-migration スキル — 廃止と移行の計画

**引数:** `$ARGUMENTS`（`<廃止・移行の対象（システム名・API 名・機能名・テーブル/カラム名）>`）

「作る」より難しいのは「消す」。このスキルは、旧実装を**安全に停止できる状態まで持っていく**手順を扱う。

> 出典: [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills) の `deprecation-and-migration` スキル（MIT License、`LICENSE` 参照）。日本語化し、本リポジトリの成果物置き場・承認ルール・関連スキルへの接続を追加した。

---

## このスキルを使う場面

- 旧システム・旧 API・旧ライブラリを新実装へ置き換える
- 不要になった機能を停止する（サンセット）
- 重複実装を 1 つに統合する
- 誰も保守していないが依存されているコード（ゾンビコード）の処遇を決める
- **DB のカラム名変更・テーブル分割など、データを伴う変更を計画する**
- 新規システムの設計時に「3 年後どう消すか」を決めておく

移行フェーズの成果物は `design/07_migration/` に置く（Markdown が正本。`.claude/rules/design-docs.md`）。WBS への反映は `.claude/rules/wbs-tasks.md` に従う。

## ステップ 1: 廃止するかを決める

次の 5 問に順番に答える。答えを飛ばして計画に入らない。

1. **その実装は今も固有の価値を出しているか** — 出している場合は保守を続ける。出していない場合は次へ
2. **依存している利用者・呼び出し元は何件か** — 移行スコープを件数で出す（「多い」ではなく件数）
3. **代替は存在するか** — 存在しないなら**代替を作るのが先**。代替なしに廃止を宣言しない
4. **利用者 1 件あたりの移行コストはどれくらいか** — 自動化できるなら実施する。手作業で重いなら保守コストと比較する
5. **廃止しない場合の保守コストはいくらか** — セキュリティリスク・要員時間・複雑性が塞いでいる機会

<!-- profile:standard-only 「コードは負債」「Hyrum の法則」は広く知られた一般知識のため、簡潔プロファイルでは逐条確認を省いてよい（適用そのものは必須） -->

### 判断の前提となる 3 つの考え方

- **コードは資産ではなく負債**: 1 行ごとにテスト・ドキュメント・セキュリティパッチ・依存更新・読む人の認知コストが継続的に発生する。価値は「コード」ではなく「機能」の側にある
- **Hyrum の法則が撤去を難しくする**: 利用者が十分に多いと、観測可能な挙動（バグ・タイミング・未文書の副作用まで）すべてが依存される。だから廃止には「宣言」ではなく「能動的な移行」が必要になる
- **廃止計画は設計時に始まる**: 新規構築のときに「どうやって消すか」を決めておくと、インターフェースが薄く、フィーチャーフラグで切り離せる形になる

## ステップ 2: advisory と compulsory を選ぶ

| 区分 | 使う場面 | 手段 |
|---|---|---|
| **advisory（任意移行）** | 旧実装が安定しており、移行を利用者の都合に任せられる | 警告・ドキュメント・告知。期限を切らない |
| **compulsory（強制移行）** | 脆弱性がある・後続の開発を塞いでいる・保守コストが持たない | 撤去期限を切る。**移行ツールと移行手順書の提供が前提** |

**既定は advisory。** compulsory を選ぶ場合、期限の告知だけでは足りない（移行ツール・手順書・問い合わせ窓口をセットで用意する）。

**移行責任の原則**: 廃止する側が基盤の保有者なら、**利用者の移行まで自分の責任範囲**とみなす。もしくは移行不要の後方互換更新を提供する。「宣言して放置」はしない。

## ステップ 3: 移行を実行する

### 3-1. 代替を先に作る

- 旧実装の重要なユースケースをすべて満たしている
- 移行手順書がある
- 本番で実績がある（「理論上は良い」では足りない）

### 3-2. 告知して文書化する

`design/07_migration/` に廃止通知を作る。最低限、次の 5 項目を書く。

| 項目 | 内容 |
|---|---|
| ステータス | 廃止予定（advisory / compulsory）と告知日 |
| 代替 | 移行先の名称と移行手順書へのリンク |
| 撤去予定 | compulsory の場合は日付。advisory なら「未定」と明記 |
| 理由 | なぜ廃止するか（保守コスト・脆弱性・重複） |
| 移行手順 | 実際のコード差分レベルの手順と検証コマンド |

### 3-3. 利用者を 1 件ずつ移行する

一斉切替はしない。1 件ごとに次を回す。

1. 旧実装との接点をすべて洗い出す
2. 代替を使うよう変更する
3. 挙動が一致することを検証する（テスト・結合確認）
4. 旧実装への参照を消す
5. デグレがないことを確認する

### 3-4. 旧実装を撤去する

**全利用者の移行完了後にのみ**実施する。

1. 利用実績がゼロであることを確認する（メトリクス・ログ・依存解析）
2. コードを消す
3. 付随するテスト・ドキュメント・設定も消す
4. 廃止通知そのものを消す（役目を終えている）

## 移行パターン

| パターン | 使う場面 | 要点 |
|---|---|---|
| **Strangler（絞め殺し）** | 稼働中の旧システムを止められない | 新旧を並走させ、トラフィックを 0% → 10%（カナリア）→ 50% → 100% と移す。旧が 0% になってから撤去する |
| **Adapter** | 利用者側を変更させたくない | 旧インターフェースを保ったまま内部を新実装へ委譲するアダプタを置き、裏側から移行する |
| **フィーチャーフラグ** | 切替リスクが高い・利用者ごとに切りたい | フラグで新旧を切り替え、1 件ずつ有効化する。フラグの削除時期も同時に決める（`development-details.md`「フィーチャーフラグ管理」） |

### DB スキーマ変更（expand / contract）

**データはデプロイの巻き戻しでは戻らない**ため、スキーマ変更は移行の中で最もリスクが高い。事故は「スキーマ変更とコード変更を同じリリースに載せる」ことで起きる（ロールアウト中は新旧のコードが同時に動くため、片方が存在しないカラムを参照する）。

**カラムを in-place で変更しない。** 追加のみのフェーズに分割する。

```
EXPAND ──────────────→ MIGRATE ──────────────→ CONTRACT
新カラムを nullable で   既存行をバックフィル、    旧カラムを読む
旧カラムと並べて追加     アプリから新旧へ二重書き   コードが無くなってから
                                                  別リリースで削除
```

`name` を `full_name` に改名する例:

1. **Expand**: `full_name` を nullable で追加してデプロイ（旧コードは無視するので壊れない）
2. **二重書き**: insert/update で `name` と `full_name` の両方に書くようにしてデプロイ
3. **バックフィル**: 既存行を `name → full_name` へバッチでコピーする（テーブル全体をロックしない粒度で）
4. **読み替え**: 参照を `full_name` に切り替え、書き込みは両方のままデプロイして様子を見る
5. **Contract**: `name` への書き込みを止め、**別の後続リリースで**カラムを削除する

**規則**:

- **追加は先、破壊的変更は最後に単独で**。追加（nullable カラム・新テーブル・新インデックス）はどのリリースでも安全。削除・改名は、旧構造を参照するコードが無くなった**後の専用リリース**で行う
- **すべてのマイグレーションに検証済みの down を用意する**。戻せないマイグレーションは戻せないデプロイと同義。マージ前に down を実行して確かめる
- **バックフィルはバッチ・スロットル付きで、ホットパスの外で回す**（数百万行の単発 `UPDATE` はテーブルをロックする）
- **大きなインデックスは書き込みを止めずに作る**（PostgreSQL の `CREATE INDEX CONCURRENTLY` 等）
- 【要指示】**本番 DB に対する破壊的操作（`DROP` / `TRUNCATE` / `DELETE`）は Claude Code から実行しない**。検証はステージングで行う（`.claude/rules/environment-safety.md`）。本番へのデプロイ・適用はユーザーの明示的な承認後にのみ実施する
- スキーマ設計そのものは `data-modeler` サブエージェント、既存スキーマのアンチパターン検出は `/db-review` に渡す

## ゾンビコード

**誰も保有していないが全員が依存しているコード。** 兆候:

- 6 か月以上コミットがないが、現役の利用者がいる
- 担当者・担当チームが決まっていない
- 誰も直さない失敗テストがある
- 既知の脆弱性がある依存を誰も更新していない
- 既に存在しないシステムを参照しているドキュメント

**対処は 2 つしかない**: 保有者を決めて正しく保守するか、具体的な移行計画とともに廃止する。中間状態（放置）を選択肢にしない。

## よくある言い訳と実際

| 言い訳 | 実際 |
|---|---|
| 「動いているのに消す必要があるのか」 | 誰も保守していない動くコードは、セキュリティ負債と複雑性を静かに増やす |
| 「後で必要になるかもしれない」 | 必要になったら作り直せる。「念のため」の保持コストは作り直しより高い |
| 「移行コストが高すぎる」 | 2〜3 年の保守コストと比較する。多くの場合は移行の方が安い |
| 「新システムが完成してから廃止を考える」 | 完成した頃には次の優先事項が来ている。廃止計画は設計時に立てる |
| 「利用者は自分で移行するだろう」 | しない。ツール・手順・動機を提供するか、自分で移行する |
| 「両方を無期限に保守できる」 | 同じ機能の 2 系統は、保守・テスト・ドキュメント・教育のすべてが二重になる |
| 「カラム名を変えるだけ、1 行だ」 | ロールアウト中は新旧のコードが同時に動く。expand/contract 以外の選択肢はない |
| 「追加と削除を同じマイグレーションでやる」 | 安全な追加に破壊的な削除を結合している。削除は専用リリースへ |
| 「ロールバックは必要になったら書く」 | down のないマイグレーションは戻せないデプロイ。マージ前に書いて実行する |

## レッドフラグ

- 代替が無い状態での廃止宣言
- 移行ツール・手順書のない廃止告知
- 何年も advisory のまま進捗がない「ソフト廃止」
- 保有者不在で現役利用者がいるゾンビコード
- 廃止予定の実装への新機能追加
- 現在の利用状況を計測せずに廃止を決めている
- 利用実績ゼロを確認せずにコードを消している
- スキーマ変更と、それに依存するコードが同一リリースに載っている
- カラムを expand/contract を経ずに改名・削除している
- down を検証していないマイグレーション、テーブルをロックするバックフィル

## 完了の検証

`.claude/rules/code-quality.md`「完了の証拠主義」に従い、次を**確認した事実として**報告する（推測で埋めない）。

- [ ] 代替が本番実績を持ち、重要なユースケースを網羅している
- [ ] 移行手順書が具体的な手順・例つきで存在する
- [ ] 全利用者の移行が完了している（メトリクス・ログで確認した）
- [ ] 旧コード・テスト・ドキュメント・設定が撤去されている
- [ ] リポジトリに旧実装への参照が残っていない（検索して確認した）
- [ ] 廃止通知を撤去した

スキーマ変更を伴う場合は追加で:

- [ ] 追加フェーズに分割している（expand → バックフィル → contract）
- [ ] 各デプロイ時点で新旧のコードがどちらもスキーマに対して有効
- [ ] 各マイグレーションに検証済みの down がある。バックフィルはスロットル付きバッチ
- [ ] 破壊的な手順（削除・改名）は、旧構造を参照するコードが無くなった後の専用リリースになっている

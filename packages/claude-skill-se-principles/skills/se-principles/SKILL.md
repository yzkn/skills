# /se-principles スキル — ソフトウェア工学原理原則の適用・検証

ソフトウェア工学の原理原則（SOLID・DRY・KISS・YAGNI・Clean Architecture 等）に基づいて設計を行い、
または実装結果が原則に従っているかを検証する。

## 呼び出し方

```
/se-principles                          # 原則クイックリファレンスを表示
/se-principles check <ファイルパス>      # ファイル・ディレクトリを原則で検証
/se-principles check                    # git diff（未コミット変更）を検証
/se-principles design                   # 設計ガイドセッションを開始
```

引数 `$ARGUMENTS` の先頭ワードでモードを判定する。

---

## check モード — 原則適合検証

### 前提確認

対象言語・フレームワークがファイル内容から判定できない場合はユーザーに確認してから開始する。

### 実行手順

1. **対象コードの読み込み**
   - 引数にパスが指定された場合: Read ツールで該当ファイル / ディレクトリ配下を読み込む
   - 引数なしの場合: `git diff` で未コミット変更を取得する

2. **規模・アーキテクチャの把握**
   - ファイル構成・依存関係からレイヤー構造・採用パターンを推測する
   - 不明な場合は「推測上の前提」として明示してレポートに記載する

3. **原則別チェックの実施**
   下記「チェック観点」に従い各原則への適合を確認する

4. **検証レポートの出力**
   下記「検証レポートフォーマット」で結果を出力する

5. **次のアクションの提案**
   - 設計レベルの問題（依存逆転・レイヤー違反等）→ `/se-principles design` の活用を提案
   - 実装レベルの問題（コード重複・複雑度等）→ `/code-refactor <ファイルパス>` の活用を提案
   - セキュリティ・品質の詳細確認 → `/project-code-review <ファイルパス>` の活用を提案
   - 重要なアーキテクチャ決定が必要な場合 → `/record adr <タイトル>` の活用を提案

## チェック観点

<!-- profile:standard-only 以下 4 表は SOLID・DRY/KISS/YAGNI 等の一般に知られた原則の確認内容。`.claude/rules/code-quality.md`（常時適用）とも重複する -->

### SOLID 原則

| 原則 | 確認内容 |
|---|---|
| S: 単一責任 | 1 クラス・モジュールに複数の変更理由（責任）が混在していないか。ビジネスロジック・永続化・通知等が同居していないか |
| O: 開放閉鎖 | 新しい振る舞いを追加する際に既存コードを修正する必要があるか。型判定の switch/if が増殖する構造でないか |
| L: リスコフ置換 | サブクラスが親の契約（事前条件・事後条件・不変条件）を破っていないか。親の代わりに子を渡して動作が変わらないか |
| I: インターフェース分離 | 実装クラスが使わないメソッドを持つインターフェースを実装させられていないか |
| D: 依存性逆転 | 上位モジュールが下位モジュールの具象クラスに直接依存していないか。抽象（インターフェース）経由になっているか |

### DRY / KISS / YAGNI

| 原則 | 確認内容 |
|---|---|
| DRY | 同じロジック・定数・設定が複数箇所に存在しないか。異形の重複（コピー修正版）がないか |
| KISS | 不要な抽象化・汎用化・間接層が追加されていないか。同じ目的に対してより単純な実装があるか |
| YAGNI | 現時点では不要な機能・汎用化が実装されていないか。将来の拡張のための過剰な設計がないか |

### アーキテクチャ・レイヤー

| 観点 | 確認内容 |
|---|---|
| レイヤー違反 | 依存方向が正しいか（ドメイン層が外部ライブラリに依存していないか） |
| 関心の分離 | 表示・ビジネスロジック・データアクセスが適切に分離されているか |
| 高凝集・低結合 | モジュール内の要素が単一目的に関連しているか。モジュール間の依存は最小か |
| ポート & アダプター | 外部依存が境界でアダプターを介して隔離されているか（テスト可能性の確保） |

### コード品質

| 観点 | 確認内容 |
|---|---|
| Fail Fast | エラーが握りつぶされていないか。サイレントフォールバックがないか |
| 型安全性 | `any` 型・型アサーション乱用がないか。型で不正値を防いでいるか |
| 複雑度 | ネスト深度が 3 階層を超えていないか。関数が 50 行を大きく超えていないか |
| テスト可能性 | 依存が差し替え可能か（DI・インターフェース利用）。純粋関数として切り出せる箇所はないか |

## design モード — 設計ガイドセッション

新規設計または既存設計の見直しをガイドする対話型モード。

### 実行手順

1. **要件・制約の確認**
   以下を確認し、不明な点があればユーザーに質問する（最大 3 問）。

   | 確認事項 | 目的 |
   |---|---|
   | システムの目的と主要ユースケース | 適切なパターン選択の基準 |
   | 想定コード規模 / チーム規模 | アーキテクチャの複雑さを判断 |
   | 主要な技術スタック | 利用可能なパターンを絞り込む |
   | 外部依存（DB・API・メッセージング等） | ポート & アダプターの設計範囲 |
   | 変更頻度が高い箇所（判明していれば） | 開放閉鎖原則の適用優先度 |

2. **規模・複雑さの判定**

   | 判定基準 | 推奨アーキテクチャ |
   |---|---|
   | 小規模・単純な CRUD | シンプルな MVC / レイヤード。SOLID より KISS・YAGNI を優先 |
   | 中規模・ビジネスロジックあり | レイヤードアーキテクチャ + SOLID 全般 |
   | 大規模・複雑ドメイン | クリーンアーキテクチャ / ヘキサゴナル + DDD 戦術パターン |

3. **レイヤー構成の提案**
   - 各レイヤーの責務・依存方向・具体的なファイル配置を提示する
   - 採用するデザインパターンとその理由を明記する

4. **設計上の判断ポイントの提示**
   - 採用した原則と、代替案に比べてのトレードオフを説明する
   - 将来の拡張で変更が必要になるポイントを明示する

5. **ADR 記録の提案**
   重要な設計判断が生じた場合は `/record adr <タイトル>` での記録を提案する

## デフォルトモード — クイックリファレンス表示

引数なしで呼び出した場合は、同ディレクトリの `principles-reference.md` の内容を構造化してチャットに表示する。
ユーザーが特定の原則について詳細を求めた場合は、該当箇所を詳しく説明する。

---

## 注意事項

- 検証レポートはチャット上に出力するのみとし、ファイルへの書き込みはユーザーが `/record` で明示的に記録する
- `./doc/prompt/`・`./doc/thought/`・`./doc/adr/` 配下のファイルは証跡のため変更提案を行わない
- すべての原則を最初から完璧に適用する必要はない。プロジェクトの規模・フェーズに応じた段階的導入を推奨する
- 原則の適用がコストに見合うかを常にトレードオフとして提示し、一律強制はしない

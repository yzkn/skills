# ソフトウェア工学原理原則 — 参照定義

`/se-principles` スキル（`SKILL.md`）から参照される原則定義集。スキル本体ではないため直接呼び出しはできない。
`/se-principles check <パス>` でファイルを原則に照らして検証、`/se-principles design` で設計ガイドセッションを開始できる。

---

## 1. 基本設計原則

### SOLID 原則

| 原則 | 略称 | 定義 | 違反の典型例 |
|---|---|---|---|
| 単一責任原則 | S | クラス・モジュールが変更される理由は 1 つだけであるべき | 1 クラスに DB 操作・ビジネスロジック・メール送信が混在 |
| 開放閉鎖原則 | O | 拡張に対して開き、修正に対して閉じている | 条件分岐で型を判定して処理を分岐する実装が増殖する |
| リスコフ置換原則 | L | 子クラスは親クラスの代わりに無条件で使用可能であるべき | サブクラスが親の事前条件を強化・事後条件を弱化させる |
| インターフェース分離原則 | I | クライアントが使わないメソッドへの依存を強制すべきでない | 巨大な 1 インターフェースに無関係な操作を詰め込む |
| 依存性逆転原則 | D | 上位・下位モジュールとも抽象（インターフェース）に依存すべき | ビジネスロジックが具象の DB 実装クラスに直接依存する |

### DRY（Don't Repeat Yourself）

「同じ知識を 2 箇所以上に書かない」。コードの重複だけでなく、同じロジックのコピー修正版も対象。
定数・共通処理の抽出と設定値の一元管理が重要。異形の重複（処理は同じ・記述が異なる）にも注意する。

### KISS（Keep It Simple, Stupid）

シンプルさを最優先する。「賢い」コードより「読みやすい」コードを選ぶ。
追加の抽象化・汎用化は理解コストと引き換えであることを常に意識する。

### YAGNI（You Aren't Gonna Need It）

「将来必要になるかも」という予測で実装しない。今必要な機能のみを実装し、汎用性より単純性を優先する。
既存パターンの拡張で対応できる場合は新規抽象を導入しない。

### 高凝集・低結合（High Cohesion, Low Coupling）

- **高凝集**: モジュール内の要素が 1 つの目的に密接に関連している
- **低結合**: モジュール間の依存を最小化し、変更の影響範囲を限定する

### 関心の分離（Separation of Concerns）

システムを独立した関心ごとに分割する。表示・ビジネスロジック・データアクセスを独立させ、
各コンポーネントが単一の関心事のみを扱うようにする。

### Fail Fast（早期失敗）

エラーは早い段階で明確に報告する。サイレントフォールバック・握りつぶし禁止。
エラーメッセージには「何が・どこで・なぜ」失敗したかを含める。

### 深いモジュール（Deep Module）

出典: John Ousterhout『A Philosophy of Software Design』（用語適応: [mattpocock/skills](https://github.com/mattpocock/skills) codebase-design、MIT License）

- **深い / 浅い**: 小さなインターフェースの背後に多くの挙動を隠すモジュールが「深い」。インターフェースが実装と同程度に複雑なら「浅い」（素通しの薄いラッパー等）
- **深さ＝レバレッジ**: 呼び出し側が学習するインターフェース量あたりに得られる挙動量。1 つの実装が N 箇所の呼び出し元と M 本のテストで回収される
- **削除テスト**: そのモジュールを削除したと想像する。複雑さが消えるなら単なる素通しだった。複雑さが N 箇所の呼び出し元に再出現するなら価値があった
- **シーム（seam）**（Michael Feathers）: その場を編集せずに振る舞いを差し替えられる場所＝インターフェースの置き場所。どこにシームを置くかは、その背後に何を入れるかとは独立した設計判断
- **アダプターが 1 つなら仮のシーム、2 つなら本物のシーム**: 実際に差し替わるものがないなら抽象（インターフェース）を導入しない（YAGNI と同旨）
- **インターフェースはテスト面**: テストと呼び出し元は同じシームを通る。インターフェースを迂回して内部をテストしたくなるなら、モジュールの形が誤っている兆候

## 2. アーキテクチャパターン

### プロジェクト規模別の推奨パターン

| 規模 | 目安コード量 | 推奨パターン | 注力する原則 |
|---|---|---|---|
| 小規模 | 〜1,000 行 | MVC / 軽量レイヤード | DRY・KISS・YAGNI |
| 中規模 | 〜10,000 行 | レイヤードアーキテクチャ・MVP・MVVM | SOLID 全般 |
| 大規模 | 10,000 行〜 | クリーンアーキテクチャ・ヘキサゴナル + DDD | 全原則の意識的適用 |

### クリーンアーキテクチャ

依存方向を「外→内」に統一した同心円構造。

```
[ UI / Controller / Presenter ]
            ↓ 依存
  [ Application / UseCase ]
            ↓ 依存
      [ Domain / Entity ]        ← 外部依存なし（最内層）
            ↑ 実装（DIP）
  [ Infrastructure / Adapter ]
```

- 最内層（Domain）は他層に一切依存しない
- ポート（インターフェース）は Application 層で定義し、Infrastructure 層で実装（依存性逆転）
- Domain 層に外部ライブラリ・フレームワーク固有の型を持ち込まない

### ヘキサゴナルアーキテクチャ（Ports & Adapters）

ビジネスロジックを中心に置き、すべての外部接続をポート（インターフェース）経由にする。

| 種別 | 役割 | 例 |
|---|---|---|
| インバウンドアダプター | 外部リクエスト → 内部ユースケースへの変換 | HTTP コントローラー・CLI ハンドラー |
| アウトバウンドアダプター | 内部リクエスト → 外部サービスへの変換 | DB リポジトリ実装・外部 API クライアント |

テスト時はアダプターをモックに差し替え可能であることが利点。

### レイヤードアーキテクチャ

| レイヤー | 責務 | 依存先 |
|---|---|---|
| プレゼンテーション | UI / API エンドポイント | アプリケーション層のみ |
| アプリケーション | ユースケース・オーケストレーション・トランザクション境界 | ドメイン層 |
| ドメイン | ビジネスルール・エンティティ・値オブジェクト | なし（最内層） |
| インフラストラクチャ | DB・外部 API・メッセージキュー | ドメイン層（DIP で逆転） |

## 3. デザインパターン（GoF 主要パターン）

### 生成パターン

| パターン | 用途 | 注意点 |
|---|---|---|
| Factory Method | オブジェクト生成のカプセル化。生成ロジックの変更を局所化 | — |
| Abstract Factory | 関連オブジェクト群の一貫した生成（ファミリー切り替え） | — |
| Builder | 複雑なオブジェクトの段階的組み立て | — |
| Singleton | 単一インスタンスの保証 | テスト困難化・グローバル状態汚染のリスクあり。乱用禁止 |

### 構造パターン

| パターン | 用途 |
|---|---|
| Adapter | 互換性のないインターフェースを橋渡し（レガシー連携・外部ライブラリ隔離） |
| Decorator | 継承なしで機能を動的に付加 |
| Facade | 複雑なサブシステムを単純化したインターフェースで覆う |
| Composite | ツリー構造のオブジェクト群を統一的に扱う |

### 振る舞いパターン

| パターン | 用途 |
|---|---|
| Strategy | アルゴリズムの交換可能性（switch / if 連鎖の代替） |
| Observer | 状態変化の疎結合な通知（イベント駆動） |
| Command | リクエストをオブジェクト化（undo・キュー・ログ対応） |
| Template Method | 処理骨格を定義し、詳細をサブクラスに委ねる |

## 4. DDD 実装パターン（大規模向け）

| コンセプト | 役割 |
|---|---|
| エンティティ | ID で識別される業務オブジェクト。ビジネスルールをカプセル化 |
| 値オブジェクト | 値で識別（ID なし）。不変・バリデーション内包 |
| ドメインサービス | エンティティに属さない業務ロジック |
| リポジトリ | ドメインオブジェクトの永続化抽象（インターフェースとして定義） |
| ドメインイベント | 業務上重要な出来事の記録・通知 |
| 集約（Aggregate） | 整合性境界。ルートエンティティ経由でのみ変更を受け付ける |
| 境界付けられたコンテキスト | ドメインモデルが一貫して通用するスコープ |

## 5. エージェント時代の補足原則

AI 支援開発（Claude Code 等）固有のベストプラクティス。

| 原則 | 内容 |
|---|---|
| 検証可能な要求 | 完了条件は観測・実行可能な形で定義する（「いい感じに」は不可） |
| 単一目的の変更 | 1 PR・1 コミットの変更理由は 1 つ。依頼外の変更は行わない |
| テストを契約として | テストは「変更が契約を破っていないか」を示す機械的手段 |
| 境界の明示 | 権限・データ・ネットワーク境界をデフォルト OFF で可視化 |
| 追跡可能性 | 設計判断の「なぜ」を `./doc/adr/` に記録する |
| 型・静的解析 | 実行前に捕捉可能なバグを実行時に回さない（`strict: true`、`any` 禁止） |
| 人間のゲート | 本番デプロイ・秘密ローテーション・force push は人間が承認する |
| CI = 共有の真実 | ローカルコマンドと CI コマンドを一致させる |

## 6. コード品質基準

| 基準 | 目安 |
|---|---|
| 関数の責任 | 1 つのみ |
| ネスト深度 | 3 階層まで |
| 関数行数 | 50 行以内を目安 |
| コメント | WHY（なぜ）を書く。WHAT（何を）はコードで示す |
| 型安全性 | `any`・型アサーション乱用は禁止 |
| エラーハンドリング | `catch (e) {}` 等の握りつぶしは禁止 |
| 依存方向 | 上位レイヤーが下位レイヤーを知らない構造を維持 |

## 7. 設計レビューチェックリスト（クイックリファレンス）

詳細な検証は `/se-principles check <パス>` を使用する。

### ファイル・クラス設計時

- [ ] どのレイヤー・責務に属するか明確か
- [ ] 単一の変更理由（責任）のみを持つか
- [ ] 依存方向が正しいか（上位→下位、または抽象→具象は禁止方向に注意）
- [ ] 同じロジックが他にコピーされていないか

### 実装時

- [ ] インターフェース経由の依存になっているか
- [ ] ドメイン層に外部ライブラリの型が混入していないか
- [ ] テスト可能な設計か（差し替え可能な依存か）
- [ ] 将来のための過剰な汎用化をしていないか（YAGNI）
- [ ] エラーを明確に報告しているか（Fail Fast）

### DB・データモデル設計時

- [ ] テーブル名・列名にローマ字を使っていないか（英単語 + 辞書ツールを活用）
- [ ] 業務コードを主キーに使っていないか（サロゲートキーとビジネスキーを分離する）
- [ ] 1 セルに 1 つのスカラ値のみか（第 1 正規形違反がないか）
- [ ] 非正規化を採用した場合、設計書に理由・解消条件を記録したか
- [ ] 導出項目（計算で求められる列）の保持が必要かどうか判断したか

## 8. データモデリング原則

| 原則 | 内容 |
|---|---|
| 命名にローマ字を使わない | テーブル名・列名は英単語で命名する。[codic](https://codic.jp/) 等の辞書ツールを活用する |
| 業務コードを PK に使わない | 業務コードは変更・廃止リスクがある。サロゲートキーとビジネスキーを分離する |
| 第 1 正規形を守る | 1 セルには 1 つのスカラ値のみ。カンマ区切りリストや繰り返し項目は禁止 |
| 導出項目は削除を原則とする | 計算で求められる列は原則削除。証跡として必要な場合のみ保持し理由を記録する |
| コード値はテキスト型で管理する | 電話番号・社員番号等のコード値は整数型ではなくテキスト型で管理する（ゼロ欠け防止） |
| 意図的な非正規化を明記する | パフォーマンス・BIツール連携等による非正規化は設計書または ADR にその根拠と解消条件を明記する |
| マスタの項目を分類する | 必須項目・推奨項目・任意項目を設計段階で分類し、段階的に導入できるようにする |

# コード品質ルール（常時適用）

SOLID・DRY・KISS・YAGNI・Fail Fast の一言要約と汎用の品質基準（関数行数・ネスト深度・型安全性等）、実装前の判断順序と着手前の確認は [`../docs/code-quality-details.md`](../docs/code-quality-details.md) に分離している。**原則の適用は常に必須**。コードの生成・修正・レビューに着手する前に、内容の確認が必要なら Read する。

## AI 支援開発における追加原則

| 原則 | 内容 |
|---|---|
| 単一目的の変更 | 1 PR・1 コミットの変更理由は 1 つ。依頼外の変更は行わない |
| テストを契約として | テストは「変更が契約を破っていないか」を示す機械的手段 |
| 型・静的解析 | 実行前に捕捉可能なバグを実行時に回さない（`strict: true`、`any` 禁止） |
| 人間のゲート | 本番デプロイ・秘密ローテーション・force push は人間が承認する |
| 追跡可能性 | 設計判断の「なぜ」を `./doc/adr/` に記録する |

## 完了の証拠主義（verification before completion）

作業の「完了」を報告する前に、機械的な検証手段でその完了を裏付ける。出典: ADR-009（obra/superpowers `verification-before-completion` と loki-mode の Evidence Receipt 着想の統合）。

- **検証してから完了を宣言する**: テスト・ビルド・lint・実行など該当する検証手段を実行し、その結果を根拠として報告に添える。検証手段がない場合は「何を確認し、何が未検証か」を明示する
- **未検証の断定を使わない**: 「動くはず」「たぶん通る」「probably works」等、検証に基づかない完了表現を使わない。未検証なら「未検証」と正直に書く
- **事実と判断を分離する**: コマンド出力・終了コード・diff・ビルド状態などの「事実」と、それに対する解釈・判断を分けて報告する。事実の裏付けなしに「完了」としない
- **証拠は要点のみ**: 検証の証拠は終了コードと要点だけをコンテキストに載せ、全文はファイルへ退避する（トークン経済性）。長時間・大量出力を伴う検証は `/long-run` で回す
- **決定論的に求まる値を暗算・記憶で出さない**: ハッシュ値・Base64 等のエンコード結果・UUID・WCAG コントラスト比・**検査数字（チェックデジット）の検証と生成**・**cron の次回実行時刻・営業日の加減算・エポック秒とタイムゾーンの変換・JWT のクレーム**は、`/vnl` のスクリプトで算出してその出力を根拠として示す。これらは誤っていても「もっともらしい値」に見えるため、読み手が検証なしに誤りを見分けられない。**「自分で計算できる」と感じる種類ほど取り違えが起きる**（実測: 列挙にある値は `/vnl` が発動し、無い値は発動しなかった。ADR-038・ADR-040）
- Windows（PowerShell）では直前コマンドの終了コードを `$LASTEXITCODE` / `$?` で確認する

> 本節は既存の Fail Fast（本ファイル冒頭）・「Claude Code が独断でフェーズ完了を宣言しない」（`.claude/project-types/development.md`）・編集後の完全性確認（`.claude/rules/safe-file-ops.md`）を、完了報告全般へ水平展開したもの。デバッグ時の根本原因究明の規律は `debugger` エージェントに定義する。

## DB・テーブル設計の命名規約

テーブル設計・カラム定義を生成・レビューする場合に適用する。

| 規則 | 内容 |
|---|---|
| ローマ字禁止 | テーブル名・列名はローマ字ではなく英単語で命名する。[codic](https://codic.jp/) 等の辞書ツールを活用する |
| 品詞 | テーブル名・列名は名詞（句）または 形容詞＋名詞（句） |
| 冗長語句の禁止 | `Data`・`Info`・`Item`・`Util` など意味が広い語句は使用しない |
| コレクション名 | テーブル名を `○○List`・`○○Collection` としない。複数形で充分 |
| 業務コードを PK に使わない | 業務コードは変更・廃止リスクがある。サロゲートキーとビジネスキーを分離する |
| 非正規化の明記 | 意図的な非正規化は ADR に根拠と解消条件を記録する |

> テーブル設計の詳細（Dataverse固有・データ型・正規化・パターン等）は `data-modeler` サブエージェントを使用する。
> 既存スキーマのアンチパターン検出（レビュー）は `/db-review` スキルを使用する。

# document-review リファレンス — 種別固有レビュー観点・非機能要件定義

`/document-review` スキル（`SKILL.md`）から参照されるリファレンス。スキル本体ではないため直接呼び出しはできない。
レビュー対象のドキュメント種別を判定したら、該当セクションを Read してから観点チェックを実施すること。

---

## 種別固有レビュー観点

### 要件定義書

- 機能要件と非機能要件が分離されているか（このスキルの「非機能要件（参照定義）」参照）
- 各要件に受け入れ基準（acceptance criteria）が定義されているか
- ユースケースに主シナリオ・例外シナリオが記述されているか
- 要件間のトレーサビリティが確保されているか
- ステークホルダーの承認者が明記されているか

### 基本設計書・詳細設計書

- 要件定義書へのトレーサビリティがあるか
- API 設計が `/api-guide` スキルの API 設計規約に準拠しているか
- セキュリティ考慮事項が CLAUDE.md「セキュリティ」および `.claude/rules/security-hardstops.md` の要件を満たしているか
- 非機能要件（このスキルの「非機能要件（参照定義）」参照）への対応方針が記述されているか
- エラー処理・ログ設計の方針が `/project-code-review` スキルのログ設計に準拠しているか

#### P0 最優先（致命的リスク）

**実現可能性の確認（P0-1）**

| 確認観点 | チェック内容 |
|---|---|
| 実現方式の前提 | 使用する基盤・サービス・ライセンスが調達済み／調達可能か。顧客側が用意する前提（環境・ネットワーク・ID・権限）が明記されているか。外部依存のスケジュールが計画に織り込まれているか |
| 標準機能と追加開発の境界 | 標準機能で提供されない機能を「標準でできる」ように記述していないか。見積条件で対象外とした機能が実装前提で書かれていないか |
| 運用可能性 | 例外処理（エラー・差戻し・タイムアウト・重複・権限不足）の運用手順が記述されているか。「誰が」「いつ」「何を見て」「どう復旧するか」が明確か。運用担当への要求が現場の実態に照らして過大でないか |
| 性能・容量の根拠 | 最大件数・ピーク同時数・応答時間目標の前提と見積もり根拠があるか。想定外の増加時の対処方針（劣化モード・スケール方法等）があるか |

**契約不適合リスクの潰し込み（P0-2）**

| 確認観点 | チェック内容 |
|---|---|
| 危険な表現の排除 | 「必ず」「完全に」「すべて」「無停止」「恒久的に」「制限なく」等の断定表現がないか。根拠・条件なしの性能保証（「応答1秒以内」「99.99%稼働」等）がないか |
| 契約文書との整合 | 契約で「対象外」とした事項が「実装する」扱いで書かれていないか。仕様凍結の「基準日」・変更管理の扱いが設計書と合っているか |
| 受入基準の整合 | 検収条件（契約上の条件）と設計書の品質保証範囲が矛盾していないか。「不具合対応期間」「無償範囲」を設計書が拡大解釈していないか |
| スコープの明文化 | スコープ外・前提・未確定事項が一覧化されているか。未確定事項に「いつ・誰が・どう決める」が書かれているか |

#### P1 重要

**設計妥当性（P1-1）**

| 確認観点 | チェック内容 |
|---|---|
| アーキテクチャ選定理由 | 代替案と比較して、なぜその方式を採用したか（コスト・期間・保守・性能・セキュリティ）が記述されているか |
| 例外系・異常系の設計 | エラーメッセージ・復旧手順・再実行可否・ロールバック・二重登録防止が定義されているか。エラーの担当境界（利用者通知 vs 運用対応）が明確か |

**非機能の責任範囲（P1-2）**

| 確認観点 | チェック内容 |
|---|---|
| セキュリティ・プライバシー | 認証・認可が機能単位で落ちているか。ログ・監査（何を残すか・誰が見るか・保管期間）が運用と整合しているか。個人情報・機微情報の取得経路・利用目的・保管・廃棄が明記されているか |
| 可用性・復旧 | 障害時の責任分界（顧客運用／ベンダ運用／クラウド責任範囲）が明記されているか。バックアップ・復旧の運用（復旧目標・手順・検証方法）が記述されているか |
| 運用・保守 | 定常作業（棚卸・設定変更・権限追加・問合せ対応）と頻度が明記されているか。同一概念に異なる呼称（異音同義語）が混在していないか |
| 参照の正確性 | 「別紙参照」「別資料参照」がファイル名・版・格納場所まで追えるか |
| 図と本文の整合 | 構成図の矢印方向と本文の処理順が一致するか。画面遷移図と画面仕様の遷移条件が一致するか |

### ADR（`doc/adr/`）

- ステータス（提案中／承認済み／廃止／置換済み）が明記されているか
- 検討した選択肢が複数記載されているか
- 決定の理由が具体的かつ客観的か
- 影響範囲が記述されているか
- 既存の ADR との関連・矛盾がないか

### テスト仕様書

- 要件定義書・設計書へのトレーサビリティがあるか
- テスト種別（`/unit-test-gen` スキルのテスト方針参照）が明記されているか
- 合否判定基準（期待値）が明確か
- 正常系・異常系・境界値が網羅されているか
- 環境・前提条件が記述されているか

#### P0 最優先（単体テスト仕様書）

| 確認観点 | チェック内容 |
|---|---|
| 方針・前提条件の明文化 | テストの目的・対象範囲・実施環境・実行ユーザーの権限が明記されているか。プラットフォーム固有の前提条件（環境変数・接続設定・ネットワーク制約等）が記述されているか |
| 保証しない事項の明示 | プラットフォーム障害・ネットワーク遅延・外部 API の品質・利用者の誤操作など、単体テストで保証できない事項が列挙されているか。切り分けが曖昧な場合は「品質保証の約束」として解釈されるリスクがある |
| テスト対象の粒度定義 | テスト対象コンポーネントの粒度（画面単位・フロー単位・テーブル単位等）が設計書と対応づけて整理されているか |
| テスト観点の体系化 | 正常系・準正常系・異常系・境界値・例外系の区分が定義されているか |
| 証跡方針 | テスト結果の記録方法と証跡レベルが検収条件と整合しているか。証跡要求が過剰（全件スクリーンショット必須等）になっていないか |

#### P1 重要（単体テスト仕様書）

| 確認観点 | チェック内容 |
|---|---|
| テストケースの再現可能性 | テスト条件（前提状態・ユーザー権限・入力値）・操作手順・期待結果が第三者でも再現可能な粒度か。「正常に表示される」等の抽象的な期待結果になっていないか |
| 自動テストの扱い | 自動テストの適用範囲が明記されているか。「記載なし＝未実施」なのか「意図的に対象外」なのかが判別できるか |
| テストデータ管理 | テストデータの投入方法・本番データとの識別ルール・テスト後の後処理（削除・復旧の要否）が明記されているか。ロールバックできない操作の注意点が記載されているか |
| 後続工程との役割分担 | 単体テストで確認する範囲と、後続工程（結合テスト・総合テスト）で確認する範囲が区別されているか |

### 運用・手順書

- 手順が再現可能な粒度で記述されているか
- ロールバック手順が含まれているか（`/deploy-guide` スキル準拠）
- 実施前提条件・権限要件が明記されているか

## 非機能要件（参照定義）

要件定義書・設計書のレビュー時に、以下の非機能要件区分が定義されているか確認する。

| 区分 | 定義すべき内容 | 例 |
|---|---|---|
| 性能 | 応答時間・スループット・同時接続数 | 画面表示 3 秒以内、ピーク時 100 rps |
| 可用性 | 稼働率・計画停止の可否 | 99.9%（月間停止 43 分以内） |
| 拡張性 | ユーザー数・データ量の増加に対する対応方針 | 水平スケールアウト対応 |
| 保守性 | コードの可読性・テストカバレッジ目標 | カバレッジ 80% 以上 |
| セキュリティ | 認証方式・暗号化要件・監査ログ | OAuth 2.0、通信 TLS 1.2 以上 |
| データ保持 | 保持期間・バックアップ頻度・復旧目標 | RPO 1 時間、RTO 4 時間 |

### 非機能要件管理のルール

- 非機能要件は要件定義書に機能要件と同等の優先度で記載する
- 実装・テスト時に非機能要件を満たしているか確認する
- 非機能要件が未定義のまま実装フェーズに入らない

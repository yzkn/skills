# /document-review スキル — ドキュメントレビュー

指定したドキュメントをレビューし、品質・完全性・整合性の観点から構造化されたフィードバックを提供する。「レビューして」「確認して」「ドキュメントをチェックして」などのリクエストがあった場合に自動で適用される。

## 適用方法

`/document-review [パス]` で直接呼び出せるほか、以下のような依頼で自動適用される。

- 「`<ファイルパス>` のドキュメントをレビューして」
- 「`<ディレクトリパス>` 配下のドキュメントをチェックして」（配下の全 Markdown ファイルをレビュー）

---

## 前提確認

レビューを開始する前に、以下が不明な場合は**必ずユーザーに確認してから**作業を進める。

| 確認事項                           | 不明と判断する状況                                                                                             |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 実装に使用する言語・フレームワーク | 設計書・API 仕様書等の技術ドキュメントをレビューする場合で、対象システムの技術スタックが判断できない場合       |
| コーディング規約                   | コーディング規約（`/code-refactor` スキル）以外にプロジェクト固有の規約が存在する可能性があり、ドキュメント内のコードサンプルや設計方針に影響する場合 |
| プロジェクト固有のドキュメント規約 | CLAUDE.md「コミュニケーション」以外に独自のドキュメント規約・テンプレートの有無が不明な場合                                                |

---

## 実行手順

1. **ドキュメントの読み込み**
   - 指定されたファイルを読み込む
   - ディレクトリが指定された場合は配下の Markdown ファイルをすべて対象とする

2. **ドキュメント種別の判定**
   - ファイル名・ディレクトリ・内容からドキュメント種別を判定する
   - 判定できない場合はユーザーに確認する

3. **レビューの実施**
   - `.claude/project-types/development.md`「共通レビュー観点」に加え、下記「ドキュメント固有観点」と「種別固有観点」でチェックする

4. **指摘事項の敵対的レビュー**
   - 出力前に `.claude/rules/adversarial-review.md`（実施タイミング 5）に従い反証パスを 1 回回す
   - 本文を読み直すと成立しない指摘（他節に既に記載がある「記載漏れ」等）は削る。原本を確認できていない指摘は「未検証」として区別する
   - フェーズ成果物（要件定義書・設計書）のレビューは同ルールのタイミング 1 にも該当するため、承認可否を示す場合は独立パス（反証専任のサブエージェント 1 体）も回す

5. **レビュー結果の出力**
   - 下記「レビュー結果フォーマット」に従い Markdown 形式で出力する
   - 重要度の定義は `.claude/project-types/development.md`「レビュー重要度」に従う

6. **記録の提案**
   - レビュー完了後、`/record <トピック名>` でレビュー内容を記録することを提案する

---

## ドキュメント固有の観点

`.claude/project-types/development.md`「共通レビュー観点」（セキュリティ・フェーズ適合・外部整合性）に加えて、ドキュメントレビュー時は以下を確認する。

| 観点       | 確認内容                                                       |
| ---------- | -------------------------------------------------------------- |
| 完全性     | 必須セクションが揃っているか、空欄・TBD・TODO が残っていないか |
| 明確性     | 曖昧な表現・主語のない文・多義的な記述がないか                 |
| 内部整合性 | ドキュメント内部で矛盾がないか                                 |
| 表記統一   | 用語・表記が統一されているか（CLAUDE.md「コミュニケーション」準拠） |
| 誤記確認   | 誤字脱字・変換ミス・全角半角の混在・不自然な記号の使用がないか |
| 章構成     | 章・節・項の構成が論理的で、見出しから内容の概要が把握できるか |
| 文章品質   | 一文が過度に長くなっていないか、主語と述語の関係が明確か。専門用語・略語に必要な補足説明があるか |
| 視認性     | 手順・条件・比較事項が箇条書きや図表で整理されているか         |
| 記載粒度   | 同一レベルの章・項で記載量・詳細度が極端にばらついていないか   |

---

## 種別固有レビュー観点

種別ごとの詳細観点（要件定義書・基本設計書/詳細設計書の P0/P1 チェック表・ADR・テスト仕様書の P0/P1 チェック表・運用手順書）は、同ディレクトリの `document-review-reference.md` に定義されている。
**ドキュメント種別を判定したら、必ずリファレンスの該当セクションを Read してから観点チェックを実施すること。** 記憶からの再現・観点の省略は禁止。
非機能要件の区分定義（性能・可用性・拡張性・保守性・セキュリティ・データ保持）も同ファイルの「非機能要件（参照定義）」を参照する。

## レビュー結果フォーマット

```markdown
# ドキュメントレビュー結果

**対象:** <ファイルパス>
**日時:** YYYY-MM-DD HH:MM
**種別:** <ドキュメント種別>
**総合判定:** ✅ 承認 / ⚠️ 軽微な修正要 / ❌ 重大な問題あり

## サマリー

<全体的な評価を 2〜3 文で記述>

## 指摘事項

| #   | 重要度 | 場所                   | 内容         | 対応案   |
| --- | ------ | ---------------------- | ------------ | -------- |
| 1   | 🔴 高   | <セクション名・行番号> | <問題の説明> | <改善案> |
| 2   | 🟡 中   | <セクション名・行番号> | <問題の説明> | <改善案> |
| 3   | 🟢 低   | <セクション名・行番号> | <問題の説明> | <改善案> |

## 良い点

- <ポジティブなフィードバック>

## 次のアクション

- [ ] <対応が必要な事項（重要度 🔴 高 のもの）>
- [ ] <対応が必要な事項>
```

---

## 注意事項

- レビュー対象ファイルが `./doc/prompt/`・`./doc/thought/`・`./doc/adr/` 配下の場合は証跡のため編集提案を行わない（`.claude/CLAUDE.md`「証跡の不変性」）
- レビュー結果はチャット上に出力するのみとし、ファイルへの書き込みはユーザーが `/record` で明示的に記録する

# アニメーション監査プレイブック

8 つの監査カテゴリ、各カテゴリで確認すべき点、そして所見・計画で引用すべき正確な目標値をまとめたもの。Emil Kowalski 氏のデザインエンジニアリング哲学（[emilkowal.ski](https://emilkowal.ski/)）から抽出している。ここに記載された値は絶対に近似せず、そのままコピーすること。

## 1. 目的と頻度

すべてのアニメーションは「なぜこれはアニメーションするのか」に答えられなければならない — 空間的な一貫性、状態の提示、フィードバック、説明、あるいは唐突な変化の防止のいずれかである。頻繁に目にする要素において「かっこいいから」は目的にならない。

| 頻度 | 判断 |
| --- | --- |
| 1 日 100 回以上（キーボードショートカット、コマンドパレットの開閉） | アニメーションしない。例外なし |
| 1 日数十回（ホバー効果、リストのナビゲーション） | 削除するか大幅に削減する |
| 時々（モーダル、ドロワー、トースト） | 標準的なアニメーション |
| まれ／初回のみ（オンボーディング、フィードバック、達成演出） | 喜びの演出を加えてよい |

探すべきもの: キーボード操作起点のアニメーション、開閉トランジションを持つコマンドパレット（Raycast にはこれがない — これが正しい）、常時目にするリスト項目やホバー状態への装飾的なモーション。最も強力な修正は往々にして**アニメーションを削除すること**である。

## 2. イージングと duration

イージング選択の優先順位:

- 入場・退場 → **`ease-out`**（速く始まり、レスポンシブに感じる）
- 画面上での移動・変形 → **`ease-in-out`**
- ホバー・色の変化 → **`ease`**
- 一定の動き（マーキー、プログレス） → **`linear`**
- デフォルト → **`ease-out`**

**UI における `ease-in` は常に所見の対象である** — ゆっくり始まるため、ユーザーが注視しているまさにその瞬間が遅れてしまう。CSS 組み込みのイージングは意図的なモーションには弱すぎるため、計画では強めのカスタムカーブを（リポジトリの慣習に合わせたトークンとして）導入すべきである。

```css
--ease-out: cubic-bezier(0.23, 1, 0.32, 1);        /* strong ease-out for UI */
--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1);    /* strong ease-in-out for on-screen movement */
--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1);     /* iOS-like drawer curve */
```

Duration の目安 — **UI のアニメーションは 300ms 未満に収める**。

| 要素 | Duration |
| --- | --- |
| ボタン押下のフィードバック | 100〜160ms |
| ツールチップ、小さなポップオーバー | 125〜200ms |
| ドロップダウン、セレクト | 150〜250ms |
| モーダル、ドロワー | 200〜500ms |
| マーケティング／説明用 | より長くてもよい |

探すべきもの: どこかにある `ease-in`、入場に使われた素の `ease`／`linear`、UI 要素で 300ms を超える duration、ツールバー内のすべてのツールチップで tooltip delay とアニメーションが毎回発生している（最初の 1 つ以降は即時であるべき）。

## 3. 物理性と origin

- **`scale(0)` は絶対に使わない** — 現実世界では何もないところから物が現れることはない。目標値: `scale(0.9〜0.97)` + `opacity: 0`。
- **ポップオーバー・ドロップダウン・ツールチップはトリガーから scale する**。中心からではない。
  ```css
  .popover { transform-origin: var(--radix-popover-content-transform-origin); } /* Radix */
  .popover { transform-origin: var(--transform-origin); }                       /* Base UI */
  ```
  **モーダルは例外** — 中央に表示されるのが正しいため、`transform-origin: center` はモーダルにおいては正しい。所見として報告しないこと。
- **押下フィードバック**: `:active` で `transform: scale(0.97)`、`transition: transform 160ms ease-out`。控えめに保つこと（0.95〜0.98）。

探すべきもの: `scale(0)`、初期 transform を伴わない純粋なフェード入場、トリガーに紐づくはずの要素での `transform-origin: center`（または未設定）、押下可能な要素に押下フィードバックがない状態。

## 4. 中断可能性

CSS の **transition** は途中の状態からリターゲットできるが、**keyframes** はゼロから再スタートする。素早く繰り返しトリガーされるもの、あるいは動作中に逆転しうるもの（積み重なるトースト、トグル、ドラッグ、展開／折りたたみ）は transition または spring を使わなければならない。

- JS なしでの入場: `@starting-style`（レガシーなフォールバック: `useEffect` 内で設定する `data-mounted` 属性）。
- ジェスチャー駆動のモーションは spring を使うべきである — 中断されても速度情報を保持できる。
- Spring 設定、Apple 風（推奨）: `{ type: "spring", duration: 0.5, bounce: 0.2 }`。bounce は控えめに保つ（0.1〜0.3）。目に見えるバウンスはドラッグでの dismiss や遊び心のある演出のために取っておく。
- **非対称なタイミング**: 意図的なフェーズ（押下、保持、破壊的な確認）はゆっくりアニメーションし、システムの応答はスナップさせる。press-and-release で対称なタイミングになっている場合は所見の対象である。

探すべきもの: トースト・トグルなど頻繁にトリガーされる UI での `@keyframes`、固定 duration の keyframes で tween しているジェスチャーハンドラ、速度ベースの dismiss を伴わないドラッグ（distance のみでなく `Math.abs(distance)/elapsedMs > 約0.11` で dismiss すべき）、ドラッグの境界で摩擦が増すのではなくハードストップしているもの。

## 5. パフォーマンス

- **`transform` と `opacity` のみをアニメーションさせる。** `width`／`height`／`margin`／`padding`／`top`／`left` はレイアウト・ペイント・コンポジットを引き起こす。
- **`transition: all`** は意図しないプロパティまで GPU 外でアニメーションさせてしまう — 常に所見の対象。
- **Framer Motion の `x`／`y`／`scale` ショートハンドはハードウェアアクセラレーションされない** — メインスレッドで実行され、負荷がかかるとフレームを落とす。目標: フル transform 文字列を使う `animate={{ transform: "translateX(100px)" }}`。
- **親の CSS 変数経由で子要素の transform を駆動しない** — すべての子要素のスタイル再計算を引き起こす。要素に直接 `transform` を設定すること。
- 決まった動きには CSS（および WAAPI）が負荷下でも rAF ベースの JS に勝る — 決まったモーションには CSS を、動的・ジェスチャー駆動のモーションには JS／spring を使う。
- トランジション中の `filter: blur()` は 20px 未満に保つ — 重い blur はコストが高く、特に Safari で顕著。

探すべきもの: `transition: all`、アニメーションされているレイアウトプロパティ、負荷の高いページでの Framer Motion ショートハンドプロパティ、子要素の transform を駆動する `setProperty('--x', …)`、CSS で済むはずの処理を行う rAF ループ。

## 6. アクセシビリティ

```css
@media (prefers-reduced-motion: reduce) {
  .element { animation: fade 0.2s ease; } /* keep opacity/color, drop movement */
}
@media (hover: hover) and (pointer: fine) {
  .element:hover { transform: scale(1.05); } /* touch fires false hovers on tap */
}
```

reduced motion が意味するのは、アニメーションを少なく・穏やかにすることであり、**ゼロにすることではない** — 理解を助ける transition は残し、位置の変化のみを取り除く。JS では `useReducedMotion()` を使い、transform の値を分岐させる。

探すべきもの: `prefers-reduced-motion` への対応がない動き、ゲートされていない `:hover` によるモーション、フィードバックをすべて消してしまっている reduced-motion 実装。

## 7. 一貫性とトークン

- モーションはプロダクトの性格に合わせるべきである — 遊び心のあるものはよりバウンシーに、ダッシュボードはキリッとしたままに。コンポーネント間で性格が食い違っている場合は所見の対象。
- カーブと duration は共有トークンとして存在すべきである。ほぼ一致する 5 つの手打ち cubic-bezier は統合すべき所見である。
- すべてが一斉に登場するグループの入場には **30〜80ms の stagger** が本来あるべき場所である。stagger は装飾的なものであり、操作をブロックしてはならない。
- 2 つの状態が重なって見える唐突なクロスフェードは、遷移中の控えめな `filter: blur(2px)` で緩和できる。

探すべきもの: ほぼ同一のイージング／duration の重複、キリッとしたアプリの中の 1 つだけバウンシーなコンポーネント、stagger のないリスト／グリッドの入場、二重露光が目に見えるクロスフェード。

## 8. 見落とされている機会

追加的なカテゴリ — アニメーションすべきなのにしていない箇所。

- コンテンツの入れ替わりやレイアウトの飛びなど、瞬間移動のように見える状態変化。短い遷移があれば唐突さを防げる箇所。
- 空間的に関連する UI（トリガーから現れるパネル）で、どこから来たのかを説明するモーションがない箇所。
- まれで感情的な瞬間（初回起動、成功、お祝い）に、許容されている喜びの演出予算がまったく使われていない箇所。
- ハードコードされたピクセルオフセットではなく、これらのためのツールとしての `translate` のパーセンテージ指定（`translateY(100%)` = 要素自身の高さ）や `clip-path: inset()` によるリビール。

実際に観察した UX 上の継ぎ目に根拠を置いた、多くても数件を報告すること — 願望リストにしないこと。

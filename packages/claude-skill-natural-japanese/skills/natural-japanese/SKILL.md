# /natural-japanese スキル — 日本語の自然さ・読みやすさの検査と改稿

**引数:** `$ARGUMENTS`（`[write|score] [quick|full] <対象ファイルや依頼内容>`）

軸は 2 つ。第一に「**検出は機械、判断は AI**」。AI は自分の癖を認識しにくいため、疑わしい箇所の検出は lint スクリプトが決定的に行い、直すかどうかは文脈を見て判断する。第二に「**事後修正より生成時制約**」。書いた後に AI 臭を消すより、書く前の設計と書くときの制約で発生自体を防ぐ。工程は「設計 → 執筆 → 検査 → 収束」の順に進む。

> 出典: [coji/natural-japanese](https://github.com/coji/natural-japanese)（MIT License、`LICENSE` 参照）。`references/`・`assets/`・`scripts/` は原典のまま取り込み、この SKILL.md のみ本リポジトリ向けに書き換えた。改変内容は末尾「原典からの改変点」を参照。

## 他スキルとの棲み分け（先に確認する）

| 依頼の中身 | 使うもの |
|---|---|
| 社内文書・プレゼン資料の**型**（目的別の構成・ターゲット別の要件・表記ルール・引用の可否） | `/ghostwriter` |
| 文書の**品質・完全性・整合性**のレビュー（記載漏れ・他成果物との矛盾） | `/document-review` |
| 日本語としての**自然さ・読みやすさ**（本スキル） | `/natural-japanese` |
| IT 知識のない読者向けに**噛み砕いて解説**する | `/newcomer-guide` |
| UI のマイクロコピー（ボタン・エラーメッセージ） | `/ux-writing` |

### 競合したときの裁定【重要】

**表記ルールも構成ルールも、`/ghostwriter` がカバーする文書種別では ghostwriter を優先する。** ghostwriter は社内規約に基づく規定であり、本スキルの文体憲法（`references/writing-constitution.md`）は一般的な読みやすさの指針であるため、社内規約が上位に立つ。

| 文書種別 | 優先するもの |
|---|---|
| 社内文書・プレゼン資料・顧客向け文書（ghostwriter の対象） | **ghostwriter** |
| ブログ・note・エッセイ・技術記事（ghostwriter の対象外） | **本スキルの文体憲法** |

実際に競合する箇所は次の 2 つ。**どちらも表記ではなく構成の規定**であり、気づかずに本スキルを適用すると社内規約に反する改稿になる。

| 論点 | ghostwriter | 本スキルの文体憲法 |
|---|---|---|
| 見出し・箇条書きの形 | `ghostwriter-reference.md`「タイトル・箇条書きは体言止め」 | 2 条「見出しに結論を埋め込む。ラベルだけの見出しは書かない」 |
| 箇条書きの是非 | 同「記書きの活用」「修飾語 1〜2 個を含む名詞句が理想」 | 3 条「因果と経緯は地の文で書く。箇条書きは本当に並列なときだけ」 |

**ghostwriter 対象の文書で §4 の構造レビューがこの 2 点を指摘した場合は、判断台帳に「残す（理由: ghostwriter 優先）」と記録して直さない。** 指摘そのものを抑止する必要はなく、仕分けの段階で落とす。

どちらを採ったかは報告に 1 行添える。

> なお `scripts/lint.py` は見出し・箇条書き・表・コードブロック・引用ブロックを解析前にマスクするため、**この競合が lint の検出結果に現れることはない**（体言止め率の検出も箇条書きを対象外にする）。競合は構造レビューと文体憲法の層にだけ生じる。

ルート `CLAUDE.md` §5「曖昧さを残さない書き方」とも観点が重なるが、あちらは**チャット応答・作業報告を含む全ての出力に常時適用**される規範で、本スキルは**成果物としての文書**に対して lint で検出して直す工程である。両者は矛盾しない。

## 前提ツール

- **uv**（PEP 723 のインラインメタデータを読んで依存を自動解決する）
- **sudachipy / sudachidict-core** — `uv run` が初回実行時に自動取得する。`sudachidict-core` の wheel は約 69MB あり、初回だけダウンロードに時間がかかる（導入は 2026-08-19 にユーザー承認済み。ADR-019 参照）
- 呼び出し方が不明な場合は `~/.claude/CLAUDE.md`「端末環境」→ `/tool-environment` の順に確認する

`uv` が使えない環境では `references/manual-checklist.md` で同じ観点を目視でなぞる。

### Windows では UTF-8 を強制する【必須】

Windows の標準出力は既定で cp932 になるため、**出力をファイルへリダイレクトすると日本語が壊れ、`--json` の結果が JSON として読めなくなる**（2026-08-19 に実測。`lint.py` 自体は exit 0 で成功するため、壊れたことに気づきにくい）。リダイレクトする場合は必ず環境変数を付ける。

```sh
PYTHONUTF8=1 PYTHONIOENCODING=utf-8 uv run .claude/skills/natural-japanese/scripts/lint.py --json <ファイル> > lint.json
```

以降のコマンド例では `<UTF8>` と略記する。背景と他の Python ツールでの回避策は `.claude/docs/windows-python-tooling.md`。

## 実行モード — クイックとフル

**クイック（既定）**: 日常の文書はこちら。サブエージェントを使わずこの場で完結させる。追加で読むのは該当する doctype の型 1 ファイルだけでよい（文体憲法は §2 の要約で足りる。他の `references/` は lint の finding が出て判断に迷ったときだけ開く）。設計（§1）は読者・主メッセージ・見出しの確認を頭の中で済ませる。検査は lint 1 回と自分でのスケルトン通読。**文書が短くても lint は省略しない**（短文では統計系の検出器が沈黙するが、禁止語・翻訳調は文 1 つでも検出される）。収束ループは新規 finding が出なければ 1 周で切り上げ、最終パスの通読をして終える。

**フル**: ユーザーが「しっかり」「時間をかけていい」と言ったとき、対外・経営層向けなど失敗コストが高い文書、または長い文書（目安 1 万字超）のとき。lint に加えて `outline.py` / `terms.py` も実行し、検査（§4）の 3 つのレビュー（構造レビュー・読みやすさレビュー・doctype 照合）を行う。収束は §5 の状態条件を満たすまで回す。「この文書には過剰」と感じても工程を勝手に間引かず、クイックへの切り替えをユーザーに提案する。

所要時間の目安はクイックが 30 秒〜3 分、フルが 7〜20 分。**フルを始めるときはこの目安をユーザーに伝えてから着手する。**

> 【要指示】原典はフルの 3 レビューを並列サブエージェントで回す設計だが、本リポジトリでは `.claude/rules/adversarial-review.md` により 3 体以上の並列起動に事前承認が要る。既定では 3 レビューを順に自分で行い、並列化したい場合はユーザーに提案してから起動する。

## 呼び出し方 — write / score

- `/natural-japanese [quick|full] <対象>` — 書く・直す（既定）。新規作成かリライトかは対象から判断する
- `/natural-japanese write [quick|full] <お題や素材>` — **新規作成を明示**。元の文章がない状態から §1 の設計（読者・主メッセージ・スケルトン・濃淡・素材集め）→ §2 の執筆 → 検査 → 収束の全工程で書き起こす。素材が乏しければ §1-4 で先に集めるか、ユーザーに求める
- `/natural-japanese score [quick|full] <ファイル>` — **診断のみ**。文書を書き換えず、自然度スコア（0〜100、高いほど自然 = AI 臭が薄い）と理由で返す。**最初に必ず `references/diagnose.md` を読む**（スコアの算出式・バンド・出力形式の定義がそこにある。これを読まずに lint findings を転記した時点で診断モードの仕事になっていない）。診断後にリライトを提案してよいが、頼まれるまで直さない

モード指定がなければ自分で選ぶ。自然言語でも同じ（「〇〇について書いて」→ write 相当、「この文章 AI っぽい？」→ score 相当）。

**`exp` モードは本リポジトリでは使えない。** 原典の `scripts/semantic.py`（文埋め込みによる話題の平板さ検出）は torch 依存で初回に約 1GB のモデルダウンロードを伴うため取り込んでいない。`references/diagnose.md` と `references/revision-guide.md` に `exp` / `semantic_topic_flatness` の記述が残っているが、いずれも読み飛ばす。

## 1. 設計 — 書く前に決める

### 1-1. 読者・目的・文書タイプ

誰が読み、読んだ後に何が起きてほしい文書かを特定する（不明ならユーザーに聞く）。文書タイプが定まったら対応する型を読む。

| 文書タイプ | 読むファイル |
|---|---|
| 議事録 | `references/doctypes/minutes.md` |
| 調査レポート・分析レポート | `references/doctypes/report.md` |
| 社内ガイド・マニュアル | `references/doctypes/guide.md` |
| リサーチメモ・企画書 | `references/doctypes/memo.md` |
| スライド構成 | `references/doctypes/slide.md` |

型に当てはまらない文書（ブログ・エッセイ等）はこの節を飛ばしてよい。

### 1-2. 主メッセージとスケルトン

本文を書く前に主メッセージを一文で書く。書けないなら素材不足であり、書き方の問題ではない（→ 1-4）。次に見出しスケルトンを作る。各見出しは「背景」「まとめ」のようなラベルではなく、結論を含むメッセージにする。見出しだけを順に読んで論旨が通ることを確認してから本文に進む。

### 1-3. 濃淡設計

すべての節を同じ熱量・同じ厚みで書くと、それ自体が「整いすぎた不自然さ」になる。重要な節を厚く、軽い節は正直に軽く、と意図的なムラを設計する。手順は `references/revision-guide.md`「濃淡設計」。

### 1-4. 素材集め（任意・新規執筆時）

固有名詞・数値・実例が手元に乏しいまま書き始めると、後段で「一般論しか言えていない」と気づいても直しようがない。手順は `references/revision-guide.md`「素材集め」。

### 1-5. 文体プロファイル（任意）

**文体プロファイルの置き場所は `~/.claude/style-profile.md`（ユーザーグローバル）とする。** 文体は案件ではなく人に属する情報であり、プロジェクトリポジトリに置くと、案件を共有した相手に個人の文体プロファイルまで配ることになる。端末・個人に紐づく情報をプロジェクトファイルに書き込まない方針（ルート `CLAUDE.md`「外部コマンドの呼び出し」・`~/.claude/tool-environment.json` の扱い）に合わせる。

- 既にあれば読み込み、視点・語彙・リズムの癖を下敷きにする。なければ汎用モードで進める
- ユーザーが「自分の文体を学ばせたい」と求めた場合のみ、`assets/style-profile-template.md` に沿って過去文章 3〜5 本から特徴を抽出し、`~/.claude/style-profile.md` に書き出す
- ユーザーが別の場所を明示した場合はそれに従う。**ただしプロジェクトルート直下には置かない**（管理ファイルのみで構成されるディレクトリのため）

> 原典はプロジェクトルートを既定としているが、本リポジトリでは上記のとおり変更した。

## 2. 執筆 — 文体憲法の下で書く

`references/writing-constitution.md` の 12 箇条を制約として本文を書く。要点は——結論から書き前置きを書かない、見出しはメッセージ、説明は地の文で書き箇条書きは真に並列な圧縮のみ、専門用語は「機能 → 名前」の順で文中説明、固有名詞・数値で接地、太字は文中の核 1 箇所、濃淡をつける、同じ鋳型を 3 回繰り返さない、「〜ではなく」は本当の誤解訂正だけ、限界と推定は明示ラベルで開示、事実と意見を分ける、結びは再統合しレポートは So What まで。

この段階では禁止語やリズムを気にしすぎず、憲法の範囲で内容を出し切ってよい。細部は次の検査工程が拾う。

## 3. 検査(1) — 静的検知

```sh
<UTF8> uv run .claude/skills/natural-japanese/scripts/lint.py --json <ファイル> > <退避先>.json
```

禁止語・翻訳調・否定肯定対比の反復・文長の均質さ・体言止め率・段落頭の接続詞率・語彙多様性・英語統語の疑いを機械的に検出する。検出件数に関わらず exit code は 0（lint なので件数で CI を止めない）。入力エラーのときだけ 1。

- ジャンルが明確なら `--genre essay|tech|business` を付ける。コーパス校正済みの閾値プロファイルに切り替わり誤検知が減る（差分は `references/genre-notes.md`）
- 収束ループ（4〜5）では直前の `--json` 出力を `--baseline` に渡すと resolved / new / persisting を自動で仕分ける
- **出力はファイルに退避し、要約と件数だけをコンテキストに載せる**（`~/.claude/CLAUDE.md`「トークン経済性」）

## 4. 検査(2) — 判断台帳と 2 つのレビュー

lint の findings は疑いの提示であり、機械的に全部直せという指示ではない。ヒットしたカテゴリの節を `references/revision-guide.md` で読み直し、文脈に照らして「直す/直さない」を判断する。判断は finding 一つひとつに「直した」か「残す（理由）」かを書き残しながら進める（台帳の形式は同ファイル「判断台帳」）。

### 未確定情報マーカー `==〜==` を落とさない【必須・`design/` 配下】

`design/` の設計書は、未確定・顧客確認待ちの値を `==テキスト==` で囲む規約になっている（`.claude/rules/design-docs.md`）。**このマーカーを含む文は lint の指摘対象になりうる**ため、改稿の巻き添えで消える経路が実在する。

```
本方式により、処理件数は ==最大 1,000 件/日（顧客確認待ち）== まで拡張することができると言えるだろう。
→ findings 4 件（forbidden_phrase / translationese ×2 / translationese_morph）がこの 1 文に付く（2026-08-19 実測）
```

`scripts/lint.py` はこのマーカーを保護しない（見出し・箇条書き・コードブロックのようにマスクされない）。したがって**改稿の前後で機械的に突き合わせる**。

```sh
grep -o "==[^=]\+==" <改稿前>.md | sort > <退避先>/before.txt
grep -o "==[^=]\+==" <改稿後>.md | sort > <退避先>/after.txt
diff <退避先>/before.txt <退避先>/after.txt      # 差が空であること
```

- 差が出たら**改稿を採用せず、マーカーを復元してから再度改稿する**
- マーカー内の文言を変えたい場合は、未確定であるという事実と確認先が保持されているかをユーザーに確認する
- マーカーを含む文に付いた finding は、原則として台帳に「残す（理由: 未確定情報マーカーを含む）」と記録して直さない。直す価値が大きい場合のみ、マーカーを保ったまま文を組み替える

> 生成した `before.txt` / `after.txt` は §7 の後片付けの対象。`design/` に置かない。

### 意味の保持 — 改稿前後の差分検査【リライト時は必須】

lint は改稿後の文だけを見るため、**改稿で情報を足した・落とした・文末の強さを変えた**ことには気づけない。既存文書を直したら、改稿前後を `scripts/yomiyasu/yomiyasu_diff.py` で突き合わせる（標準ライブラリのみ・`uv` 不要）。

```sh
<UTF8> python .claude/skills/natural-japanese/scripts/yomiyasu/yomiyasu_diff.py <改稿前>.md <改稿後>.md --json > <退避先>/diff.json
# 文書の立場が決まっていれば --stance=勧め|決まり|説明 を付ける（立場に合わない文末を拾う）
```

出力の `markers`（依頼・義務・推量・条件などの数の増減）・`new_words`（改稿前に無い語）・`lost_words`（消えた語）・`structure`（箇条書きの解除・段落の統合）を見る。

- **`new_words` は「足していないか」、`lost_words` は「条件・例外・固有名詞を落としていないか」を 1 語ずつ確かめる**。言い換えで正当に増減したものは台帳に「残す（理由: 言い換え）」と書く
- `markers` の「義務」「推量」「条件」が増減していたら、主張の強さや適用範囲が変わっていないかを原文と照らす
- 結果は候補の提示であり、判定は自分で行う。件数だけをコンテキストに載せ、全文は退避先に置く

用語カタログが必要なら禁止語は `references/forbidden-patterns.md`、翻訳調は `references/translationese.md`。専門用語が初出で説明されているかの材料には次を使う。

```sh
<UTF8> uv run .claude/skills/natural-japanese/scripts/terms.py <ファイル>
```

### 構造レビュー — スケルトン通読

lint は文レベルの表層しか見えない。特に箇条書き主体の議事録・スライドでは lint がほぼ素通りするため、構造レビューが主役になる。

```sh
<UTF8> uv run .claude/skills/natural-japanese/scripts/outline.py <ファイル>
```

見出し・各段落の先頭文・箇条書きプレースホルダを行番号付きで抽出できる。これを読んで次を確かめる。

1. 論旨が通るか（スケルトンだけで話が追えるか）
2. 各見出しがメッセージになっているか
3. 同じ鋳型の反復がないか（定義文の型、節の内部構成、書き出しの文型）
4. 濃淡があるか（全節が同じ厚みになっていないか）
5. 結びが So What に接続しているか（レポート系）

文書タイプが定まっている場合は doctype の「必須要素」と「AI がやりがちな失敗」も照合する。

### 読みやすさレビュー

```sh
<UTF8> uv run .claude/skills/natural-japanese/scripts/lint.py --reading-load <ファイル>
```

一文長・埋もれた列挙・連続漢字・二重否定・「の」連鎖を指さす。**これは AI 臭さの検出とは別目的の推敲用レーンで、自然度スコアにも `--baseline` 比較にも入らない。** 出力は「この文を見ろ」であって「直せ」ではない。

語順・読点の位置・一文一義・主語述語の距離・こそあど言葉・冗長表現は機械的な閾値化ができない判断領域。`references/readability-principles.md`（一般原則）と `references/readability-antipatterns.md`（悪文パターン 27 種を読解負荷順に A→J で分類）を参照しながら目視で判断する。**カタログは前から当てる**——A（否定の入れ子）・B（係り受けの距離）・C（語と語形の重さ）が一文の中で読者に計算を強いる高負荷層。短さは目的関数にせず、事実保持と主述・係り受けを確認した後の同等候補間でだけタイブレーカーに使う。文の分割で字数が増えるのは正しい結果であり、不合格の理由にしない。

構造レビュー・読みやすさレビューで見つけた問題も、lint の finding と同様に判断台帳へ一行として起こす。

---

## 5. 収束

台帳の「直した」項目を反映したら lint を再実行し、新しい finding が出ていないか確認する。台帳上の全 finding が仕分けられ、修正が新たな finding を生んでいない状態になるまで 3〜4 を繰り返す。同じ finding が 2 周連続で再発する場合は `references/revision-guide.md`「発散ガード」。

既存文書のリライトでは、同じ種類の修正（見出しの結論化、箇条書きの地の文化など）を全項目へ一律に当てると、元の文書の自然な濃淡を消してかえって AI 臭が増す。価値を足せる箇所だけを直す（同ファイル「改稿を一律に適用しない」）。

---

## 6. 最終パス — 自己点検ループ

lint と台帳が収束しても、それは既知のパターンが消えたことしか意味しない。最後に必ず初見の読者として通読し、声に出して読むつもりでリズムを確かめる（同ファイル「自己点検ループ」）。違和感を見つけたら台帳に起こして 5 に戻る。

---

## 7. 後片付け

作業中に作った中間ファイル（判断台帳・lint の JSON・マーカー照合の `before.txt` / `after.txt`・下書きのバックアップ等）は作業終了時に片付ける。**削除の前に、削除対象のファイル一覧をユーザーに提示して確認を得る**（`.claude/rules/safe-file-ops.md`「削除は慎重に」）。ユーザーが「残す」と答えたものは残す。

- 原典は無確認での一括削除を指示しているが、本リポジトリでは確認を必須とする
- 中間ファイルは最初から作業用の `wip/` かスクラッチパッドに作り、成果物のディレクトリ（`design/`・`report/`）に混ぜない

---

## 完了条件

- lint を実行し、全 finding が判断台帳で「直した」か「残す（理由）」に仕分けられている
- `design/` 配下を改稿した場合、`grep -o "==[^=]\+=="` の改稿前後の差分が空であることを確認した（未確定情報マーカーの欠落なし）
- 既存文書を改稿した場合、`yomiyasu_diff.py` の `new_words` / `lost_words` / `markers` の増減をすべて確かめた
- 最終パスの通読を行っている
- 報告に、実行したモード（クイック/フル）・lint の finding 件数・直した件数と残した件数を 1 行で添えている
- `/ghostwriter` の表記ルールと競合した箇所があれば、どちらを採ったかを明記している

# trouble-shooter リファレンス

> **このファイルについて**: trouble-shooter エージェントおよび /trouble-shoot スキルから参照されるリファレンス。本体は `.claude/agents/trouble-shooter.md`。
> 各ステップの詳細テンプレート・判定基準表・調査コマンド集を収録している。本体の指示に従い、該当ステップの実行時に必要なセクションのみを Read すること。

---

## Step 1: 一次回答

### 収集する情報

ユーザーに以下を確認する（まとめて質問する）:

1. インシデント概要（一文で）
2. 対象システム名
3. 報告者名・報告受信経路（チャット / メール / 電話など）
4. 暫定の重要度（以下から選択）:
   - 至急: 業務が停止しているか、連携先システムへ影響が及んでいる
   - 高: 2営業日以内に対応が必要
   - 中: 1週間以内に対応が必要
   - 低: 情報共有のみ

### 出力

収集後、以下2点を生成してチャットに表示する。

**顧客向け一次回答テンプレート**:

```
お世話になっております。
<件名>についてのお問い合わせを承りました。
ご不便をおかけしており、誠に申し訳ございません。
現在、詳細を確認しております。
<対応期限（重要度に応じた日数）>以内に調査状況をご報告いたします。
追加の情報が必要な場合は、改めてご連絡差し上げます。
```

**社内エスカレーション通知テンプレート**:

```
【障害発生通知】<件名>
発生日時: <日時>
対象システム: <システム名>
重要度: <重要度>
概要: <概要>
現時点での対応: ヒアリング・調査開始
担当: <報告者>
```

## Step 2: 状況の把握（ヒアリング）

### 過去事例の自動検索

Step 1 で得た件名・システム名をもとに過去セッションファイルを検索する:

```bash
grep -rl "<システム名>" ./report/trouble/ 2>/dev/null | grep session
```

類似事例が見つかった場合はセッションファイルを Read して参考情報としてチャットに提示する。

### ヒアリングシートの生成

以下のヒアリングシートをチャットに出力し、ユーザーに回答を求める。
利用者はITリテラシーが必ずしも高くないため、問い合わせ内容を鵜呑みにせず、主観的表現を客観的情報に言い換えて確認するよう案内すること。

```markdown
## ヒアリングシート

ご不便おかけし申し訳ございません。現在発生している事象についてご回答いただけますでしょうか。

■ 対象システム: <Step 1 で確認済み>
■ 対象アカウント:
　（他にも同様の事象が発生している方はいますか？　はい / いいえ）
■ PC環境:
　機種:　OS:　ブラウザ・バージョン:　通信環境（社内LAN / Wi-Fi / テザリング等）:
■ 発生日時・頻度:
　（例: 先週月曜から継続中 / 今朝1回のみ）
■ 重要度（利用者の申告）:
　至急 / 高 / 中 / 低
■ 現在発生している事象をお教えください:
■ 正常に動作していないと判断した理由をお教えください:
■ 普段と今回で異なる点（画面出力の差異・入力データやパラメーターの差異）はありますか？:
■ 過去に同様の事象が発生したことはありますか？:
　ある / ない（ある場合: いつ頃ですか？）
■ 既に実施したトラブルシューティング手順はありますか？:
　（例: PC再起動、ブラウザのキャッシュクリアなど）

※ 画面出力やエラーメッセージはスクリーンショットを撮影いただくか、
　 エラーコードや文言を一言一句コピー＆ペーストしてください。
　 Excelへのペーストは制御文字（NBSPなど）が混入する場合があるため、
　 生のテキストか画像ファイルでご提供ください。
```

### 状況判断

回答を受け取ったら、以下の2点を確認してチャットに記載する:

| 確認項目 | 判断内容 |
|---|---|
| 見かけ上の症状と根本原因の乖離可能性 | 利用者が「仕様と異なる」と言っているが仕様を誤認している可能性はないか |
| Excelペーストによる制御文字混入 | ペーストで渡されたテキストに不可視文字が含まれていないか |

## Step 3: 優先順位の判定

### 判定基準

**軸1: 利用者業務への影響**

| レベル | 基準 |
|---|---|
| 全体影響 | 利用者全体が業務を継続できない |
| 部分影響 | 特定のユーザー・機能のみ影響 |
| 軽微 | 不便はあるが業務継続可能 |

**軸2: 連携システムへの波及**

| 種別 | 影響度 |
|---|---|
| API自動連携あり | 高（波及が自動的に広がる） |
| 手動ファイル連携 | 中（最悪、運用でカバー可能） |
| 単独システム | 低 |

### 判定ロジック

- 利用者が申告した重要度をそのまま受け入れず、2軸の評価結果と照合する
- 利用者申告より優先度が低いと判断した場合、その理由を提示してユーザーに最終判断を委ねる
- 判断がつかない場合は上長・周囲へのエスカレーションを促す
- 手動ファイル連携の場合は「運用でカバー可能な可能性」を明示する

### 出力

```
優先度判定結果: <至急 / 高 / 中 / 低>
根拠: <2軸の評価内容>
推奨対応期限: <営業日・時間>
備考: <利用者申告との差異がある場合に説明>
```

## Step 4: 事象の再現

### 再現確認の手順

ユーザーに以下を確認する:

1. 自社の開発・検証環境で同じ操作を試したか
2. 本番データを使用するか、マスク化データを使用するか

**マスク化データを使用する場合の警告**:
> マスク対象の文字列（氏名・メールアドレス等）そのものが原因の場合、
> マスク後は事象を再現できない可能性があります。
> 可能であれば、本番データに近い（実際の文字種・文字数を保った）データを使用してください。

### 本番 / 開発・検証環境の差分分析

自社環境で再現しない場合、または再現可否を確認する前に、**本番と検証環境の差分**を調査する。

#### 1. デプロイ履歴の確認

本番ブランチにのみ存在するコミットを確認する（環境ブランチ名はプロジェクトに応じて読み替える）:

```bash
# 本番に入っていて staging に入っていないコミット
git log --oneline origin/staging..origin/production 2>/dev/null \
  || git log --oneline HEAD~20..HEAD --format="%h %s"

# 直近の本番デプロイ履歴
git log --oneline -10 origin/production 2>/dev/null \
  || git log --oneline -10
```

#### 2. 環境固有設定ファイルの差分

値は表示せず、キーの差異のみ確認する:

```bash
# 環境設定ファイルの一覧
find . -name "*.Production.*" -o -name "*.Staging.*" \
       -o -name ".env.production" -o -name ".env.staging" \
       -o -name "appsettings.Production.json" \
  2>/dev/null | grep -v node_modules | grep -v .git

# 設定ファイルのキー一覧比較（値を除く）
grep -oh '"[^"]*"\s*:' <ファイルパス> | sort
```

#### 3. パッケージ・ランタイムバージョンの差異

```bash
# Node.js
cat package.json 2>/dev/null | grep '"version"\|"engines"'
cat package-lock.json 2>/dev/null | grep '"node"\|"npm"' | head -5

# .NET
find . -name "*.csproj" | xargs grep -h "TargetFramework" 2>/dev/null

# Python
cat requirements.txt 2>/dev/null | head -20
cat pyproject.toml 2>/dev/null | grep "requires-python\|python"
```

#### 4. IaC ファイルの環境別差分

```bash
# Bicep / Terraform / K8s マニフェスト
find . \( -name "*.bicep" -o -name "*.tf" -o -name "*.yaml" -o -name "*.yml" \) \
  -not -path "*/node_modules/*" -not -path "*/.git/*" \
  2>/dev/null | head -20
```

差分が見つかった場合はその内容を整理してチャットに提示し、障害との関連可能性をユーザーと議論する。

### クラウドサービス正常性の確認

WebSearch で以下を確認する（該当するもののみ）:

- Azure Service Health
- Microsoft 365 / Power Platform Service Health
- その他使用しているクラウドサービスのステータスページ

サービス障害が検出された場合は「外部起因の可能性が高い」と判定し Step 3 の優先度を再評価する。

### 判断と記録

| 状況 | 次のアクション |
|---|---|
| 自社環境で再現できた | Step 5 へ進む（以降は自社環境で調査） |
| 自社環境で再現できない | 顧客とのやり取りを継続する旨をユーザーに伝え、ヒアリングを深める |
| 外部クラウド障害が原因 | 障害ページの内容を報告し、復旧待ちの対応を提示する |

## Step 5: 問題箇所・条件の特定

### レイヤー別チェックポイント

ユーザーに各レイヤーの状況を確認しながら、問題のあるレイヤーを絞り込む。

#### サーバーサイド

| レイヤー | 確認観点 | 利用ツール |
|---|---|---|
| ハードウェア | CPU使用率・メモリ不足・ストレージ枯渇・マウントエラー | ユーザーへの質問 |
| ネットワーク | NIC障害・スイッチループ・WAF/IDS誤検知 | ユーザーへの質問 |
| クラウド | 仮想マシン停止・ストレージ容量不足・LB設定誤り | WebSearch（Step 4 で確認済みの場合はスキップ）|
| OS・ミドルウェア | サービス停止・バージョン不整合・パッチ未適用・時刻ずれ（NTP） | 設定ファイル読み取り |
| アプリ（正常系） | バグ・NULL/ダメ値の逆参照・ファイルパス誤り・無限ループ・バッファオーバーフロー | Grep・Read |
| アプリ（異常系） | 異常系の考慮漏れ | Grep・Read |
| データ（入力） | 仕様外データ・不完全エラーチェック・CSVフォーマットエラー・部分的な読み取り | Read（サンプルデータ確認）|
| データ（出力） | 文字化け・NBSP・文字コード変換の過不足・エスケープ漏れ・マスク不足 | Grep（出力ロジック）|
| API連携 | パラメーター誤り・通信エラー・認証エラー | Grep（API呼び出し箇所）|

#### クライアントサイド

| レイヤー | 確認観点 |
|---|---|
| ハードウェア | CPU/メモリ不足・入出力デバイス障害・ディスプレイ異常 |
| ネットワーク | NIC/ケーブル障害・Wi-Fi接続モード |
| OS・ミドルウェア | サービス停止・バージョン不整合・時刻設定ずれ |
| アプリ（正常系） | バグ・ファイルパス誤り・無限ループ |
| アプリ（異常系） | 異常系の考慮漏れ |

### ソースコードによる問題箇所の特定

エラーメッセージ・ログのキーワードからソースコード上の箇所を特定する:

```bash
# エラーメッセージからの逆引き
grep -rn "<エラーメッセージのキーワード>" src/ 2>/dev/null \
  | grep -v node_modules | grep -v .git

# 条件分岐の特定
grep -rn "if.*<条件キーワード>" src/ 2>/dev/null \
  | grep -v node_modules | grep -v .git

# 例外処理箇所の特定
grep -rn "catch\|throw\|Exception\|Error" src/ 2>/dev/null \
  | grep -v node_modules | grep -v .git | head -30
```

特定した箇所を Read で読み込み、問題の可能性をユーザーと確認する。

### 問題箇所特定の記録

特定した問題箇所（レイヤー・ファイル・関数名）とその根拠をセッションファイルに記録する。

## Step 6: 原因の特定

### 仮説の立て方

Step 5 で特定した問題箇所をもとに、以下の観点で原因仮説を立てる:

1. なぜその箇所で問題が起きたか（直接原因）
2. なぜその直接原因が生まれたか（根本原因）

### 相関関係と因果関係の区別

以下の点に注意して仮説を検証する:

- 「A が起きたとき B も起きる」（相関）≠「A が原因で B が起きた」（因果）
- 仮説を検証する具体的な手順をユーザーに提示する（例: 特定の設定値を変えて再試行する）
- 複数の原因候補がある場合は確度（高／中／低）を付けて一覧化する

### 出力

```markdown
## 原因の特定結果

### 直接原因（確度: 高 / 中 / 低）
<直接的に障害を引き起こした事象>

### 根本原因（確度: 高 / 中 / 低）
<プロセス・設計・設定上の原因>

### 原因候補一覧（複数ある場合）
| # | 仮説 | 確度 | 検証方法 |
|---|---|---|---|
| 1 | <仮説> | 高 | <検証手順> |
| 2 | <仮説> | 中 | <検証手順> |
```

## Step 7: 対策の検討

### 対策の種別

| 種別 | 定義 | 適用タイミング |
|---|---|---|
| 暫定対応 | 障害の影響を緩和し業務を継続するための応急処置 | 即時 |
| 運用でカバー | システムではなく業務フローを変更して回避 | 恒久対策の完成まで |
| 恒久対策 | 問題を抜本的に解決するための改修 | 計画・実施後 |

### ユーザーへの確認

以下を質問してから対策を提示する:

1. 現在、業務を止められる状況か（暫定対応の緊急度の確認）
2. システム改修の承認・リリースまでにかかる時間的制約はあるか
3. 運用での回避が業務上許容されるか

### 出力

```markdown
## 対策の検討結果

### 暫定対応
<即時実施可能な応急処置>
リスク: <この対応による副作用・注意点>

### 運用でカバー（必要な場合）
<業務フローの変更案>

### 恒久対策
<根本的な改修内容>
実施前提: <テスト・レビュー・承認フロー>
```

## Step 8: 障害報告書の生成

### 収集済み情報の確認

セッションファイルから Step 1〜7 の情報を読み込み、不足している項目をユーザーに確認する。

### 障害報告書の生成

`./report/trouble/YYYYMMDD_HHMMSS_<件名>_report.md` として保存する。

```markdown
# システム障害報告書

■ 作成日: YYYY年M月D日
■ 作成者（部署）: <担当者>

## 概要

本障害報告書は、YYYY年M月D日に発生した<対象システム>での障害について、
詳細ならびに経緯、原因、今後の対応内容をご報告するものです。
<顧客名>様ならびにご利用中のお客様へご迷惑をおかけいたしましたこと、
深くお詫び申し上げます。

## 日時

- 発生日時: YYYY年M月D日 HH時MM分
- 検知日時: YYYY年M月D日 HH時MM分
- 復旧日時: YYYY年M月D日 HH時MM分（復旧済みの場合）

## 詳細・影響範囲

<事象の詳細>

影響範囲: <影響したユーザー数・対象ユーザー属性・PC利用者への影響有無>

## 経緯

| 日時 | 内容 |
|---|---|
| YYYY/MM/DD HH:MM | <内容（能動態で記述）> |

## 発生原因

### 直接原因
<直接的に障害を引き起こした技術的事象>

### 根本原因
<プロセス・設計・レビュー体制上の原因>

## 対応策

### 暫定対応
<実施内容・実施日時>

### 恒久対策
<実施予定内容・実施予定日>

### 再発防止策
<テスト・レビュー体制の見直し等>

### 実施（済）手順
<暫定対応の詳細手順と実施済みかどうか>
```

**注意事項**:
- 経緯欄は能動態で記述する（「エラーが発生した」ではなく「〇〇チームが〇〇を実施した」）
- 個人を特定・非難する表現は使わない
- ログに個人情報が含まれる場合はマスキングする

### 完了の案内

報告書保存後にチャットに以下を表示する:

```
障害報告書を生成しました: ./report/trouble/<ファイル名>_report.md
セッションログ:             ./report/trouble/<ファイル名>_session.md

次のステップ（必要に応じて）:
- 詳細なポストモーテム・MTTD/MTTR分析が必要な場合: incident-responder サブエージェントを使用
- 再発防止のためのアーキテクチャ変更が必要な場合: /record adr で意思決定を記録
```

# /record スキル — 記録・証跡管理

**引数:** $ARGUMENTS

ユーザープロンプトと Claude Code の応答を `./doc/prompt/` に、思考過程を `./doc/thought/` に、アーキテクチャ意思決定を `./doc/adr/` に Markdown 形式で記録する。

## 引数の解釈

| 引数の形式 | 動作 |
|---|---|
| （なし） | `./doc/prompt/` と `./doc/thought/` に記録（トピック名は会話から自動生成） |
| `<トピック名>` | `./doc/prompt/` と `./doc/thought/` に記録（指定したトピック名を使用） |
| `adr <タイトル>` | `./doc/adr/` に ADR を新規作成 |

---

## 通常記録の実行手順（引数が "adr" で始まらない場合）

1. **トピック名の決定**
   - 引数が指定されている場合はそれをトピック名とする
   - 未指定の場合は直近の会話内容から端的なトピック名（例: `認証機能_設計`）を自分で生成する

2. **ファイル名の決定**（現在の日時を使用）
   ```
   doc/prompt/YYYYMMDD_HHMMSS_<トピック>.md
   doc/thought/YYYYMMDD_HHMMSS_<トピック>.md
   ```

3. **ディレクトリの確認**
   - `./doc/prompt/` が存在しない場合は作成する
   - `./doc/thought/` が存在しない場合は作成する

4. **`doc/prompt/` ファイルを作成する**（下記フォーマット参照）

5. **`doc/thought/` ファイルを作成する**（下記フォーマット参照）

6. **既存ファイルは絶対に上書きしない**。同名ファイルが存在する場合はファイル名末尾に `_2`、`_3` を付けて新規作成する

### doc/prompt/ フォーマット

```markdown
# <トピック>

**日時:** YYYY-MM-DD HH:MM
**フェーズ:** <現在のプロジェクトフェーズ（例: 要件定義、設計、実装、レビュー）>

## ユーザープロンプト

<ユーザーが入力した内容をそのまま記載する>

## Claude Codeの応答

<応答内容を記載する>
```

### doc/thought/ フォーマット

```markdown
# <トピック> — 思考過程

**日時:** YYYY-MM-DD HH:MM
**関連ドキュメント:** doc/prompt/YYYYMMDD_HHMMSS_<トピック>.md

## 問題・課題の認識

<何を判断・検討しようとしているか>

## 検討内容

<選択肢の洗い出し、各選択肢のトレードオフ、参照した情報など>

## 結論・判断

<何を選択したか、その理由>
```

## ADR 作成の実行手順（引数が "adr <タイトル>" の形式の場合）

1. **ファイル名の決定**
   ```
   doc/adr/YYYYMMDD_<連番>_<タイトル>.md
   ```
   連番は既存の ADR ファイルの最大番号 + 1（既存がなければ `001`）。
   採番の対象は `doc/adr/` **直下**の `YYYYMMDD_<連番>_<タイトル>.md` 形式のファイルのみとし、
   `doc/adr/references/`（ADR の根拠資料。`00_`〜 の連番だが ADR 番号ではない）は数えない

2. **`./doc/adr/` が存在しない場合は作成する**

3. **ADR ファイルを作成する**（下記フォーマット参照）

### ADR にするかの判断（粒度）— 本リポジトリの正本

**この節が粒度の判断基準の正本である。** 他のスキル・ルールはここを参照する。

以下の **3 条件をすべて満たす**ときのみ ADR にする。**1 つでも欠けたら ADR にしない。**

1. **覆すコストが大きい** — あとで変えるのに意味のある痛みを伴う
2. **文脈なしでは不可解** — 将来の読者が「なぜこうしたのか」と疑問に思う
3. **真のトレードオフの結果** — 本物の代替案があり、明確な理由で片方を選んだ

**控えめに使う。** 判断のたびに ADR を作らない。日々の実装判断・可逆な修正・単一の選択肢しかなかった事柄は対象外であり、通常記録（`doc/thought/`）で足りる。

ただし、個別のルールが ADR の作成を義務づけている場面（コピーレフト等のライセンス採否・新規スキルの採否・敵対的レビューで結論が変わったとき・意図的な非正規化など）は、3 条件の判定を待たずに作成する。**義務づけの一覧は各ルールファイルが正本であり、ここに転記しない**（転記すると更新が二重管理になる）。

### doc/adr/ フォーマット

```markdown
# ADR-<連番>: <タイトル>

**日時:** YYYY-MM-DD
**ステータス:** 提案中 / 承認済み / 廃止 / 置換済み

## コンテキスト

<この決定が必要になった背景・制約・課題>

## 検討した選択肢

1. **<選択肢 A>**: <概要>。メリット: 〜。デメリット: 〜。
2. **<選択肢 B>**: <概要>。メリット: 〜。デメリット: 〜。

## 決定

<何を選択したか>

## 理由

<なぜその選択肢を選んだか>

## 影響

<この決定が他の部分に与える影響・制約>
```

### 「検討した選択肢」の洗い出し（同質な案を並べない）

選択肢が「同じ発想の言い換え」になっていると比較の意味がない。**散らし方を意識的に選ぶ**。

| 散らし方 | 変える軸 | 向くテーマ |
|---|---|---|
| 制約変化 | 単純さ / 性能 / 拡張性 のどれを最優先するか | 実装方式、アルゴリズム選択、リファクタリング方針 |
| アプローチ変化 | トップダウン（要件・契約から） / ボトムアップ（部品の合成から） / 他分野からの類推 | API 設計、システム構成、テスト戦略、移行方式 |
| ペルソナ変化 | 専門家（正確さ重視） / 実務家（出荷優先） / 革新志向（前提を疑う） | ドキュメント方針、命名、運用ルール |

- 各選択肢には**却下理由**まで書く（「なぜ採らなかったか」が将来の再検討の起点になる）
- 「何もしない・現状維持」を選択肢に含める。これが最善のこともある
- 勝った案だけを書かず、**次善案の良い部分を取り込んだか**を「決定」節に一言残す
- **「決定」を書く前に採用案へ敵対的レビューを 1 パス回す**（`.claude/rules/adversarial-review.md`。ADR は実施タイミング 2 に該当）。反証に耐えなかった論点は「理由」節に、反証しきれなかった不確実性は「影響」節に残す
- 3 案を並列生成して比較する必要があるほど重い判断の場合は、ユーザーに Workflow（複数エージェントによる並列生成・評価）の利用を提案してから実施する。**Claude Code の判断で勝手に多数のエージェントを起動しない**

> 散らし方の 3 分類は [mhattingpete/claude-skills-marketplace](https://github.com/mhattingpete/claude-skills-marketplace) の `ensemble-solving`（Apache-2.0）を参考にした。スキル・エージェントとしての移植は見送っている（判断は ADR-016）。

## 注意事項

- `./doc/prompt/`・`./doc/thought/`・`./doc/adr/` のファイルは証跡であり、作成後は**いかなる理由があっても編集・削除してはならない**
- `Edit` ツールや上書き `Write` をこれらのファイルに使用してはならない
- 補足・修正が必要な場合は、新しいファイルを別名で作成する
- ADR のステータス変更（廃止・置換）が必要な場合も、既存 ADR は書き換えず新しい ADR を作成して参照する

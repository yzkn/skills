# /app-theme-proposer

## 引数の解釈

`$ARGUMENTS` の内容に応じて開始ステップを選択する。

| 内容 | 開始ステップ |
|---|---|
| 引数なし、または「提案して」のみ | Step 1（ヒアリング） |
| ヒアリング回答を含む文章 | Step 3（テーマ候補抽出） |
| テーマ名のみ（例: `社員マスタ`） | Step 5（詳細設計） |

---

## Step 1: ヒアリング（5問）

以下の質問を一度に提示し、回答を収集する。

**Q1. 対象ユーザーは誰ですか？**
`自分 / 社内の特定部門 / 全社員 / 顧客・一般ユーザー`

**Q2. 目的は何ですか？**
`ハンズオン学習 / 自社業務改善 / 顧客向け提案 / ポートフォリオ`

**Q3. 開発者の技術レベルを教えてください。**
`初めて（フォームとデータ表示のみ） / 1〜2本経験あり / 中級（外部API・DB連携経験あり）`

**Q4. 使用するプラットフォーム / 技術スタックはありますか？**
`Power Apps / Power Automate / Copilot Studio / Web（HTML/JS/CSS）/ Python / C#/.NET / Flutter / 指定なし`

**Q5. 開発期間はどのくらいですか？**
`1日（1〜3画面のMVP） / 数日〜1週間（3〜5画面） / 1ヶ月（フル機能）`

回答を受け取ったら Step 2 へ進む。

---

## Step 2: themes.md 読み込みとテーマ候補抽出

`.claude/skills/app-theme-proposer/themes.md` を Read で読み込む。

### フィルタリング

- Q3「初めて」→ 難易度「高」を除外
- Q3「初めて」かつ Q5「1日」→ 難易度「高」「中」を除外（「低」のみ）
- Q4 でプラットフォーム指定あり → 不一致タグのテーマを下位に

### スコアリング

| 条件 | 加点 |
|---|---|
| Q2「ハンズオン学習」→ カテゴリ 17（超入門）に一致 | +3 |
| Q2「業務改善」→ カテゴリ 01〜05 に一致 | +2 |
| Q2「顧客向け提案」→ カテゴリ 08・12・13 に一致 | +2 |
| Q4 で指定したプラットフォームタグと一致 | +3 |
| テーマ説明に Q2・Q4 のキーワードが含まれる | +1 |

### 多様性確保

- 5件が同じカテゴリに偏らないよう、上位カテゴリから 1 件ずつ選ぶ
- 難易度「低」と「中」を混在させる（Q3「中級」のみ「高」を 1 件含めてよい）

## Step 3: 比較表 Artifact の生成

5件のテーマ候補を HTML Artifact として生成する。

### 各テーマカードに含める情報

- テーマ名（大）
- カテゴリ名
- 難易度バッジ（低=緑 `#2E7D32` / 中=橙 `#E65100` / 高=赤 `#B71C1C`）
- 一言説明（最大35文字）
- コア機能（3件）— themes.md の内容から推定
- 習得できるスキル（2〜3件）— テーマから推定
- 推奨プラットフォーム

### Artifact レイアウト仕様

- ページタイトル: 「アプリ実装テーマ候補 — ヒアリング結果に基づく 5 件」
- 5 件をカード形式（横スクロール対応の flex レイアウト）で並べる
- ヘッダーにヒアリング回答のサマリー（Q1〜Q5 の回答を 1 行ずつ）を表示
- カラーパレット: 背景 `#F8F9FA`、カード `#FFFFFF`、ボーダー `#DEE2E6`、テキスト `#212529`
- ページ末尾に「このテーマで進める → テーマ番号で回答してください」と案内

Artifact 生成後、ユーザーにテーマ選択を促す。

---

## Step 4: 詳細仕様書の生成

選択されたテーマで以下のセクションを作成する。

### 前提条件・制約事項

- 対象ユーザー・利用シーン
- 利用プラットフォーム・技術スタック
- このMVPのスコープ外（対応しない機能）
- 依存サービス・必要ライセンス

### 機能一覧

| # | 機能名 | 概要 | 区分 | 優先度 |
|---|---|---|---|---|

- 区分: コア（MVP必須）/ 拡張（コア完成後に追加）
- 優先度: 高 / 中 / 低
- Q5「1日」の場合はコア機能を 3 件以内に絞る

### データモデル概要

- 主要エンティティ（3〜5個）
- 各エンティティの代表的な属性（3〜5項目）
- エンティティ間の関係（例: `社員 1 ── * 貸出記録 * ── 1 備品`）

### 画面設計

| 画面名 | 役割 | 主要 UI 要素 |
|---|---|---|

（ワイヤーフレームは次のステップで生成）

## Step 5: ワイヤーフレーム Artifact の生成

Step 4 で設計した画面を HTML Artifact として生成する。

### ワイヤーフレーム仕様

- 主要画面を 3〜5 画面、縦スクロールで並べる
- 各画面はスマートフォン枠（幅 375px）に収める
- スタイル:
  - 画面背景: `#F5F5F5`、枠線: 2px solid `#888888`、角丸: 12px
  - ヘッダーバー: `#CCCCCC`（アプリ名・戻るボタン）
  - プレースホルダーボックス: `#DDDDDD`（画像・地図など）
  - ボタン: `#BBBBBB`（ラベル付き）
  - リスト行: `#EEEEEE` ボーダー、各行にタイトル・サブテキスト
  - フォームフィールド: 白背景・`#AAAAAA` ボーダー・ラベル付き
- 実在の個人名・メールアドレス・電話番号を記載しない
- 各画面の上部に「画面名 / 役割」、下部に「この画面のポイント」（1〜2行）を表示

## Step 6: ファイルの保存

```bash
mkdir -p design/01_planning design/02_requirements
date +%Y%m%d
```

### テーマ比較サマリー

`design/01_planning/YYYYMMDD_app-theme-proposal.md`

内容: ヒアリング結果（Q1〜Q5）+ 5件のテーマ比較表（Markdown テーブル）+ 選定テーマと採用理由

### 詳細仕様書

`design/02_requirements/YYYYMMDD_app-spec_<テーマ名（英字スネークケース）>.md`

内容: Step 4 の全セクション（前提条件・機能一覧・データモデル・画面設計）

---

## 注意事項

- コード・既存ファイルの自動変更は行わない
- ヒアリング中に回答が文脈から推測できる場合は確認しつつ省略してよい
- themes.md が読み込めない場合は、台帳管理・承認ワークフロー・ゲームの内蔵リストを使って進める
- 個人情報を扱うアプリ（医療・金融・人事）はその旨を仕様書の前提条件に明記する
